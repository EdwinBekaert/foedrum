# M1 — First pour

Open · [GitHub milestone](https://github.com/EdwinBekaert/foedrum/milestone/2)

M1 takes a real issue in a test Brewery to a pull request, end to end. This page gets the rest of
what M1 built when the milestone closes; until then it shows how to see the Cellar at work.

## See it

```sh
npm ci
npm run demo
```

`npm run demo` makes a scratch Brewery and target repository in `.foedrum/tmp/demo/`, with bare
remotes there, and brews an order with Nip, the test-first recipe in Foedrum's `defaults/`,
through `foedrum serve`'s own Cellar; then a second order with `foedrum brew`, and it shows
`foedrum resume`'s line for the Cellarman's attempt. The Gauger and the Cellarman are scripted (the
Nip fixture of the M1 end-to-end test) and the code host is an in-process fake, so it needs node
and git only: no gh, no GitHub, no `claude`, no network, and nothing on your machine's git
configuration (ADR 0097, ADR 0139). The red proof and the checks run the target's own
`node --test`. It takes about 2 minutes on a Windows laptop.

It walks through ten steps and waits for Enter between them. `npm run demo -- --no-pause` goes
straight through, as it does when its input is not a terminal.

| Step | What to look for |
|---|---|
| 1. The diagnosis serve runs with | The demo's own diagnosis, not `foedrum doctor` on your machine: the demo starts no `claude` and no gh, so it checks neither. |
| 2. The order comes in | An issue in the Brewery, labelled `recipe:nip` by a user it lists, is all serve needs to take it as a batch for Nip. |
| 3. `foedrum status` as the batch moves | The batch goes from the order to brewing, and the Gauger's `gauge #1` has committed a failing test when the Cellar is killed. |
| 4. The kill and the restart | The Cellar is killed with SIGKILL mid-attempt. The restart finds `gauge #1` lost with it and brews it again as `gauge #2`. |
| 5. The red proof and the failed check | `red #1` must see the Gauger's test fail before `implement #1` may start. `green #1` fails the Cellarman's first fix, so `implement #2` starts, told why: the failed checks of step `green`, with the failed test's own `not ok` line. |
| 6. The pull request and the status comment | One pull request and one status comment on the fake code host, though the Cellar lived twice. The comment is shown as its Markdown, without its hidden revision marker. The pull request is #2 because the fake host numbers comments and pull requests from one counter. |
| 7. On tap | `foedrum status` shows the batch on tap, with its pull request. |
| 8. `foedrum brew 2 --as ann` | The same order again as issue #2, labelled once the Cellar has stopped and brewed from a terminal instead of the Cellar: `foedrum brew` orders it, routes it by its label, and drives that one batch to its own pull request. |
| 9. `foedrum resume 1-1 implement#2` | `resume` finds the Cellarman's session of that attempt and prints the line that opens it in its worktree in a terminal. The demo opens it nowhere, since it starts no `claude`. |
| 10. `foedrum replay 1-1` | Every event the batch went through, and the state the fold makes of them. |

`foedrum status`, `foedrum resume` and `foedrum replay` are the CLI's own commands, run in the
scratch Brewery: they read its event store, and nothing else that could reach GitHub.
`foedrum brew` runs on the demo's seams, as the Cellar does.

To brew a real order from a Claude Code session, install the plugin:

```sh
claude plugin marketplace add EdwinBekaert/foedrum
claude plugin install foedrum@foedrum
```

or, from a checkout, `claude --plugin-dir plugin`. Then run `/foedrum:brew <issue>` in a session
started in a Brewery's root. Its skills run `foedrum` from your PATH (a checkout's
`node src/cli/main.ts` until the npm package is published), and that one does reach gh, GitHub and
`claude` (ADR 0125).
