# 0107. One writer of the state worktree at a time, so an index.lock there is stale at once

Date: 2026-10-21 · Status: Accepted · Amends [0024](0024-state-branch-layout-outbox-and-divergence.md) (how a start and a flush use the state worktree) and [0061](0061-chaos-faults-at-sites-shrinking-worktrees-and-the-state-branch.md) (two drivers flushing one state worktree is no longer open)

## Context
The state worktree (`<workRoot>/state`) is where a driver writes the Brewery's state branch: its start checks that a commit can be made (`checkSigning`: `write-tree`, `commit-tree`) and every flush stages, commits and pushes there (`src/engine/state-branch-git.ts`, ADR 0024). git creates `index.lock` in the worktree's git folder while it writes the index, and a git that is killed leaves it behind; every later git that writes the index then fails with `Unable to create '…/index.lock': File exists`. A Cellar killed during a flush therefore could not start again: its signing check stopped on the lock (#300). CI's Windows legs saw it in the demo, which kills the Cellar mid-attempt (runs 39579197252 and 39588597434).

The attempt worktrees remove a stale lock in their repair, when it is older than a minute ([ADR 0029](0029-attempt-worktrees-layout-claims-and-repair.md), `removeStaleIndexLock`). The age stands in for knowing that no git runs there. For the state worktree a minute is too long, since the start is what waits, and the age would still be a guess: [ADR 0019](0019-interactive-sessions-and-one-command-layer.md) has two kinds of driver of one Brewery on one machine (the Cellar and interactive sessions), each with a driver lock of its own (ADR 0037), so a lock another live driver holds and one left behind look the same. Who may write the state worktree was left open by ADR 0024, ADR 0044 and ADR 0061 (#174).

## Decision
- **One writer at a time, through a lock of Foedrum's own.** A start and a flush of the state branch hold the state worktree's writer lock, `<workRoot>/state.lock` beside the worktree, for as long as they run git there. It is the same kind of lock as a driver's (`takeFileLock`, `src/platform/file-lock.ts`, ADR 0037): a SQLite database in exclusive locking mode, whose file lock the operating system drops when the process dies, however it dies. Inside one process, the state branch runs its start and its flushes one at a time already; the lock adds the other processes of the work root.
- **So an index.lock found under the lock is stale at once.** Every git that writes the state worktree's index runs under the writer lock, so while a start or a flush holds it, an `index.lock` in the worktree's git folder (`git rev-parse --absolute-git-dir`) was left by a git that no longer runs for a writer that no longer holds the lock. The start removes it after it opens the worktree and before `checkSigning`, and every flush before it writes, through `removeTree`, without the 60 s age of the attempt worktrees; each removal says so in one line (`foedrum serve: removed a stale index.lock from the state worktree: <path>`).
- **A live writer's lock is left alone.** A start that cannot take the writer lock waits for it, polling every 250 ms for at most 150 s (longer than a flush's push deadline of 120 s), and then stops with a `StateBranchStopError` that names the lock. A flush that cannot take it returns `failed` at once, without touching the worktree: its caller retries on its own deadline (the supervisor tick, ADR 0044), and a flush pushes every event after the marker, so the other driver's flush may already have pushed this one's events.
- **Not the driver lock:** each driver has its own owner and lock, so no driver lock covers the worktree. **Not one flusher per work root:** a driver that held the worktree for its whole run would keep every other driver of the Brewery from flushing, against ADR 0019's interactive sessions that work without the Cellar.

## Consequences
- A Cellar killed in a flush, or between a flush's `write-tree` and its commit, starts again: its start removes the lock, says so, and goes on.
- A git started by a driver that was killed can outlive it for the length of one git call (on Windows a killed process's children go on running unless they are in a job). Its lock is then removed while it still writes. The state worktree's index holds nothing of its own: every flush stages the worktree's files again (`add -A`) and the commit's contents come from the store's events, so the worst case is a git call of the next flush that fails once, which the next tick retries.
- The work root holds one more file of Foedrum's (`state.lock`), state outside the event store like the driver locks: it coordinates processes on one machine and decides nothing about a batch.
- The chaos case of the state branch (ADR 0061) gets no kill between `write-tree` and the commit: its in-memory state branch re-implements the shell's steps without git, so a lock in it would test the model's own removal, not `state-branch-git.ts`'s. The unit tests of the shell cover the removal with a fake git that answers `File exists` while a lock file is in a test folder, and a held writer lock in the same folder; the harness still runs one driver.

## Alternatives considered
- **The attempt worktrees' 60 s age:** the start of a killed Cellar would wait or fail for a minute, and the age guesses at what the lock knows.
- **Remove the lock only when a git call fails with `File exists`, and retry it:** the same removal, decided later and spread over every git call of the start and the flush; under the writer lock, removing before the first git call is the same answer with one check.
- **A pid file of the writer, taken over when that process is gone:** ADR 0037 rejected it for the driver locks: reading a process's start time differs on each platform, and two processes that find the same stale file must race safely to take it over.
