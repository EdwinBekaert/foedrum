# 0098. Foedrum's defaults load under the Brewery's files, and a brewer input can name a lens

Date: 2026-10-20 · Status: Accepted, amended by [0100](0100-nip-ships-with-a-default-cellarman-and-the-default-brewers-name-the-builder-alias.md) (the first default brewers and recipe) and [0141](0141-doctor-reports-prompt-sizes-unused-files-and-what-a-brewery-file-drops-from-its-default.md) · Amends [0053](0053-recipe-files-reach-the-engine-brewer-steps-in-a-line-first.md) (where the files are: the defaults load with the Brewery's, and lenses are read too) and [0041](0041-untrusted-input-in-per-prompt-nonce-tags.md) (a new input source, `lens`)

## Context
Foedrum ships default files under `defaults/`: today the five tasting lenses (`defaults/lenses/*.md`, [ADR 0017](0017-test-first-recipes-and-tasting-lenses.md), [ADR 0022](0022-five-default-lenses.md)), and soon the Gauger and Nip, the first default brewer and recipe (#218). Nothing loaded them. `loadRecipes` read only the Brewery's `recipes/` and `brewers/` (ADR 0053), whose last alternative said that default recipes would load "through the same function, next to the Brewery's" once there were any. A brewer's prompt could not hold a lens either: an input came from the order, an earlier step's out doc or a repository file (brewers-and-recipes §1.1), and a lens is none of those. A Gauger that designs tests needs the test-design lens's text in its prompt (#205).

## Decision
- **Where the defaults are.** `defaults/recipes/*.jsonc`, `defaults/brewers/*.md` and `defaults/lenses/*.md` of Foedrum's own install, found from the module's location (`FOEDRUM_DEFAULTS` in `src/engine/brewery-files.ts`, `../../defaults` from it), never from the working directory: a Brewery gets the defaults of the Foedrum that runs it, wherever it runs. They are read the way the Brewery's folders are (directly in the folder, by name; a file or folder that cannot be read is listed with the reason), and each carries its path from the install's root, `defaults/brewers/gauger.md`, so a problem line says which file it is about.
- **Under the Brewery's files, by name.** `readBreweryFiles` also reads the Brewery's `lenses/*.md`. `loadRecipes` takes the Brewery's recipes, brewers and lenses, then each default whose file name (without the extension) no Brewery file of the same kind has (`filesInUse`). A Brewery file of the same name replaces the default whole: the default is not read, so a broken default the Brewery replaces is no problem. A default the Brewery keeps loads like a Brewery file, all or nothing (ADR 0053): a broken one fails the load, naming its `defaults/` path. There is no merging of fields and no way to drop a default without replacing it. A recipe that names a brewer neither has fails with `it names no brewer "<name>" that the Brewery's brewers/ or Foedrum's defaults have (ADR 0098)`.
- **Which defaults are in use.** A valid load returns the paths of the defaults in use, recipes, then brewers, then lenses. `foedrum doctor` prints them in one line, `Defaults in use: defaults/lenses/correctness.md, … (a Brewery file of the same name replaces one)`, or `Defaults in use: none`, when it read the Brewery and its files load. `foedrum serve` checks the model alias of every brewer in use, the defaults' included.
- **A lens has no frontmatter.** A lens file's name is its name, and its whole text is the lens.
- **A brewer input can name a lens.** `"from": "lens:<name>"`, with a `PathSafeId` name, takes the text of the Brewery's `lenses/<name>.md`, else the default's. It is read when the brewer is loaded, and the step's brewer carries the lenses its inputs name (`StepBrewer.lenses`). A brewer whose lens input names a lens neither has is refused then, as its file: `brewers/<name>.md: the brewer "<name>" has the input "<input>" from the lens "<lens>", which neither the Brewery's lenses/ nor Foedrum's defaults have (ADR 0098)`. So an unknown lens stops the load, never an attempt.
- **Through the one prompt function.** A lens's text reaches the prompt as any input does, through `assembleBrewerPrompt` (ADR 0041), tagged with a new `source` kind, `lens <name>, file <path>`. It is held to the 1 MiB limit of an input when it loads: a larger lens fails the load as its file (`lenses/<name>.md: it is larger than 1048576 bytes, …`), once, instead of every attempt of its brewer. A lens whose file cannot be read or is too large is reported once, as that file, and not also as a lens its brewer lacks. It stays untrusted like every input: a Brewery's lens comes from whoever can commit to the Brewery, and a trusted input needs an ADR of its own (ADR 0041).

## Consequences
- A Brewery without a recipe, brewer or lens file of its own loads Foedrum's default of that name, and one with its own file loads its own. #218 adds the Gauger and Nip as the first default brewer and recipe, and every Brewery gets them.
- A default recipe or brewer that does not load stops every Brewery that keeps it, as a broken Brewery file does. Foedrum's own tests load the defaults, so that is a Foedrum defect, not a Brewery's; a Brewery works around it with a file of the same name.
- Every recipe a Brewery keeps from the defaults is brewable, and the router may pick it once there is a router. A Brewery that does not want a default recipe replaces it.
- The step `lens` field (brewers-and-recipes §3) still fails the load (ADR 0053). When tasting lands (#26), a Taster step's lens can be passed to the brewer the same way.
- A lens input's text is fixed when the recipes are loaded: a change to a lens file reaches a brewer the next time the Brewery's files are read.

## Alternatives considered
- **Defaults from the working directory or a `defaults/` folder of the Brewery.** The Brewery would carry copies, and a `node src/cli/main.ts` started elsewhere would read other files. Defaults belong to the installed Foedrum.
- **Merging a Brewery file into the default of its name, field by field.** Hard to read and to explain; a Brewery that wants a small change copies the default and edits it, which is one file to look at.
- **Loading only the defaults a Brewery names.** A Brewery names recipes through labels at run time, so the load could not tell which defaults it needs, and doctor could not check them all at once.
- **Reading the lens when the attempt is planned.** An unknown or unreadable lens would then fail the attempt, after the batch reached it, instead of the load. Reading it with the brewer refuses it once, at the start, with the brewer's file named.
- **A lens as a `file:` input.** `file:` reads the target repository's worktree, which the Brewery's and Foedrum's lenses are not in.
