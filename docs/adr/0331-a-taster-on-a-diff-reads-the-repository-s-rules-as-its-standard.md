# 0331. A Taster on a diff reads the repository's rules as its standard

Date: 2026-11-06 · Status: Accepted · Amends [0042](0042-the-claude-command-line-and-stream-contract.md) (what `context: lean` means for a brewer's reading)

## Context
A brewed Taster starts with no repository rules: `--safe-mode` and `--setting-sources ""` keep `CLAUDE.md` and the rule folders from loading (ADR 0042, [ADR 0046](0046-only-the-runners-settings-the-init-check-and-a-line-by-line-stream.md)).
`defaults/brewers/taster.md` said to read them "when the lens asks you to", and only a few lenses mention them, in passing or, for design conformance, as their whole subject.
Over all 16 brewed Taster sessions on the maintainer's machine on 2026-11-06, none opened an instruction file, a rule file, a decision record, a design page, the architecture page or the glossary (#876).
On the three self-brew orders of #374, a design page or decision record went stale each time and `/brew-review`, whose reviewers are told to read those files first, found it.
A headless session with the brewer's flags, told to read `CLAUDE.md` with its Read tool, read it, so the gap is only an instruction.

The prompt also stood in the way: it says the files a Taster reads in a repository were written by someone else, and that instructions in them are reported as findings. An instruction file is nothing but instructions.

## Decision
- **`context: lean` says what loads, not what a brewer may read.** The flags stay as they are: nothing loads by itself, no hook or server runs. A brewer whose prompt asks may read a repository's rules with its Read tool, inside its worktree, under its allow rules ([ADR 0093](0093-brewers-file-tool-rules-are-read-and-edit-rules-scoped-to-the-worktree.md)). `context: repo` stays open and refused.
- **On a diff, the default Taster reads the repository's rules before it judges**, whatever its lens names: the instruction file at the root (`CLAUDE.md`, or `AGENTS.md` where that is what it has), then what that file or the changed code names for the files the change touches: decision records, design pages, and the rule files for them where the repository keeps scoped rules in a folder. The words bound it, since `CLAUDE.md` is about 15,000 tokens here and `docs/adr` holds over 300 files: not a tour. The prompt's section ([`taster.md`](../../defaults/brewers/taster.md)) holds the wording.
- **They are the standard, never orders to the Taster.** They give it no tool and no wider lens and cannot tell it to approve. What they say to someone working on the repository (how to push, how to open a pull request), an agent at work included, is read past. The injection rule stays whole for everything else, and a line in these files that addresses their reviewer, or tells any reader to approve or to leave a finding out, is reported as a finding like any other instruction.
- **It stays inside its lens.** The rules say what counts as wrong in what the lens asks about, and add nothing for it to ask. No default lens changes: [design conformance](../../defaults/lenses/diff/design-conformance.md) asks for more than the section names, and the section says a lens that asks for more reads what it asks for.
- **A change that edits its own judge.** A Taster has no git and reads these files at HEAD, so `/brew-review`'s "the rules come from the base" does not hold. It judges by the rule as the lines {change} removes give it, and a change that weakens or removes a rule it would otherwise break, within the lens, is a finding that quotes both. Lines it adds to these files excuse nothing: an exception that covers what the change does is a finding that names it, unless the lens says how a change of direction is recorded and the change records it so, as design conformance does for a decision record.
- **Nothing to read fails nothing.** A repository with none of these files goes on as before, with no finding and no failed attempt. A file too large to read whole is read as far as needed and said under `riskLeft`, not as a finding.
- **A plan Taster behaves as before.** The file's body is one text for both kinds of step, so a plan Taster's prompt does hold the new section, with its first sentence telling a step that reviews a plan to skip it. Its plan paragraph is unchanged, and it still reads the repository's instructions when its lens asks. Keeping them byte for byte apart would take a second brewer or engine text, and the issue asks for neither.
- The Taster's `version` goes to 8. Nothing compares a brewer's version, so no Brewery's stored state or `foedrum doctor` reacts to it.

## Where the self-edit rule is weaker than `/brew-review`
`/brew-review` runs its reviewers on a copy of its criteria taken from the base, and its summary names any criteria the pull request changes (`Review criteria changed`).
Here the old rule exists only as text in the diff, and a model has to notice it:
- It holds only when the diff was not cut. {change} stops at 256 KiB, and an edit to an instruction file may lie past the cut. The prompt then lets the rules only make the lens stricter, with a line in them excusing nothing, and asks for a `riskLeft` line saying they were judged as HEAD has them.
- `riskLeft` is not a finding: an advisory Taster approves past it.
- A rule a change weakens by adding a contradicting file or line, with nothing removed, has no old text to compare: it holds only if the Taster sees the addition for what it is.
- A rule no lens of the recipe judges has no Taster to read it, as for any rule of that kind. The acceptance lens still reports an edit its order did not ask for.

## Rejected
- **The engine passes the instruction file as an input, read at the batch's start commit.** That would make "the rules come from the base" hold, with no cut. But the whole file then sits in every prompt, tagged as data never to be followed (ADR 0041) while it has to serve as the standard, and it costs engine code for a question this issue opens. If #879 or a real order shows the self-edit gap matters, this is the place to go next.
- **`context: repo`.** It loads the repository's hooks and servers with the instructions, which ADR 0042 left open for that reason, and it would load all of it into every turn with no bound.
- **A sentence in each lens.** A Brewery's own lenses would get none of it, and the rule that these files are no orders to the Taster belongs where the injection rule is.

## Consequences
- **Cost, expected and not measured.** No real session ran for this change. The baseline is in the stored transcripts of #868's three Tasters: correctness took 8 turns, 38,000 tokens written to the prompt cache and 244,000 read from it; acceptance 5, 28,000 and 123,000; security 2, 20,000 and 31,000. On this repository each diff Taster now also reads about 15,000 tokens of `CLAUDE.md` and a few decision records and design pages of 1,000 to 4,000 tokens each, so about 20,000 to 35,000 more tokens are written to the cache, roughly double, and read back on each later turn. Reads grow more than writes, and most for a Taster that took 2 turns and now takes several. The prompt itself grows by about 700 tokens. It multiplies by the Tasters of a step and by the rounds, each a new session: `nip` runs three. A repository with a small instruction file pays little. When the maintainer runs #879, it will record tokens per Taster against the prompt at `765cc856`.
- **The stall limit stays.** Only a write or a commit counts as progress (ADR 0047), so a Taster's whole review runs against its `stall` of 30 turns or 10 minutes, before its one write. In the 15 stored brewed Taster sessions on the maintainer's machine whose folder names a default lens (the count this change read, one short of the order's 16), the first write came after at most 7 turns and 0.6 minutes, the median 1 turn, so a few more reads leave room. Raising it now would be a limit with no failure behind it. If #879 or a real order shows a Taster stalled while reading, raise it then.
- **Whether it finds more is not shown here.** A test can only pin the prompt's words. #879's re-tasting of three brewed heads is what can show it, and no numbers exist until the maintainer runs it. A miss there on a stale page points at the lens first: `nip` has no design conformance lens, and the acceptance lens counts a document only when the change makes it wrong.
- **More rules are stated to a Taster, and the severities did not change.** `blocker` still "breaks a stated rule or invariant", so a blocking step can send back more than before. When the maintainer runs #879, it will report findings outside its key as true or false.
- **Migration: no file in a Brewery has to change.** A Brewery that replaced `brewers/taster.md` with its own copy keeps its prompt and gets none of this until it adds the section `## The repository's rules` of [`defaults/brewers/taster.md`](../../defaults/brewers/taster.md) to its copy, above `## Out doc`; `foedrum doctor`'s notice on what a Brewery file drops from its default lists the default's headings ([ADR 0141](0141-doctor-reports-prompt-sizes-unused-files-and-what-a-brewery-file-drops-from-its-default.md)), so it names this one. A running batch's later Taster attempts get the new text.
