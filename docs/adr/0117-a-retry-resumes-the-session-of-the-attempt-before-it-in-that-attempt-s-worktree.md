# 0117. A retry resumes the session of the attempt before it, in that attempt's worktree

Date: 2026-10-22 · Status: Accepted · Amends [0019](0019-interactive-sessions-and-one-command-layer.md) (only a retry resumes, and a session claude cannot find costs one failed attempt before the fresh one), [0029](0029-attempt-worktrees-layout-claims-and-repair.md) (when a resumed attempt's previous process is known to be gone, and the task tree of a resumed attempt), [0047](0047-the-claude-brewer-runner-its-stream-endings-and-progress.md) (a resume that finds no session fails retryably instead of blocking on the environment) [0059](0059-attempt-plans-from-the-brewer-of-the-step.md) (the plan of a resumed attempt), [0066](0066-the-task-tree-continues-from-the-latest-succeeded-attempt.md) (a resumed retry goes on in the failed attempt's worktree and branch instead of starting where it started, and the task tree of a resumed success is that worktree's branch) and [0116](0116-the-driver-records-each-attempt-s-session-and-claude-s-report-goes-on-step-finished.md) (a resumed attempt records the id of the session it continues, which the plan passes with `--resume`, and `SessionRef` gains `fallback`)

## Context
A brewer's `retryMode` says what its step's next attempt does after a failure: `fresh` starts a new Claude Code session with the same inputs, `resume` continues the session of the attempt before it ([ADR 0019](0019-interactive-sessions-and-one-command-layer.md)). [ADR 0029](0029-attempt-worktrees-layout-claims-and-repair.md) decided where a resumed attempt runs (in the worktree of the attempt whose session it continues, with no worktree of its own, never beside that attempt's process) and gave the manager `recreate` to get that worktree back. [ADR 0116](0116-the-driver-records-each-attempt-s-session-and-claude-s-report-goes-on-step-finished.md) records each attempt's session on `step.started`, and claude's init report on `step.finished`. Since #325 a lease claims every worktree its session continues (`worktreeClaims`). The claude command line takes `--resume <id>` (`claudeArgs`). Nothing planned or started a resumed attempt yet (#326, part 3 of #169), and the loader still refuses `retryMode: resume` ([ADR 0059](0059-attempt-plans-from-the-brewer-of-the-step.md)).

Four things were open: which attempts resume, when the previous attempt's process is known to be gone, what a resumed attempt is told, and what happens when its session or worktree cannot be got back ([ADR 0006](0006-no-mid-run-questions.md)'s and ADR 0019's fallback, a fresh attempt).

## Decision

### Which attempts resume
- **Only a retry.** `decide` marks an attempt it schedules because its step's attempt before it failed, as a retry: the engine's own retry of a retryable failure, a cancelled or lost attempt, and a human's `retry` from Stuck. The mark is new on `step.scheduled`, `retry: true`. No other attempt resumes: the first of a step, one a `rewind` or a `recipe` schedules (fresh sessions, ADR 0019's table), and, until #327, one an `answer` schedules, which still gets the answers as a fresh attempt's input.
- **Not the attempt a route schedules** (`onFail`, `onBlocked`). A route goes back to a step that succeeded, and the branch of that step's session is then the batch's task tree ([ADR 0066](0066-the-task-tree-continues-from-the-latest-succeeded-attempt.md)): a resumed attempt commits on it, so one that failed would move the task tree past the last success, and the next step would start from work that was refused. The chaos run of the attempt worktrees found it (seed 1949414058, 200 runs). So a routed attempt starts fresh, with the `route` input ([ADR 0128](0128-an-attempt-a-route-schedules-gets-what-sent-it-back.md)). A retry after a success (a step that succeeded, then Stuck on a divergence because its recipe file changed, then retried) starts fresh for the same reason.
- **Only when the driver is told the brewer resumes.** `openDriver` takes `resumes(attempt)`, false by default. `foedrum serve` does not set it, and the loader still refuses `retryMode: resume`, so no Brewery reaches this until #327 wires it to the brewer's `retryMode`. The tests set it.
- **The session to resume** is the one of the latest attempt of the step before it. It resumes only when that attempt **finished with claude's init report** (`step.finished`'s `claude`, ADR 0116):
  - an attempt that finished went through its runner's end, so its process is gone. One the supervisor lost, whose process may outlive its driver (#37), and one Stuck abandoned, which never finishes, have no report, and so do not resume ([ADR 0029](0029-attempt-worktrees-layout-claims-and-repair.md)'s "when the runner cannot tell that it is gone");
  - a run that ended before claude's init left no session to resume, or one claude did not start.
- **The worktree** is the one that session ran in: the attempt of the step with that session id that recorded a worktree. A resumed session keeps its id (claude's `--resume` without `--fork-session`), so every attempt of one session names the same id, and the one with a worktree made it.

### Starting it
- **It waits for the previous attempt's lease to go** ([ADR 0055](0055-a-step-waits-for-the-lease-of-its-abandoned-attempt.md)), as every attempt of a step does: also a lease `foedrum resume` holds on a finished attempt while an engineer's session runs ([ADR 0126](0126-foedrum-resume-opens-a-finished-attempt-s-session-in-its-worktree.md)).
- **Under its own lease, the driver recreates that worktree** (`recreate`, at the commit the attempt that made it recorded) and records `step.started` with `session: { id, resumes, worktree }`: the same id, `resumes` naming it, the recreated path, and **no `worktree`** of its own ([ADR 0029](0029-attempt-worktrees-layout-claims-and-repair.md)). Its lease claims that worktree through `session.resumes` (#325).
- **The fold** gives a resumed attempt that succeeds the task tree of the attempt whose worktree it ran in: its commits are on that attempt's branch ([ADR 0066](0066-the-task-tree-continues-from-the-latest-succeeded-attempt.md)). An input from that step (`step:<id>`) and a route's out doc are read where the attempt ran, `session.worktree`.

### Its plan
- **`claude --resume <id>`** in that worktree, with the brewer's model, effort, tools and settings as a fresh attempt has them ([ADR 0059](0059-attempt-plans-from-the-brewer-of-the-step.md)), and its commits counted on the branch of the attempt that made the worktree, from that attempt's commit.
- **The prompt is short**: the session already holds the brewer's instructions, the out doc contract and the inputs, which are not read again. It is `The run before this one ended before the step was done. Go on with the step where it stopped, then write <out doc> as your instructions say.`, with no tagged input.

### Falling back to a fresh attempt
- **When the session or its worktree cannot be got back, the attempt starts fresh** in a worktree of its own, as today, and records why on its session, `session.fallback` (ADR 0019's "records why"): `<step>#<n> has no session claude started`, `<step>#<n> succeeded, and its branch holds the task tree`, `no attempt of session <id> has a worktree`, `the worktree of <step>#<n> could not be recreated: <git's reason>`, or, for a driver whose worktree manager has no `recreate`, `the worktree of <step>#<n> cannot be recreated here`.
- **A session claude cannot find** ends the resumed run before claude's init (`claude ended before the session started`: a transcript gone after 30 days, another machine or config directory, ADR 0116). For a run that resumes, the stream reader names it a session it could not resume, and the attempt **fails retryably**, `claude could not resume the session: <claude's line>`, instead of blocking on the environment (ADR 0047). Its retry, if the step has one left, sees an attempt with no init report and starts fresh. A fresh run that ends the same way still blocks on the environment.

## Consequences
- With the switch on, a brewer whose attempt crashed, timed out its turn or was cancelled continues its own session in its own worktree, uncommitted work included, after the run's lease is gone.
- A missing session costs one attempt of the step's `maxAttempts` before the fresh one; a step with none left is Stuck as `attempts_exhausted`, and a human's `retry` starts fresh. Checking for the transcript before the start would save it, but how Claude Code stores transcripts is not Foedrum's (ADR 0116).
- An attempt lost with its driver, or abandoned by Stuck, starts fresh after a retry, though its worktree may hold its work. Telling that a lost process is gone needs the runner to record it (ADR 0029's follow-up with #37).
- `step.scheduled` and `SessionRef` gain an optional field each; earlier events stay valid.
- The guards in `src/checks/` (`testsUnchanged`, `noPush`, the red proof's commits) read an attempt's own `worktree` and branch; a resumed attempt has neither, so #327 must point them at the worktree it ran in before the loader lets a resuming brewer through.

## Alternatives considered
- **Infer a retry from the attempt before it (a failure, not a success).** No event: but a `rewind` or `recipe` back to a step whose last attempt failed would resume the old worktree instead of starting at the rewound commits.
- **Resume along a route too, and keep the task tree at a commit.** The routed attempt would see its own earlier work, but the task tree is a branch (ADR 0066), and the commit of a finished attempt is not in the log; recording it is a change of ADR 0066 for a later decision.
- **Resume after a lease expired.** The lease of a lost attempt expires while its process may still run (#37): two processes would share a worktree.
- **Look for the transcript before the start**, as `foedrum resume` does (ADR 0126). It saves an attempt, but puts Claude Code's storage layout into the engine; the stream already says when claude found no session.
- **Fall back within the same attempt** when claude finds no session. The attempt's recorded session would not be the one that ran, and its prompt would have to be both the short one and the full one.
- **Give a resumed attempt a worktree record of its own** (`worktree` on its `step.started`, the same path). Every reader of a worktree would think it made it: the cleanup would see two attempts claim one branch, and `starts` would count it again.
