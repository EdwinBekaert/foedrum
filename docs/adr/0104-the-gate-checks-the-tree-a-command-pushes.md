# 0104. The local gate checks the tree a command pushes, not the hook's working directory

Date: 2026-10-21 · Status: Accepted · Amends [0045](0045-the-local-gate-reads-commands-as-the-shells-would.md) (what the gate reads) , [0060](0060-the-gate-refuses-gh-pr-ready-without-the-review-summary.md) (where `gh pr ready` is looked up) and [0065](0065-the-gate-refuses-npx-of-packages-not-in-the-lockfile.md) (what counts as a change of directory before npx)

## Context
The gate ran the detached-HEAD check, the `node_modules` check and `npm run check` in the hook's working directory, and looked `gh pr ready`'s pull request up there (#132). A session in the main checkout that runs `git -C .claude/worktrees/<n> push`, or `cd .claude/worktrees/<n> && git push`, pushes the worktree while the gate checks the main checkout, so the worktree goes unchecked. The same holds for `gh pr create`, and for `cd <worktree> && gh pr ready` without a number, which marks the worktree's pull request ready while the gate reads the summary of another. Sessions `cd` into worktrees inside a command all the time.

## Decision
- **The reader tracks where each command runs.** Reading a command (ADR 0045), the gate keeps the directories it changes into, in order, from the hook's working directory: `cd`, `chdir`, `pushd`, `Set-Location`, `sl`, `Push-Location` and PowerShell's `cd..` and `cd\`, each lasting for the rest of the command, after any separator (`;`, `&&`, `||`, `|`) and inside `( )`. A wrapper's directory option applies to its command only: `env -C`/`--chdir`, `sudo -D`/`--chdir`, read as getopt reads a wrapper's options: also written straight after the option (`env -C../wt`), in a group of short options (`env -iC ../wt`) and as a unique prefix of the long option (`env --chd=../wt`). git's `-C` applies to that git call: the last one wins, each resolved against the ones before it, as git reads them. bash's `cd -P`/`-L`/`-e`, cmd's `cd /d` and `Set-Location -Path`/`-LiteralPath` are read as they are meant.
- **The checks run there.** For `git push` and `gh pr create`, the detached-HEAD check, the `node_modules` check and `npm run check` run in that directory, under the deadlines they had (10 s, and 540 s for the check). `gh pr ready` is looked up there too. The path is resolved against the hook's working directory, with `~` and `~/…` as the home directory and, on Windows, Git Bash's `/c/…` as the drive `C:`.
- **A directory computed at run time blocks.** When a change of directory is computed at run time (`cd "$d"`, `git -C $d`, `$( )`, `$env:X`) or kept by the shell (`cd -`, `~-`, `popd`, `Pop-Location`, a bare `cd`, a drive letter alone, `wsl --cd`, which names a Linux path), a `git push` is blocked with one line that says to push from inside the worktree, and `gh pr create` the same way. A `gh pr ready` without a number is blocked with one line that says to give the number; with a number, it is looked up in the hook's working directory, as before. A command nested in one that changes directory (`cd x && bash -c "git push"`) counts as computed, since the gate does not track where the nested command starts. The reading of a command without its quotes, when a quote is left open in one dialect (ADR 0045), is that command itself, so it runs where the command does.
- **Only trees inside the project.** The gate runs a tree's code before the command is approved (its `npm run check` script, git, gh), so a directory the command changes into must be inside the project the session works in: `CLAUDE_PROJECT_DIR`, compared by real path as the read guard does ([ADR 0049](0049-reviewers-read-only-inside-the-checkout.md)), and with its refusals before anything is resolved: on Windows a network, device or drive-less path, or one on another drive than the project's, is outside without being touched, so the gate opens no share a command names. A review's scratch clone under `.foedrum/tmp/` (of the project or of a worktree) is outside too, since it may hold someone else's branch. The path is resolved once, `..` included, and the checks run in that resolved path, so the reading the gate checks is the one that runs (ADR 0049's two readings of `link/..` are for tools that open the path as given). A push, `gh pr create` or `gh pr ready` that changes into a directory outside it is blocked with one line that names the directory, before anything runs there; so is every one that changes directory when `CLAUDE_PROJECT_DIR` is not set. A command that changes no directory runs in the hook's working directory, as before.
- **One tree per command.** A command that pushes or opens pull requests from two directories (`git -C a push; git -C b push`) is blocked with one line, so the check still runs once per command, within the hook's 600 s. The line also says that the gate may have read one directory two ways (a backslash path that bash and PowerShell read differently) and to write the path with `/`.

## Consequences
- Pushing a worktree from the main checkout, with `-C` or after `cd`, checks the worktree. CLAUDE.md's "push from the checkout you changed" now holds for these forms by the gate, not only by care.
- A command that is proposed with a directory outside the project (a clone of someone else's branch, a folder a prompt names) cannot make the gate run that tree's check script before the user sees the command.
- Reading a wrapper's options as getopt does also closes a gap of ADR 0045: `env -iC <dir> git push` read `<dir>` as the program and missed the push.
- `env -C`, `sudo -D`, `wsl --cd`, `popd` and `Pop-Location` now also count as a change of directory for npx and its relatives, which are refused after one (ADR 0065), since npx would look in another `node_modules`.
- A push after a computed `cd` is refused, even when it would have pushed the right tree: write the path as it is, or run the push from inside the worktree.
- The readings that assume the worst of what they cannot read (ADR 0045) now also see places. The re-reading of the arguments of a command that runs text skips the options before them, (`-c`, and cmd's `/c`), so `bash -c "cd x && git push"` and `cmd /c "cd /d x && git push"` check `x`; a reading that still sees the push in two places blocks it as two trees, failing closed.
- Not read, as with other arguments computed at run time: `git --git-dir`/`--work-tree`, `Start-Process -WorkingDirectory`, a `cd` whose program name is itself computed, and a `cd` whose effect does not reach the push: inside a subshell (`(cd x); git push`), before `|` (bash runs each part of a pipeline in a subshell) or before `||` (the push runs only when the cd failed). In those the gate checks `x` although the push runs in the hook's directory, so it checks a tree the push does not come from; the lexer does not keep which separator split the command. Trees are compared as resolved, without case folding, so one folder written in two cases is blocked as two trees, failing closed. Git Bash's `/c/…` is read as the drive in every reading, also PowerShell's, where it is a folder on the current drive; a PowerShell session that writes such a path gets the drive's tree checked. The gate catches a session's mistakes, not intent.

## Alternatives considered
- **Block every push that changes directory:** simple, but `cd <worktree> && git push` is the normal way for a session that started in the main checkout, and the gate can tell where it goes.
- **Check every directory a command names:** two checks can pass the hook's 600 s; one tree per command keeps the deadlines.
- **Resolve the push's checkout from git (`git rev-parse --show-toplevel` in the named directory):** one more process per push; the check already runs in the directory, and npm finds the package root from it.
