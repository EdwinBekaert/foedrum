# 0096. The engine's git reaches the remote outside the clone's configuration

Date: 2026-10-20 · Status: Accepted · Amends [0071](0071-the-openpullrequest-action-two-effects-of-the-batch.md) (where the push and its lookup run, and what they name) and [0090](0090-the-push-fetches-the-base-in-a-git-directory-of-its-own.md) (the git directory of its own serves every network call, and its root moves)

## Context
Every attempt worktree shares its clone's git directory, and so its configuration (`.git/config`, and whatever an `include.path` there names). A brewer that can write there, with `git config` or a script an allowed command runs, plants a command or a destination that the engine's git then uses with the maintainer's credentials: `credential.helper`, `core.askPass` and `core.sshCommand` run commands; `remote.<name>.url`, `remote.<name>.pushurl` and `url.<base>.insteadOf` send the call elsewhere; `core.hooksPath` runs hooks; `include.path` brings in any of them (#200, from the review of #178). A push raises the stakes over a fetch: it carries the push login gh's keyring holds (#194).

[ADR 0090](0090-the-push-fetches-the-base-in-a-git-directory-of-its-own.md) moved one call out: the fetch of the base runs in a git directory of Foedrum's own, whose objects are the clone's, from `https://github.com/<repo>.git`. The push and its `ls-remote` ([ADR 0071](0071-the-openpullrequest-action-two-effects-of-the-batch.md)) and the worktree manager's fetch before each new attempt ([ADR 0012](0012-worktrees-from-local-clones.md)) still ran in the clone, by its `origin`.

## Decision
- **Every network call the engine makes for a clone runs in a git directory of its own** (`withOwnGitDir`, `src/workspace/clone-git.ts`), the way ADR 0090's base fetch did: made per call with `git init --bare --template=` and the clone's object format, run with `GIT_OBJECT_DIRECTORY` at the clone's object store, `core.hooksPath` at the null device, `gc.auto=0` and `maintenance.auto=false`, and removed after, also when the call fails. Git there reads that directory's configuration and the user's global and system ones, never the clone's: no key of the list above, from the clone or through its includes, takes part.
  - **The push** (`openBranchPush`, `src/workspace/branch-push-git.ts`) pushes `<sha>:refs/heads/foedrum/…` to the URL Foedrum names, never by force and with `--no-verify`. The source is the commit's full sha, never a ref of the clone, so no ref a brewer moves changes what is sent.
  - **Its lookup** (`remoteTip`) is `ls-remote --refs <url> refs/heads/foedrum/…` from such a directory.
  - **The base fetch** (`baseTip`) is ADR 0090's, through the same helper.
  - **The worktree manager's fetch** (`fetchIntoClone`, used by `openAttemptWorktrees`): the directory's `refs/remotes/<remote>/*` start as the clone's (one `update-ref --stdin`), so the server sends only what the clone lacks and git's check of what came stops there, as ADR 0090 found for a blobless clone; `fetch --no-tags --no-write-fetch-head --no-recurse-submodules --no-auto-maintenance <url> +refs/heads/*:refs/remotes/<remote>/*` brings every branch; the refs that moved are written back into the clone with one `update-ref --stdin`, a local call (below). It fetches one at a time per manager, as before.
- **The URL is the one Foedrum names**: `https://github.com/<owner>/<name>.git`, the repository the pull request goes into, for `local` and `managed` repositories alike (`OwnRemote`, which `serveShell` builds per repository). Without it, `openBranchPush`'s network calls throw `The pushes from <clone> name no URL to reach the remote by` before git runs; `openAttemptWorktrees` requires it. Tests pass a local bare repository's path or `file://` URL instead; nothing in them reaches the network.
- **One root for these directories**: `<work root>/<owner>.<name>/git-dirs/` (`ownGitDirsRoot`), which replaces ADR 0090's `base/`. A killed call's directory stays there, a few kilobytes; one left in `base/` by an earlier version stays too.
- **Every other git call in the clone runs with `IN_CLONE`** (`inClone`, `src/workspace/clone-git.ts`): `GIT_NO_LAZY_FETCH=1`, `protocol.allow=never`, `core.hooksPath` at the null device and `core.fsmonitor=false` for the call. Those four turn off every route by which a planted key makes these calls start a command: a lazy fetch, which a partial clone (or a clone a brewer declares one with `extensions.partialClone`) makes when a call reads an object it lacks and which goes through the transport and so through the keys above; a hook; an fsmonitor. `protocol.allow=never` stops every transport on any git version, and `GIT_NO_LAZY_FETCH` (git 2.44) makes the failure clear. The secret scan's own settings (ADR 0079) stay, with these on top. Each engine call in a clone:

| Call | Where | A planted key that could make it start a command | Now |
|---|---|---|---|
| `push` | openPullRequest's push | `credential.helper`, `core.askPass`, `core.sshCommand`, `remote.*.url`/`pushurl`, `url.*.insteadOf`/`pushInsteadOf`, `include.path`; hooks (`pre-push`, `reference-transaction`) through `core.hooksPath` | own git directory |
| `ls-remote` | the push's lookup | the transport keys | own git directory |
| `fetch` of the base | the push's empty check and scan (ADR 0090) | the transport keys, hooks, `core.alternateRefsCommand` | own git directory (unchanged) |
| `fetch` of every branch | the worktree manager, before a new attempt | the transport keys, `reference-transaction` and other hooks, `core.alternateRefsCommand` | own git directory |
| `rev-parse` | the push's commit and the clone's directory; the manager's base, branch tips and directory | none, but a lazy fetch of an object the clone lacks | `IN_CLONE` |
| `merge-base --is-ancestor` | the push's empty check; `countCommits` (ADR 0074) | as `rev-parse` | `IN_CLONE` |
| `rev-list --count` | `countCommits` | as `rev-parse` | `IN_CLONE` |
| `log` ×3, `cat-file` | the secret scan (ADR 0079) | textconv, diff drivers and signatures, already off; a lazy fetch, already off | ADR 0079's settings and `IN_CLONE` |
| `for-each-ref`, `worktree list`, `config --remove-section` | the manager's cleanup and fetch | as `rev-parse` | `IN_CLONE` |
| `update-ref` | the cleanup's branch delete; the fetch's write-back | the `reference-transaction` hook | `IN_CLONE` |
| `status` | the manager's check of a worktree (`--git-dir` at its record, ADR 0029) | `core.fsmonitor` (already off); a lazy fetch; a clean filter (below) | `IN_CLONE`; filters stay |
| `worktree remove` | the cleanup | the `status` it runs in the worktree, as above | `IN_CLONE`; filters stay |
| `worktree add` | a new or resumed attempt | `post-checkout` and `reference-transaction` hooks; `core.fsmonitor`; a smudge filter (below); in a partial clone, the lazy fetch of the files it checks out, through the transport keys | `core.hooksPath` and `core.fsmonitor` for the call; filters and the lazy fetch stay |

- **What it does not cover, and why.**
  - **Filter drivers.** A brewer can commit a `.gitattributes` line (`* filter=x`), or write `info/attributes` in the clone's git directory, and set `filter.x.smudge`, `filter.x.clean` or `filter.x.process` in the clone's configuration. `worktree add` then runs the smudge command as it checks the files out, and `status` and `worktree remove` run the clean command on a file whose stat changed. No per-call setting turns every driver off: the call would have to name each driver, which only the brewer's own files know, and `GIT_ATTR_SOURCE` (an empty tree) skips the committed `.gitattributes` but not `info/attributes`.
  - **The lazy fetch of `worktree add` in a partial clone.** The managed clone is blobless, and its checkout downloads the files it needs by its promisor remote, which is the clone's configuration; turning the transport off would fail every checkout. Closing it means fetching the missing files first through a git directory of Foedrum's own and checking out with no transport.
  - **`readDiff`** (`src/checks/step-commits.ts`, the red proof's diff, ADR 0078) runs `git diff --no-ext-diff --no-textconv` in the clone: no driver runs, and its one route is a lazy fetch, as for `worktree add`.
  - Both need a change to how an attempt's worktree is checked out, beyond the calls #200 names; they go to a follow-up issue.
  - The user's global and system configuration apply, as for all git Foedrum runs (ADR 0090); a brewer that can write those, or the clone's object store (`objects/info/alternates`, which the git directory of its own reads), is #135's to close. `foedrum status` (the user's own command, ADR 0092) and the state branch (the Brewery checkout, which no brewer shares) are not in this list.

## Consequences
- `test/integration/clone-config.test.ts` plants each key of #200 in a real clone's configuration (`credential.helper` with the origin's URL at a local server that asks for a login, `core.sshCommand` with the origin's URL over ssh, `remote.origin.pushurl`, `url.<nowhere>.insteadOf`, `include.path` of a file that redirects the origin, and `core.hooksPath` with hooks that fail) and shows the push, the `ls-remote` and the worktree manager's fetch reach the origin and run none of them; and that a managed repository's blobless clone pushes and fetches through a git directory of its own.
- A `local` repository's worktrees now fetch from `https://github.com/<repo>.git`, as its push and base fetch do (ADR 0090), not from its clone's `origin`: the user needs read access there through their own credential helper, or a `url.*.insteadOf` of their global configuration for ssh. Its clone's `origin` is taken to be that repository, as ADR 0071 already took it for the push: the fetch writes the repository's branches into `refs/remotes/origin/*`.
- The worktree manager's fetch brings no tags, writes no `FETCH_HEAD`, prunes nothing, and brings every branch whatever the clone's own fetch refspec says. In the blobless managed clone it brings the new commits' files whole, since a filtered fetch needs a promisor remote, which is the clone's configuration; it brings only what the clone lacks.
- Each push, lookup and fetch makes and removes a small git directory, an `init` more per call.
- A local call that reads an object a partial clone lacks fails instead of fetching it; the engine's local calls read commits and refs, which a blobless clone has.

## Alternatives considered
- **Override the planted keys per call** (`-c credential.helper=`, `-c core.sshCommand=`, `-c remote.origin.url=…`). An empty `credential.helper` drops the user's own helpers too, `remote.<name>.url` is a list whose first entry wins, and `url.<base>.insteadOf` and `include.path` cannot be reset without knowing the names a brewer chose.
- **Check the clone's configuration and refuse anything Foedrum did not write.** As in ADR 0090: a user's clone has settings of the user's, and another batch's brewer can write between the check and the call.
- **A clone per attempt, or worktrees in a git directory brewers cannot write.** It would close filters and lazy fetches too, but changes how every attempt is made and needs the brewer's sandbox to keep it out (#135, #190); the follow-up weighs it against fetching first.
- **One lasting git directory per repository.** ADR 0090 rejected it: shared refs and locks, and what is written there stays.
- **Push from the clone with the URL on the command line** (`git push <url> <sha>:<ref>`). It skips `remote.origin.*`, but still reads the clone's `url.*.insteadOf`, credential helper, ssh command and includes.
