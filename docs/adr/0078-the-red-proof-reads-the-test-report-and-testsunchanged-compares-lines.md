# 0078. The red proof reads the test report, and testsUnchanged compares the lines of the tests

Date: 2026-10-18 · Status: Accepted · Amends [0017](0017-test-first-recipes-and-tasting-lenses.md) (how the red proof and the guard read), [0059](0059-attempt-plans-from-the-brewer-of-the-step.md) (testsUnchanged loads), [0064](0064-test-first-recipes-when-onblocked-and-a-red-proof-required.md) (test-first recipes brew), [0066](0066-the-task-tree-continues-from-the-latest-succeeded-attempt.md) (a step's commits) and [0069](0069-check-steps-run-the-repositorys-commands-in-an-attempt-of-their-own.md) (the red proof runs) · Amended by [0118](0118-retrymode-resume-loads-and-an-answer-resumes-the-session-that-asked.md) · Corrected 2026-10-18 (#210): both diffs are read in the clone, never in an attempt's worktree, whose `.git` file a brewer can rewrite

## Context
[ADR 0017](0017-test-first-recipes-and-tasting-lenses.md) makes test-first a recipe structure: the Gauger commits failing tests, a red proof (a check step with `"expect": "fail"` and `"of": "<step>"`) shows they fail because the behaviour is missing, and Cellarman makes them pass under the `testsUnchanged` guard. It fixes what each part must do, not how: the red proof reads "a structured test report (TAP or JUnit XML)" and passes only when "the tests committed by that step fail" on "a failed assertion or an error thrown by the code under test", with "no load, compile, import or collection error"; the guard rejects an attempt that "changes or removes the test declarations or assertions" of those tests, while "helpers, fixtures, imports and new tests may change".

[ADR 0064](0064-test-first-recipes-when-onblocked-and-a-red-proof-required.md) made the loader require a red proof of every test-first recipe, and [ADR 0069](0069-check-steps-run-the-repositorys-commands-in-an-attempt-of-their-own.md) runs check steps but refuses the red proof by name, so no test-first recipe loads. [ADR 0059](0059-attempt-plans-from-the-brewer-of-the-step.md) refuses every guard but `requiresOutDoc`. This decision is #176: how the engine reads a report, what it counts as missing behaviour, which tests are the proven step's, what the guard compares, and where a repository without a test report stops.

Foedrum works in any language (ADR 0023), so none of this can lean on one language's parser; and the engine decides without a model (architecture §4).

## Decision

### The red proof runs the test check and judges its report
- **It loads.** ADR 0069's refusal of the red proof goes. Its `of` must name a step whose brewer produces commits, or the load fails: `step "<id>" proves the tests of step "<of>", whose brewer commits nothing (ADR 0078)`, since it would find no tests. The loader keeps the step each red proof proves (`StepChecks.proves`) and each recipe's first red proof (`StepChecks.redProof`), which ADR 0064's rule makes the one that proves the first writing step.
- **What the proven step committed** is read with git in the clone the attempt worktrees were added to (the one `serve` gives the attempt plans, ADR 0074), never by discovery in the red proof's worktree, whose `.git` file git would follow (#210): `git diff` from where the step's **first** attempt started to the branch of its latest attempt that succeeded, with `--no-color --no-ext-diff --no-textconv --text --no-renames --unified=0` (`--text`, so a committed `.gitattributes` cannot make the tests binary files and hide their lines), fixed `a/` and `b/` prefixes and `core.quotePath=false`, whatever the user's settings say, and up to 16 MiB of output instead of the runner's default 4 MiB (ADR 0035), so large fixtures or a regenerated lock file still read. ADR 0066 gave a step's commits as its succeeded attempt's own range; from the first attempt instead, a Gauger that a failed red proof sent back keeps the tests its first attempt wrote, since its second attempt starts on top of them. A step with no succeeded attempt blocks the red proof (`divergence`); git that cannot read the range blocks it on the environment.
- **The run** is the repository's `test` check, as any check runs (ADR 0069: the platform shell, the brewers' minimal environment, the deadline less 10 s, a kill-on-close Job Object on Windows), and its reading is recorded on `step.finished` as any check's. A check that did not exit (killed, ended by a signal, unstarted) ends the step as ADR 0069 says. Otherwise the **exit code decides nothing**: the report does.
- **The report** is where `testReport` in `foedrum.jsonc` says (ADR 0023): `{ "format": "tap" }` reads the command's stdout, not stderr, which may then be as large as a report file (16 MiB); `{ "format": "tap" | "junit", "path": … }` reads that file of the worktree, which the runner removes before the command runs, a folder included, through the platform's removal, which retries a file another process holds open, so a report the tree holds (committed by a brewer, or left over) never stands for this run's. It removes only inside the worktree, with links on the path resolved; a path it cannot remove, or one that leads out of the worktree, blocks the red proof on the environment, naming why. After the command it reads the file as an out doc is read (a regular file inside the worktree, one link, at most 16 MiB). A missing file, one that cannot be read, or one that is not the format fails the red proof, naming why.
- **TAP** (versions 13 and 14): a carriage return alone ends a line, as a line feed does; every test point (`ok`/`not ok`, an optional number and dash, the description up to the first unescaped `#`), at any indent; a `SKIP` or `TODO` directive makes it skipped; a test point after deeper-indented ones is their parent (TAP 14 and node put subtests first); the YAML block after a point is its detail, up to its `...` or, when that never comes, a line shallower than its `---`; `Bail out!` is recorded; the `# Subtest: <name>` comment before a test only names it and is dropped; every other line (comments, a runner's own output) is the text outside any test. Text without a test point is not TAP.
- **JUnit XML**: the `testcase` elements under a `testsuites` or `testsuite` root, nested suites included, read by a small XML reader of Foedrum's own (no dependency): a `failure` or `error` child fails a test, `skipped` skips it, and their `type`, `message` and text, with the testcase's `system-out` and `system-err`, are its detail; a suite's own `system-out` and `system-err` are the text outside any test. A DOCTYPE with an internal subset is refused (it could define entities); an undefined entity is not XML, and neither is a report nested deeper than 256 elements.

### What counts as missing behaviour
The red proof passes only when each of these holds, checked in this order; the first that does not names the reason, `the red proof of step <of> failed: <why>`:
1. The run did not bail out.
2. **No load, compile, import or collection error anywhere in the report**: in the text outside any test, or in the detail of any failed test. One is a line that names one of a fixed list: `SyntaxError`, `ReferenceError`, `Cannot find module`, `ERR_MODULE_NOT_FOUND`, `does not provide an export named`, `Test suite failed to run`, `ModuleNotFoundError`, `ImportError`, `NameError`, `ERROR collecting`, `errors during collection`, `collection failure` or `error`, `error TS<n>`, `error CS<n>`, `cannot find symbol`, `NoClassDefFoundError`, `ClassNotFoundException`, `compile error` or `failure` or `failed`, `compilation error` or `failure` or `failed`, `failed to compile`, `could not compile`. node writes a test file's load error as comments above a test that says only `test failed`, so the whole report is read, not each test's own detail. A compiled language whose build fails writes no report at all, which fails the red proof as above. A proven test that fails with one of these is refused too, even when the code under test threw it: a report cannot tell the two apart, and a Gauger that tests such an error asserts on it instead.
3. **The proven step's tests are in the report.** A test is one of them when it has no subtests and its name, as the report gives it, stands as a whole in a line the step added: after something that is no letter, digit, underscore or dot, and before something that is none of those nor a space, or the line's end (a CRLF file's carriage return does not count), in a line that does not only assert: a call of the function a test is named after (`calc.add(`, `assert.equal(add(1, 2), 3)`) declares nothing. A name longer than 1,000 characters is never one of them, so names that code a brewer wrote cannot make the match slow, as a declaration writes it (`test('adds two numbers'`, `def test_adds(`, `void addsTwoNumbers(`). The name also counts without the parameters a runner appends (`adds(int, int)[1]` as `adds`), and as its last part after a class or module (`com.acme.AddTest.adds` as `adds`) when that part has at least three characters. A runner that reports a name the declaration does not hold (jest-junit's default `{classname} {title}`) needs its name template set to the test's own title.
4. **None of them passed**: one that passes before the implementation is a stub that returns a value (#46, #47); the reason says stubs throw.
5. **None of them was skipped**: a skipped test proves nothing.

Tests the step did not add may pass, or fail on an assertion; only a load error among them refuses the run. A red proof that passes ends `succeeded` (`output: null`); one that does not ends `failed`, not retryable, and takes its `onFail` route, else makes the batch Stuck (ADR 0069).

### testsUnchanged compares the lines of the proven step's tests
- **It loads**: the loader takes it out of ADR 0059's refused guards. It guards the tests of the step that the recipe's first red proof proves; in a recipe without a red proof, or a batch that skipped the proven step (`testFirst` off) or never got it to succeed, it has nothing to guard.
- **Where it runs.** `guardTests` (`src/checks/tests-guard.ts`) wraps the brewer runner. When an attempt of a step whose brewer has the guard ends `succeeded`, it reads two diffs in the clone, as the red proof does, never in the attempt's worktree, whose `.git` file its brewer can point at a repository of its own (#210): what the proven step committed (as the red proof reads it) and what this attempt committed, from where it started to the tip of its attempt branch, in the files the proven step committed only (each given to git as a literal path, since a brewer names them). The branch, not `HEAD`: the task tree carries the branch on (ADR 0066), so an attempt that moves `HEAD` off it cannot hide its commits from the guard. Meanwhile it answers the attempt's progress, so its lease holds, and a stop aborts git and ends the attempt `cancelled`. Every other ending passes through untouched.
- **What it compares.** The proven step's test files are the files in which it added a line that declares a test (`test(`, `it(`, `describe(` and their kin, `def test…(`, `@Test`, `[Fact]`, `[Theory]`, `[Test…]`, `func Test…(`, `#[test]`, `TEST(`). In them, the protected lines are the lines it added that declare a test or assert (`assert…`, `expect…(`, `.should`, `raises(`, `t.Error`/`t.Fatal`/`t.Fail…`, `EXPECT_…(`/`ASSERT_…(`), except a line that only imports. The attempt fails the guard when, in a test file, it removed a protected line more often than it added it back, each line compared trimmed. So moving a test within its file or reindenting it is no change; moving it to another file or renaming the file is one; new tests, fixtures, helpers, imports and the stubs, which are in other files or are no declaration or assertion, change freely.
- **The outcome**: `failed`, retryable, `the guard testsUnchanged: the attempt changed or removed <n> line(s) of the tests of step <of>, <file>: <line> (and <n> more)`. Another attempt starts afresh at the task tree and may keep the tests; the brewer's `maxAttempts` bounds it, then the batch is Stuck. Cellarman that believes a test is wrong reports `blocked` + `findings`, which `onBlocked` sends back to the Gauger (ADR 0064). Git that cannot read either diff blocks the attempt on the environment.

### A repository without a test report stops the batch at its start
`stepRunner` takes a `refuse` that blocks an attempt on the environment without starting it. `foedrum serve` refuses every attempt of a batch whose recipe's first red proof would run (`Recipe.skip` answers nothing for it) when the batch's repository has no `testReport`: `recipe <name> proves its tests red, which needs the test report of <repo>: add "testReport" to its entry in foedrum.jsonc, { "format": "tap" } or { "format": "junit", "path": "<file>" } (ADR 0017)`. The batch's first attempt is the first refused, so it is Stuck before a brewer spends a token. The check runner gives the same line if a red proof gets that far. The engine's `decide` stays without repositories: the step runner is the first place that knows which repository a batch writes in.

## Consequences
- A test-first recipe loads and brews in `foedrum serve`: `test/integration/test-first.test.ts` runs one through `openDriver` with real git, real worktrees and `node --test` writing TAP, and the fake brewer runner in claude's place. The Gauger's first commit does not compile and the red proof sends it back; Cellarman's first attempt weakens an assertion and the guard stops it; the bottle's branch ends with the red commit, then the green one.
- The two lists (load errors; declarations and assertions) are what make both parts language-independent, and also what they miss. A load error worded otherwise passes as missing behaviour; an assertion style the list lacks is not protected. Either list grows by a change to the engine, with a test.
- A line of a test file that asserts but is a helper (`const check = (x) => assert.ok(x)` in the test file itself) is protected, so Cellarman cannot change it. A helper in a file of its own is free.
- The proven step's commits end at its attempt branch, a ref every worktree of the clone shares. An attempt that moved it (`git branch -f`) would hide the tests from the guard; brewers get git only through allow rules with a fixed subcommand (ADR 0062), so one can only when its Brewery allows a subcommand that moves refs. Recording each attempt's tip on `step.finished` would close this without relying on that rule; it is left for a follow-up.
- A red proof costs one run of the test check and one git call; a guarded attempt costs two git calls after it ends.
- As for any check (ADR 0069), a Gauger sent back by `onFail` is not yet told why: the reason is in the event log, not in its prompt.
- ADR 0066's "a step's commits are `<start>..<tip of its succeeded attempt's branch>`" now starts at the step's first attempt.
- The router's switch-off of `testFirst` for one order, the Gauger as a default brewer (with how Foedrum's default files and lens texts reach a brewer) and Nip as a default recipe move to #205.

## Alternatives considered
- **Find the proven step's tests by a baseline run** of the tests at the tree before the step, taking the tests that are new or newly failing. Exact, but it doubles the test runs and needs a second worktree per red proof, and a baseline that does not build says nothing.
- **Find them by file** (JUnit's `file` attribute, a TAP diagnostic's `location`). Not every runner writes one, and TAP has no standard for it.
- **Read each runner's failure kinds** (node's `failureType`, JUnit's `failure` against `error`). Runner-specific, and a stub's "not implemented" is a JUnit `error` while a failed import may be too; a compile error often leaves no test to classify.
- **Parse the tests** for the guard. Exact for one language, and Foedrum works in any.
- **Keep every line the proven step added.** Simple, but blocks the helpers, imports and fixtures ADR 0017 lets change ("a file-level guard" is refused there for the same reason).
- **Compare the test names in the reports** before and after. Catches a removed test, not a weakened assertion.
- **Check the test report in `decide`, at routing.** `decide` is pure and knows no repositories; teaching it `foedrum.jsonc` for one rule would widen every caller.
- **A guard failure that is not retried.** A fresh attempt may well keep the tests; `maxAttempts` already bounds the cost, and a brewer that disagrees has `blocked` + `findings`.
