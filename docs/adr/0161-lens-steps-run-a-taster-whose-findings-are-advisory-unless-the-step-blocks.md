# 0161. Lens steps run a Taster, whose findings are advisory unless the step blocks

Date: 2026-10-23 · Status: Accepted · Amends [0017](0017-test-first-recipes-and-tasting-lenses.md) (lens steps run one after another until parallel groups, #428; what makes a brewer a Taster; blocking on a Taster's step), [0053](0053-recipe-files-reach-the-engine-brewer-steps-in-a-line-first.md) and [0143](0143-lenses-in-two-folders-diff-and-plan.md) (a step's `lens` and `blocking` load on a Taster's step), [0098](0098-foedrum-s-defaults-load-under-the-brewery-s-files-and-a-brewer-input-can-name-a-lens.md) (a step's lens reaches its brewer as a lens input) and [0041](0041-untrusted-input-in-per-prompt-nonce-tags.md) (a new input source, `change`)

## Context
[ADR 0017](0017-test-first-recipes-and-tasting-lenses.md) decided that tasting is done through lenses: a recipe step gives the Taster a `lens`, and the Taster reviews through it.
Nothing ran it. The load refused every step with a `lens` or `blocking` (`which the engine does not follow yet`, [ADR 0053](0053-recipe-files-reach-the-engine-brewer-steps-in-a-line-first.md)), Foedrum shipped no Taster, and an out doc had no place for findings or a verdict: every out doc was read against the contract's schema.
Since [ADR 0143](0143-lenses-in-two-folders-diff-and-plan.md) a step's lens is named by its folder, and the load already checks it against what the step reviews.
Running lens steps side by side in a `parallel` group is #428, the simplify lens #429, and house-yeast rules that reach a lens's Taster #434.

## Decision
- **A Taster is a brewer whose out doc schema is `tasting`** (`output.schema`). Its out doc adds `findings` to the contract, each with `severity` (`blocker`, `major`, `minor`), `why`, `introduced` ([ADR 0094](0094-reviewers-show-their-evidence-and-mark-pre-existing-defects.md)), and `file` and `line` unless it is about the change as a whole, and a `verdict`, `approve` or `changes`, that a `done` must have (`TastingOutDoc`, `src/schemas/out-doc.ts`). The schema, not the brewer's name, is what the engine reads, so a Brewery can write Tasters of its own.
- **A lens step loads on a Taster only.** The load refuses, each with its line: a `lens` on another brewer (`step "x" has a "lens", but its brewer "cellarman" is no Taster: …`), a Taster's step without a `lens`, a lens neither the Brewery nor the defaults have, and a Taster with an input named `lens` already. `blocking` on another brewer is Brett's (ADR 0017) and still fails as not followed yet.
- **The step's lens is the Taster's input `lens`**, ADR 0098's lens input added to the step's brewer by the load, so the lens reaches the prompt through `assembleBrewerPrompt`, tagged `lens diff/correctness, file defaults/lenses/diff/correctness.md`, as a lens a brewer names itself does. Doctor counts it as a lens in use.
- **A Taster that reviews a diff is told where the change starts**: a `change` input, the commit its batch started at in the worktree's repository (`Batch.starts`), with how to read it, `git diff <commit> HEAD` and `git log <commit>..HEAD`. The default Taster may run those and `git show`. A Taster that reviews a plan gets none; what it reads is #391's to settle.
- **Findings are advisory by default.** A `done` Taster succeeds whatever its verdict, and the batch goes on. The pull request's body lists each Taster's verdict and findings under its step, in the fenced block of what each step reported (ADR 0071, ADR 0088), and the status comment lists the findings in a **Findings** section, ten per step and a count of the rest.
- **`"blocking": true` on a Taster's step makes `changes` block.** The runner settles a `done` with the verdict `changes` as `blocked` by `findings` (`settleAttempt`), so the engine, not the model, decides that it holds the batch up. The step's own `onBlocked` route then sends the batch back, with the Taster's out doc as the route input (ADR 0128), as it does for any findings blocker, and after its `maxRounds` the batch is Stuck. No second review mechanism: a recipe that wants Cellarman to fix what a Taster found writes `"onBlocked": { "findings": { "goto": "implement", "maxRounds": 1 } }` on the lens step.
- **Lens steps run one after another** until parallel groups land (#428): a recipe with one lens step per lens lists them in a line.
- **Foedrum ships a default Taster**, `defaults/brewers/taster.md`: read-only (`access: read`, `produces: report`, no tool that writes), on the alias `builder`, which every Brewery that keeps the default brewers maps already ([ADR 0100](0100-nip-ships-with-a-default-cellarman-and-the-default-brewers-name-the-builder-alias.md)). Its verdict is `changes` when the change introduced a blocker or major finding. It runs `git diff`, `git log` and `git show` only; `git diff --output` could write a file, but only in the Taster's own worktree, which no step commits or reads.
- **Nip tastes through `diff/correctness` after green**, advisory, before the pull request opens. That costs each Nip batch one more brewer run: its time (the Taster's deadline is 20 minutes, its stall limit 10) and its tokens, a lens of about 600 words, the order and whatever of the change it reads. A Brewery that does not want it replaces `nip.jsonc` (ADR 0098).

## Consequences
- A recipe can review its batch's change through any lens, and a pull request shows what each lens found, also when nothing holds the batch up.
- The status comment and the pull request body hold model output in one more place; it goes through the same filters as the summaries and assumptions (one escaped line, secrets left out).
- A Taster's attempt that ends `blocked` by findings on its own, on a step without a route, makes the batch Stuck, as any brewer's would; the default Taster is told to end `done`.
- Every Nip batch runs a Taster, so the demo shows its finding in the pull request and the status comment.

## Alternatives considered
- **The Taster by its name, `taster`.** Simpler, but a Brewery's second Taster under another name would be refused, and the engine needs the schema anyway to read the verdict.
- **The Taster decides to block, by ending `blocked`.** The model would choose whether a finding holds the batch up; ADR 0017 keeps that in the recipe, and the engine reads the verdict.
- **A `blocking` route of its own, back to a step the lens step names.** A second way back next to `onBlocked`, with its own rounds to count; the findings route already carries the out doc to the step it goes to.
- **The engine puts the diff in the prompt.** It would start git when planning an attempt and send a whole diff every time; the commit and two git commands let the Taster read what its lens needs.
