# 0066. The task tree continues from the latest succeeded attempt

Date: 2026-10-17 · Status: Accepted, amended by [0078](0078-the-red-proof-reads-the-test-report-and-testsunchanged-compares-lines.md) (a step's commits start at its first attempt) · Amends [0029](0029-attempt-worktrees-layout-claims-and-repair.md) and [0037](0037-attempt-worktrees-in-the-engine-and-driver-locks.md) (where a new attempt's worktree starts), [0059](0059-attempt-plans-from-the-brewer-of-the-step.md) (what a brewer may ask for) and [0063](0063-foedrum-serve-its-configuration-and-wiring.md) (its open question on `tree: task`)

## Context
Every attempt writes in a git worktree of its own, made by the driver under the attempt's lease and recorded in `step.started` (ADR 0029, ADR 0037). Until now each one starts at the repository's base, `origin/<base>` (ADR 0063), so a later step does not see what an earlier step committed: a recipe of two writing steps (Gauger, then Cellarman) cannot work. A brewer asks for `"tree": "task"`, the batch's task tree, where the earlier steps' commits are (brewers-and-recipes §1), and the other values (`integration`, `checkout`, `scratch`) load but change nothing.

Three follow-ups read the commits of the steps before them: check steps (#177) run the repository's checks on them, the red proof (#176) checks out the test commits before the implementation, and `openPullRequest` (#178) pushes them. They need one answer to "where is the task tree of this batch now?" that survives a kill between two steps, a retry, a rewind and a lost attempt.

## Decision

### The task tree is commits on an attempt branch
- **The task tree of a batch is the branch of its latest attempt that succeeded with a worktree**, in the order the events recorded the finishes, or the commit of its latest rewind for the batch's repository, whichever was recorded last. Before either, it is the repository's base. The fold keeps it on the batch (`Batch.taskTree`): `{ kind: 'attempt', stepId, attempt, repo }` on a `step.finished` that succeeded, `{ kind: 'rewound', shas }` on `batch.rewound`.
- **It is commits, not files.** What a brewer left uncommitted stays in its own worktree and does not reach the next step; a step that hands work on commits it (`produces: commits`). The tip is the attempt branch's tip, read when it is needed, not the worktree's `HEAD`: a brewer that switches its worktree to another branch leaves its commits out.
- **Nothing writes a succeeded attempt's branch afterwards.** A succeeded attempt's run has ended (its finish is recorded from the run's end), no later attempt checks its branch out, and the cleanup never deletes a branch of a live batch (ADR 0029). So the tip read when the next attempt starts is the tip the attempt left. This assumes a brewer reaches git only through its own worktree: one that points its `.git` file at another worktree's record could commit on that branch, as it could already move any ref of the clone. Keeping a brewer inside its worktree is the sandbox's work (file-tool rules scoped to the worktree, ADR 0049, #135), not the task tree's. A resumed session (`retryMode: resume`, #169) continues on its attempt's branch; it then decides how it amends this.

### Where a new attempt's worktree starts
- **Every attempt still gets a worktree of its own, on its own branch** (ADR 0029's layout), made with `git worktree add -b <its branch> <path> <start>`. `taskTreeStart(batch, repository)` (`src/engine/task-tree.ts`, pure) gives the start: the base (`origin/<base>`), `refs/heads/<branch of the task tree's attempt>` (built again with `attemptBranch`, as ADR 0037 does: the recorded branch is never acted on), or the rewind's commit for the repository. The manager resolves it after its fetch to a commit, which `step.started` records as `worktree.commit`.
- It throws, and the attempt fails retryably with `the attempt could not get its worktree: <reason>` (ADR 0037's path), when the task tree is an attempt of another repository than the one the batch writes in now, or a rewind that names no commit of it. Its attempts run out and the batch goes Stuck with that reason; a human rewinds or changes the repository.
- **A retry, or the attempt after a lost or abandoned one, starts where the failed one started**: the task tree did not move, since only a success moves it. The failed attempt's commits stay on its branch, and its worktree with them, until the batch ends, for a human to read; they never reach a later step. No commit is copied (no cherry-pick, no reset): a new attempt only branches from a commit that exists.
- **A skip** leaves the task tree where it is: the step after it starts from the steps before. **A loop or an `onFail` route** that goes back to an earlier step continues from the latest success, which may be a later step's: the task tree only moves forward in the event log.
- **A rewind** (ADR 0025) names the commit of each repository it resets; the next attempt starts at the commit of the batch's repository, and the steps after it continue from there.
- **A kill between two steps** cannot lose or duplicate commits. The task tree is folded from the events and its tip read from git each time an attempt starts: a driver that starts again finds the same tip. A kill between `git worktree add` and `step.started` leaves a worktree at that tip, which the next start of the same attempt reuses (ADR 0029's reuse needs the start it is given, now the tip). `test/chaos/worktrees.test.ts` checks it: every attempt starts at the tip of the attempts that succeeded before it, across kills.

### What `tree` gives, for now
- `tree: task` is the only value the engine follows. A brewer with `integration`, `checkout` or `scratch` fails the load, one line each, as ADR 0059's refusals do: `step "<id>" has the brewer "<name>", with "tree": "<value>", which the engine does not follow yet (ADR 0059)`. `integration` comes with multi-repository bottles, `checkout` (a read-only checkout) and `scratch` (a tree whose commits never count) with the engine knowing a step's tree.
- A read brewer (`access: read`) with `tree: task` gets a worktree at the task tree's tip and reads the earlier steps' commits there. It has no `git.commit`, so its branch stays at its start, and its success leaves the task tree at the same commit: the next step starts where it started. Should it commit anyway (an allow rule that reaches `git commit`), its commits count like any success's: the engine follows the branch, not the brewer's `access`, until it knows a step's tree. So a read brewer must have no allow rule that reaches `git commit`, which nothing checks yet: refusing a read step's commits (its branch tip past its `worktree.commit`) goes with the checks after an attempt that `noPush` and `scope` need (ADR 0059).

### How the steps after a brewer find the task tree
- **A check step (#177)** is an attempt like a brewer's: the driver gives it a worktree at `taskTreeStart`, and it runs the repository's checks there, never in an earlier attempt's worktree, which a check's build would change. Its success moves the task tree to its own branch, at the same commit.
- **The red proof (#176)** reads which commits each step added: an attempt's `step.started` records where it started (`worktree.commit`), and its branch's tip is where it ended, so a step's commits are `<start>..<tip of its succeeded attempt's branch>`.
- **The push (#178)** resolves the same `taskTreeStart` in the clone with `rev-parse` and pushes that commit to the bottle branch. Git never runs from inside an attempt worktree for it (ADR 0029).

### Claims, I2 and cleanup
- Attempts never share a worktree: a later attempt reads only a commit of an earlier attempt's branch, in the clone, and checks out a branch of its own. So I2 (one live lease per worktree) holds as it did, and the claims of ADR 0029 and ADR 0037 do not change: an attempt's lease claims its own folder, the batch's claim keeps every folder and branch of a live batch, a Stuck batch included, and everything of the batch goes when it ends.
- A live batch therefore keeps one worktree per attempt, as before; the earlier ones are also where `step:<id>` inputs are read (ADR 0059).

## Consequences
- A recipe of two writing steps brews through the driver: the second step's worktree has the first step's commits (`test/integration/attempt-worktrees.test.ts`, through `openDriver` and real git).
- `Batch` has a new optional field in the fold; no event changes, and nothing in the event log or its JSON Schema does either. A batch folded from earlier events gets its task tree from them.
- Brewers with `tree` other than `task` no longer load; none of the default recipes uses one.
- Each attempt's worktree is a full checkout, as before. A batch of many steps keeps them all until it ends; for a large repository the disk cost grows with the attempts, not the steps.
- `taskTreeStart` is the one place #176, #177 and #178 ask where the batch's work is.

## Alternatives considered
- **One worktree per batch, handed on from step to step.** One checkout per batch, but every hand-on must wait until the previous attempt's process is known to be gone (ADR 0029's rule for resumed sessions), which the runner cannot tell for a lost attempt on another machine; a retry would have to reset the failed attempt's changes, which ADR 0029 refuses (it may destroy work that is not the attempt's); the claims of a lease would have to follow the chain of attempts; and an earlier step's out doc, which a later step reads as `step:<id>`, would be overwritten in place.
- **Record the tip in `step.finished`.** The log would name each step's last commit, but the driver would have to run git between the run's end and the finish, and a kill there would leave a run whose end is not recorded; the branch already holds the tip, and nothing moves it afterwards.
- **The latest succeeded attempt by step order in the recipe.** Simpler to state, but wrong for loops and `onFail` routes, which go back to an earlier step whose old success would hide the later commits.
- **Copy the earlier commits onto the new attempt's branch (cherry-pick).** Every attempt would start at the base and replay the chain; a conflict would stop a step that changed nothing, and a kill part-way would leave half a chain.
