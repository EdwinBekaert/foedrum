# 0090. The push fetches the base in a git directory of its own

Date: 2026-10-20 · Status: Accepted · Amends [0071](0071-the-openpullrequest-action-two-effects-of-the-batch.md) (which base the empty check reads) and [0079](0079-the-push-scans-the-batch-s-commits-for-secrets.md) (which base the scan reads from)

## Context
The openPullRequest push ([ADR 0071](0071-the-openpullrequest-action-two-effects-of-the-batch.md)) records an empty push, and opens no pull request, when the base holds every commit of the task tree. It read the base as the clone's `origin/<base>`. That ref moves only when something fetches the clone, and the worktree manager fetches only when it adds a worktree. When main has moved on since, and holds the task tree already (its commits were merged by hand, or the plan committed what a human pushed meanwhile), the push sees commits beyond a stale base, pushes the bottle branch, and GitHub refuses the pull request ("No commits between") on every pass until the action's 2 h deadline: the batch goes Stuck on `deadline_passed` instead of the clear `no commits beyond main` reason (#202, from the review of #198). The secret scan ([ADR 0079](0079-the-push-scans-the-batch-s-commits-for-secrets.md)) reads from the same base, so it scanned commits main already had.

Two ways out: read the remote's tip with `ls-remote`, as the push's `find` already does for the bottle branch, or fetch the base. And every git call the engine makes in the clone reads the clone's configuration, which each attempt worktree shares and a brewer can write (`git config url.<x>.insteadOf`, `include.path`, `credential.helper`, `core.sshCommand`, `core.hooksPath`, #200). A new network call must not add to that.

Also in #202: `serveShell` gave a `local` repository without a clone the path `''`, so git would run in serve's working directory, the Brewery checkout. `serveSetup` refuses such a repository first, so it was unreachable, but nothing said so where git runs.

## Decision
- **The push effect fetches the base before the empty check**, under the effect's deadline, in both its `find` and its `apply`: `BranchPush.baseTip(<base>)` returns the commit the remote's base points at now, and that commit is what the empty check (`merge-base --is-ancestor`) and the secret scan's range (`<task tree> ^<base>`) read. `origin/<base>` in the clone is no longer read by the push; it stays where a batch starts (ADR 0066).
- **A fetch, not `ls-remote`.** `ls-remote` names the tip but brings no objects: a tip the clone lacks can be neither the ancestor check's commit nor the start of the scan's range, and a tip the clone lacks is exactly the case this fixes.
- **The fetch runs in a git directory of Foedrum's own, never in the clone** (`openBranchPush`, `src/workspace/branch-push-git.ts`). `<work root>/<owner>.<name>/base.git` (`baseGitDirPath`, `src/workspace/attempt-worktrees-git.ts`) is a bare repository that Foedrum makes with `git --git-dir=<it> init --bare --template=` and the clone's object format, and its fetch runs with `GIT_OBJECT_DIRECTORY` at the clone's object store (`<git-common-dir>/objects`, so the managed clone's alternates still count). The objects land in the clone, the fetched ref (`refs/heads/<base>`) stays in Foedrum's directory, and git reads that directory's configuration and hooks, never the clone's: no `url.*.insteadOf`, `include.path`, `credential.helper`, `core.sshCommand`, `remote.*` or hook a brewer wrote there takes part. Brewers do not reach that directory: it is in no worktree, so their file rules (#135) leave it out, and no worktree's git points at it.
  - **From a URL Foedrum names**: `https://github.com/<owner>/<name>.git`, the repository the pull request goes into, for `local` and `managed` repositories alike, not the clone's `origin`, whose URL is the clone's configuration.
  - **Only what the clone lacks**: the clone's `origin/<base>` is the fetch's `--negotiation-tip`, so the server sends the commits after it; without one, the fetch brings the base's whole history once.
  - **Nothing else runs**: `--no-tags --no-write-fetch-head --no-recurse-submodules --no-auto-maintenance`, with `gc.auto=0`, `maintenance.auto=false` and `core.hooksPath` at the null device for the call. A gc there would see only Foedrum's own ref and could prune the clone's objects, so none runs.
  - The base name reaches git only when it is a branch name that cannot be an option, a second refspec or a range; the fetch gets 300 s, as the push does, and the effect's deadline stops it sooner.
- **What it does not cover.** The user's own configuration (global and system) applies, as for every git Foedrum runs, so an `insteadOf` or credential helper of the user's still works. The other git calls of the push in the clone (`rev-parse`, `merge-base`, `ls-remote`, `push`) and the worktree manager's fetch still read the clone's configuration: #200 remains open for them.
- **A `local` repository without a clone throws** where its clone path is worked out (`worktreeClonePath`): `The local repository <owner/name> names no clone`. The push and the worktrees of `serveShell` both go through it, so neither runs git in the Brewery checkout.

## Consequences
- A task tree the remote's base holds is recorded as empty, and the batch goes Stuck at once with `batch <id> has no commits beyond <base> to open a pull request with`, also when the clone never fetched. A task tree that is not is scanned from the base the pull request will be compared with. `test/integration/pull-request-push.test.ts` shows it with real git, with a `url.<nowhere>.insteadOf` of the origin planted in the clone's configuration, directly and through an `include.path`, which a fetch in the clone would follow.
- Every push, and every `find` of one, fetches. On an up-to-date base that is a round trip with no objects.
- A `local` repository's push now needs read access to `https://github.com/<repo>.git` through the user's credential helper, as a `managed` one already did (ADR 0071); a user who reaches GitHub only over ssh gets it through a `url.*.insteadOf` of their own global configuration. A fetch that needs a prompt fails, and the effect is tried again each pass until the action's deadline, as a failed push is.
- The fetched objects are referenced only from Foedrum's directory, so the clone's own gc may prune them after its grace period; the next push fetches them again.
- `BranchPush` has `baseTip(base)`; its fakes in the unit and chaos tests answer it.

## Alternatives considered
- **`ls-remote` the base, then fetch only when the tip is missing.** Two network calls where one does, and the fetch is needed in the case that matters.
- **`git fetch origin <base>` in the clone.** One call, and it would update `origin/<base>` for the next batch too, but it reads the clone's configuration, where a brewer can point `origin` or an `insteadOf` anywhere and plant a credential helper (#200).
- **Check the clone's configuration first and refuse anything Foedrum did not write.** A user's own clone has settings of the user's, and a brewer of another batch can write between the check and the fetch.
- **Fetch into a private ref of the clone.** Still the clone's configuration and hooks.
- **Ask the code host whether the base contains the task tree.** GitHub's compare needs both commits on GitHub, and the task tree is not pushed yet.
