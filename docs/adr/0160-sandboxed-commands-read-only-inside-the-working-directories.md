# 0160. Sandboxed commands read only inside the working directories

Date: 2026-10-23 · Status: Accepted · Amends [0087](0087-sandboxed-commands-go-through-the-allow-rules-and-never-see-credentials.md) (what a sandboxed command can still read)

## Context
On the sandboxed level ([ADR 0010](0010-cross-platform-and-isolation-levels.md)), a command an allow rule lets run (`npm test`, which runs code a brewer can edit) reads "most of the machine". [ADR 0087](0087-sandboxed-commands-go-through-the-allow-rules-and-never-see-credentials.md) hides the logins Foedrum's own setup relies on, at their default paths, and lists what stays open (#247): the Windows user's logins on WSL2 under `/mnt/c/Users/<user>/`; a `GH_CONFIG_DIR`, `XDG_CONFIG_HOME` or `CLAUDE_CONFIG_DIR` that moves a login; and other tools' credentials (`~/.docker/config.json`, `~/.kube`, `~/.netrc`, cloud CLIs). A list of paths can't be complete. It left `permissions.blockReadsOutsideWorkingDirectories` for a decision of its own.

Claude Code's documentation, read for this ADR on 2026-10-23 ([Settings reference](https://code.claude.com/docs/en/settings-reference), `permissions.blockReadsOutsideWorkingDirectories` and "Sandboxed commands under the block"; [Sandboxing](https://code.claude.com/docs/en/sandboxing), "Filesystem isolation"; [Settings](https://code.claude.com/docs/en/settings), "Fix a broken settings file"), says:

- **What it does to sandboxed commands.** "When sandboxing is on, the block also covers sandboxed commands. Claude Code denies them read access to your home directory and to the other roots that hold user files: `/Users`, `/home`, `/root`, `/Volumes`, `/mnt`, `/media`, `/run/media`, and `/srv`."
- **What it re-opens.** "It then re-opens the working directories, worktrees Claude Code creates in the session, the session temp directory, and the parts of `~/.claude` that commands need, such as skills and plugins." In a linked git worktree, "the repository's common `.git` directory stays readable and writable to sandboxed commands". And "Claude Code re-opens your global git configuration files to sandboxed commands": `~/.gitconfig`; "The `config`, `ignore`, and `attributes` files under `$XDG_CONFIG_HOME/git`"; "Files your global git configuration names through `[include]`, `[includeIf]`, `core.excludesFile`, or `core.attributesFile`", except where "a file lies where a sandboxed command can write". "`~/.git-credentials` and `$XDG_CONFIG_HOME/git/credentials` stay blocked." "A `denyRead` entry that covers a file always takes precedence over this re-open."
- **Where it does not reach sandboxed commands.** "In these cases the block doesn't reach sandboxed commands, while Claude's file tools keep enforcing it": filesystem isolation off through `sandbox.filesystem.disabled`; `allowManagedReadPathsOnly` set; "The path of the directory you started Claude Code in contains a glob character such as `*`, `?`, or `[`".
- **What it does to the file tools.** "Claude Code denies `Read`, `Grep`, `Glob`, and `LSP` calls on those paths" "in every permission mode, including `bypassPermissions`". And "A Bash command the shell parser can't trace, such as one that changes directory more than once or runs a subshell, prompts you even in auto mode and `bypassPermissions` mode. [...] This prompt doesn't apply when the command runs in the sandbox and the sandbox enforces the block."
- **Its scope and version.** "A `true` in any file applies"; "Requires Claude Code v2.1.257 or later."
- **An entry a version does not accept.** A value the schema rejects makes Claude Code skip the file ("Settings Error"); "only individual entries fail, such as a malformed permission rule or an unknown hook event name. Claude Code skips those values and keeps the rest of the file in effect" ("Settings Warning"). The docs do not say which of the two a version before 2.1.257 makes of this key. [ADR 0151](0151-brewers-write-no-attribution.md)'s case was a known key with a value an older version rejects (`attribution: false`), which the reference says skips the whole file; the reference says nothing like it for this key.

Measured on 2026-10-23 with `claude -p` (Claude Code 2.1.301, native Windows, so no sandbox), the fake Messages API of [ADR 0057](0057-real-claude-tests-are-opt-in-and-claude-proofs-leave-the-suite.md) making the model call `Read`, `--setting-sources ""` and only a `--settings` file, from a scratch working directory with a file next to it:

| Settings | Mode | Read of | Result |
|---|---|---|---|
| `allow: [], deny: []` (control) | `bypassPermissions` | the file outside | its content |
| the same with the block | `bypassPermissions` | the file outside | refused: "… is outside …; the permissions.bl[ockReadsOutsideWorkingDirectories] …" |
| the same with the block | `bypassPermissions` | a file inside | its content |
| `deny: ["Read"]` with an unknown `permissions.notARealKey247: true` | `bypassPermissions` | a file inside | "No such tool available: Read": the deny rule next to the unknown key held |
| `allow: ["Read(./**)"]` with the block, as a brewer's | `dontAsk` | the file outside | refused, by the block |

So 2.1.301 reads the key from a `--settings` file, refuses a file-tool read outside the working directory with it and not without it, and keeps the rest of a file whose `permissions` hold a key it does not know. What the block does to sandboxed commands needs macOS, Linux or WSL2 and is the docs', not a run's, like the rest of ADR 0087's sandbox block.

## Decision

### The block on the sandboxed level
- **`attemptSettings` writes `"permissions": { …, "blockReadsOutsideWorkingDirectories": true }` whenever it writes the sandbox block** (`src/brewers/attempt-settings.ts`), and the schema (`AttemptSettings`, `src/schemas/attempt-settings.ts`) refuses a sandbox block without it, as it refuses one without `autoAllowBashIfSandboxed: false`.
- This replaces a longer list as the answer to "what else can an allowed command read": every path under the user roots that is not re-opened is denied, whatever tool keeps a credential there. It closes ADR 0087's three gaps where they lie under those roots: the Windows user's home on WSL2 under `/mnt` (no entry needs the Windows user's name), a config directory moved elsewhere under the home, and other tools' credentials (`~/.docker`, `~/.kube`, `~/.netrc`, `~/.config/gcloud`, …).
- **Not on the permissions-only level.** There the file tools' rules are already scoped to the worktree ([ADR 0093](0093-brewers-file-tool-rules-are-read-and-edit-rules-scoped-to-the-worktree.md)), and the control run shows the block adds nothing to them under `dontAsk`; but a shell command the parser can't trace would prompt, and under `dontAsk` be denied, which would change what a brewer's allowed commands may do without closing anything. The block's command part needs the sandbox to enforce it.
- **ADR 0087's credentials stay**, as the second line for what the block re-opens or does not reach: `credentials.files` is "the same restriction that `filesystem.denyRead` applies", which takes precedence over the re-open, so `~/.claude/.credentials.json` stays hidden inside the re-opened parts of `~/.claude`, and the variables are not files at all. Recorded here, as CLAUDE.md asks of a second layer: it catches a login in a re-opened path, a login outside the user roots that a variable names (below), and the cases the docs list where the block does not reach sandboxed commands.

### The variables that move a login
- `serveSetup` reads `GH_CONFIG_DIR`, `XDG_CONFIG_HOME` and `CLAUDE_CONFIG_DIR` from its own environment (`configDirsOf`), and the attempt plans and `foedrum resume` pass them to `attemptSettings`, which adds a `deny` entry for each login they move: `$GH_CONFIG_DIR`; `$XDG_CONFIG_HOME/gh` (where gh looks when `GH_CONFIG_DIR` is unset, [gh environment](https://cli.github.com/manual/gh_help_environment)) and `$XDG_CONFIG_HOME/git/credentials`; `$CLAUDE_CONFIG_DIR/.credentials.json` ("If you've set the `CLAUDE_CONFIG_DIR` environment variable, Claude Code keeps the `.credentials.json` file under that directory instead", [Authentication](https://code.claude.com/docs/en/authentication), "Credential management").
- Resolved when the settings are written, from the driver's environment: that is where gh, git and Claude Code wrote the logins. A brewer's own `env` cannot move a login that already exists.
- Only an absolute value counts. An empty one is unset, as gh reads it, and a relative one resolves against whichever process reads it, so it names no one place. The paths are POSIX (`path.posix`): the sandboxed level never runs on native Windows.
- Under the user roots these entries repeat the block; they matter where the block does not reach, or where a variable points outside those roots (`/opt`, `/data`, …).
- The Anthropic profiles directory (`~/.config/anthropic`) does not follow `XDG_CONFIG_HOME` in the docs, so no entry is derived from it.

### What stays open
- **Outside the user roots.** A credential in `/etc`, `/opt`, `/var` or another root the docs do not list stays readable, unless a variable above names it.
- **Re-opened files that hold a secret.** `~/.gitconfig`, the files under `$XDG_CONFIG_HOME/git` and the files they include are readable to sandboxed commands; a token kept there (an `http.extraHeader`, a URL with a token in `url.<base>.insteadOf`) is too. The docs' answer is a `denyRead` entry for that file, which would also take git's identity and settings from every brewer's commit; Foedrum does not know which file a machine keeps a token in. A Brewery whose global git configuration holds a token must not run untrusted repositories on this level. The brewer's git asks no credential helper ([ADR 0109](0109-a-brewer-s-git-holds-no-push-credential.md)), so a helper's stored login is not reached through git.
- **The cases the docs list.** Foedrum never writes `sandbox.filesystem.disabled` or `allowManagedReadPathsOnly`, and `--setting-sources ""` loads no other file but managed settings (ADR 0046), which Foedrum does not get around. A work root whose path holds `*`, `?` or `[` turns the block off for sandboxed commands while the file tools keep it; ADR 0087's credentials still apply there.
- **The OS keyring** and **the network** are as ADR 0087 says.
- **Before Claude Code 2.1.257.** The docs do not say whether an older version skips the key or the whole file; 2.1.301 keeps a file with a `permissions` key it does not know (above). The sandboxed level has not run yet (ADR 0087, "Unverified against `claude`"); its first run checks the version it needs.

### Tests
Unit only: `test/unit/attempt-settings.test.ts` (the block with a sandbox and not without, the entries each variable adds, once each, nothing for an empty or relative value, and the schema refusing a sandbox block without the block or with it `false`), `test/unit/serve-config.test.ts`, `test/unit/attempt-plan.test.ts`, `test/unit/attempt-plans.test.ts` and `test/unit/resume.test.ts` (the variables reach the settings), `test/unit/doctor.test.ts` (doctor's advice). The control run above is a proof of `claude`, not a test in the suite (ADR 0057).

## Consequences
- On the sandboxed level, an allowed command reads the worktree, the clone's common `.git`, git's global configuration, the parts of `~/.claude` Claude Code re-opens and the system outside the user roots, and nothing else of the user's files.
- `foedrum doctor` says the sandbox hides the home folder and the other user folders, and on WSL2 that they include the Windows user's logins under `/mnt`; its line that the sandbox left them readable (ADR 0087, review of #250) is gone.
- **A toolchain installed under the home is unreadable to sandboxed commands**: node from nvm (`~/.nvm`), Volta, asdf or fnm, tools in `~/.local/bin`, a user-level npm cache. An `npm test` that needs one fails on this level; one installed under `/usr`, `/opt` or Homebrew's prefix does not. The docs give no setting for a brewer to re-open one, and Foedrum writes no `allowRead`. A Brewery on this level installs its toolchain outside the home until #427 decides how to re-open one.
- A worktree under `/mnt` on WSL2 stays readable as the working directory; the rest of `/mnt` does not.
- The settings file of every sandboxed attempt grows by one key, and by up to four paths when the variables are set.

## Alternatives considered
- **A longer list of paths** (ADR 0087's approach): every tool added by hand, the Windows user's name needed on WSL2, and still incomplete. The block covers what the list misses; the list stays only as the second line above.
- **`sandbox.filesystem.denyRead: ["~/"]` with `allowRead: ["."]`** (the docs' own example): covers only the home, not `/mnt` or the other user roots, and re-opens neither git's configuration nor what Claude Code needs of `~/.claude`. The docs point to the block instead: "To deny sandboxed commands read access to home directories and mounted volumes while keeping the working directories readable, set `permissions.blockReadsOutsideWorkingDirectories` instead of writing path rules."
- **The block on every level:** see "Not on the permissions-only level".
- **Deny the re-opened git configuration too:** a brewer's commits would lose the machine's git identity and settings, and a Brewery would have to set them per clone; the cost lands on every Brewery for a token few keep there.
- **Entries for the Windows home on WSL2** (`/mnt/c/Users/<user>/…`): the block denies `/mnt` without the user's name, which the attempt settings do not know.
