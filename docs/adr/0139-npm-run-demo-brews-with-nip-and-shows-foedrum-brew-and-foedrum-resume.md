# 0139. `npm run demo` brews with Nip and shows `foedrum brew` and `foedrum resume`

Date: 2026-10-22 · Status: Accepted · Amends [0097](0097-npm-run-demo-is-a-script-on-serve-s-seams-with-the-tests-fakes.md) (what the demo imports from `test/helpers/`, its Brewery and brewer, its lives, its walkthrough and its integration test)

## Context
[ADR 0097](0097-npm-run-demo-is-a-script-on-serve-s-seams-with-the-tests-fakes.md) built `npm run demo` on a one-brewer `stout` recipe with `testFirst: false` and a scripted brewer that commits a fixed file. M1's "See it" (`docs/milestones/m1.md`) points at the demo, and since it was built M1 gained what a user should see there: Nip from `defaults/` (Gauger, red proof, Cellarman, checks), the attempt a route schedules getting what sent it back ([ADR 0128](0128-an-attempt-a-route-schedules-gets-what-sent-it-back.md)), `foedrum brew` ([ADR 0123](0123-foedrum-brew-drives-one-batch-under-an-owner-of-its-own.md)) and `foedrum resume` ([ADR 0126](0126-foedrum-resume-opens-a-finished-attempt-s-session-in-its-worktree.md)). #180 built the Nip fixture (`test/helpers/nip-fixture.ts`, [ADR 0121](0121-the-m1-end-to-end-test-runs-nip-through-serve-with-real-git-and-checks-and-faked-github-and-brewers.md)) for the M1 end-to-end test: a tiny target repository with a `node --test` test, a Brewery with no recipe of its own, the order, and the scripted Gauger and Cellarman. #366 asks the demo to brew with it.

Three things needed deciding: where the kill goes now that a run has seven attempts, how `foedrum brew` and `foedrum resume` run in a demo that starts no gh and no `claude`, and what becomes of the `stout` recipe.

## Decision
- **The demo brews with Nip through the Nip fixture,** not a brewer of its own: the Brewery's files are `nipBreweryFiles`, the target repository is `NIP_TARGET_FILES`, the order is `NIP_ORDER`, and `scripts/demo/brewer.ts` puts `scriptedNip` in serve's runner seam with the demo's git configuration. The `stout` recipe and the fixed-file brewer go. This widens ADR 0097's list of what the demo imports from `test/helpers/`: besides `fakeGitHubApi` and `ghOver` for the code host, it imports the Nip fixture, `scriptedNip` for the brewer seam in place of `fakeBrewerRunner` and `behave`, and the fixture's data that goes with it (`NIP_TARGET_FILES`, `nipBreweryFiles`, `NIP_ORDER`). That data is no seam's other side, but it is what `scriptedNip`'s script brews, so the demo and the E2E test run the same order against the same repository.
- **The kill comes after the Gauger's first commit.** The restart loses `gauge #1` and brews `gauge #2`; the red proof, the Cellarman's first fix, the failed `green`, the Cellarman's second attempt and the pull request follow in the second life. A kill later in the run would lose an attempt a route scheduled, whose retry gets no route input (ADR 0128), and the demo would no longer show it.
- **The fixture plays each step's script in the order its runner starts that step's attempts**, not by attempt number: `gauge #2`, the first Gauger attempt the second life starts, plays the Gauger's one entry. For the E2E test, in one process, the order is the attempt number, as before.
- **The Cellar shows what the Cellarman's second attempt was told**: the route input's source and the failed test's own TAP line, read from the attempt's prompt (`routeLines`), once the attempt has brewed.
- **`foedrum brew` runs in a third process,** `scripts/demo/cellar.ts <scratch> brew`, on the same machine and seams as the Cellar's lives, with `runBrew` (`src/cli/brew.ts`) in place of `runServe`. Its order is a second issue, `#2`, the same order filed without a label so the Cellar's intake leaves it; once the Cellar has stopped, the demo labels it `recipe:nip` through the code host, whose journal keeps it, and runs `foedrum brew 2 --as ann`. It orders the issue, routes it by its label, and drives that one batch to its pull request. `brewFromCheckout` is not used: it gathers doctor's facts, which would start the machine's gh and `claude`.
- **`foedrum resume` is printed, never opened.** The demo runs the CLI's own `foedrum resume 1-1 implement#2` (`cliFromCheckout`) with `CLAUDE_CODE_CHILD_SESSION=1` for that call, so resume takes the branch ADR 0126 gives a Claude Code session: it finds the Cellarman's attempt and its session id in the store and prints the line to run in a terminal, without looking for the transcript, reading doctor's facts or starting `claude`.
- **The walkthrough has ten steps:** the diagnosis; the order; `foedrum status` as the batch moves, up to the kill; the kill and the restart; the red proof and the failed check; the pull request and the status comment; on tap; `foedrum brew 2 --as ann`; `foedrum resume 1-1 implement#2`; and `foedrum replay 1-1`.
- **A good run** has both batches on tap, two pull requests on the code host and one status comment on each order (`problemsOf`). The integration test (`test/integration/demo.test.ts`) checks the headings in order, the lost Gauger attempt said once, the route input's lines, `foedrum brew`'s order, route and on-tap lines, `foedrum resume`'s line, every step outcome of batch 1-1 in the store, batch 2-1 on tap, and the Cellarman's second fix at the tip of the bottle branch. `test/integration/brew.test.ts`, which brewed the demo's `stout` Brewery, brews the Nip fixture's. Both tests run `foedrum brew` through Nip, and both are kept: `brew.test.ts` is brew's own test, `runBrew` in the test's process, and checks its bottle branch, its pull request's head and base and the commit pushed to the remote; `demo.test.ts` checks that the demo program starts brew in a process of its own after the Cellar and shows its lines, and does not check the branch or the push.

## Consequences
- The demo shows M1 as it is: a test-first recipe from `defaults/`, a red proof, a failed check sent back with its reading, a crash, `foedrum brew` and `foedrum resume`.
- It takes longer: two Nip runs of seven attempts each, about 2 minutes on a Windows laptop under other sessions' load, against ADR 0097's 25 s. Each attempt makes a worktree and fetches, and a check runs the target's tests. The integration test's hang guard and each life's deadline grow with it.
- `foedrum brew`'s integration test now runs Nip's seven attempts too, and takes longer.
- Batch 2-1 brews the same change as batch 1-1 and opens a second pull request with it: the fixture has one order's script, and #180's fixture is reused, not copied.

## Alternatives considered
- **Keep `stout` and add Nip beside it.** Two recipes and two brewers to keep in step with the engine, and the demo would show a one-step recipe that no default uses.
- **Brew the second order with a lighter recipe.** It needs a recipe and a brewer of the demo's own, the second fixture #366 rules out.
- **Restart with `foedrum brew` instead of the Cellar.** The killed Cellar's lease of the batch lives for one lease, 5 minutes, and `brew` refuses a batch another owner holds (ADR 0123); `--as cellar` is refused too.
- **Run `foedrum brew` through `brewFromCheckout`.** It reads doctor's facts, which start the machine's gh and `claude`; the demo starts neither.
- **Open `claude` for `foedrum resume`.** The demo starts no `claude` and must run without a terminal; the printed line is what a Claude Code session, and the plugin, show.
