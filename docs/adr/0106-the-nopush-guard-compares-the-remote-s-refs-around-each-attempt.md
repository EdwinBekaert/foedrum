# 0106. The noPush guard compares the remote's refs around each attempt

Date: 2026-10-21 · Status: Accepted · Amends [0042](0042-the-claude-command-line-and-stream-contract.md) (what `noPush` compares, and how it ends the attempt), [0059](0059-attempt-plans-from-the-brewer-of-the-step.md) (`noPush` loads) and [0062](0062-brewers-never-allow-git-with-no-fixed-subcommand.md) (the check of the remote it waited for) · Amended by [0109](0109-a-brewer-s-git-holds-no-push-credential.md) (a brewer's git holds no push credential)

## Context
Pushing is always the engine's job (brewers-and-recipes §1). [ADR 0062](0062-brewers-never-allow-git-with-no-fixed-subcommand.md) closed git's own spellings of a push at the allowlist, and showed what the allowlist cannot close: any allowed command that runs a command of its own line or file reaches a push (`npm exec`, `node -e`, `git rebase -x`, a script behind `npm test` that a writing brewer edits, a hook `git commit` runs). And a brewer's environment keeps `HOME`, `USERPROFILE` and `APPDATA`, through which git finds the user's credential helper (#173's comment), so such a push carries the user's own login. So the `noPush` guard stayed refused ([ADR 0059](0059-attempt-plans-from-the-brewer-of-the-step.md)) until the engine checks the remote itself, which holds for every spelling (#173).

The remote also moves for reasons that are not the brewer's while an attempt runs: the engine pushes another batch's bottle branch ([ADR 0071](0071-the-openpullrequest-action-two-effects-of-the-batch.md)), creates or deletes a claim ref ([ADR 0043](0043-target-repository-issues-as-a-work-queue-claimed-by-a-ref.md)) and, when the Brewery is also a target repository, pushes the state branch after events ([ADR 0024](0024-state-branch-layout-outbox-and-divergence.md)); GitHub moves `refs/pull/*` whenever a pull request or its base changes; and people and bots push.

## Decision
- **What it compares.** `guardPushes` (`src/checks/push-guard.ts`) wraps the brewer runner, outside `guardTests`. For an attempt whose brewer names `noPush`, it lists every ref of the attempt's repository (`ls-remote --refs`) before the brewer starts and again after the attempt ended, whatever its ending (also when its runner rejected: a changed ref then makes the divergence, and otherwise the runner's error goes on), and compares the two by name (`changedRefs`, `src/checks/no-push.ts`, pure): a ref that moved, was created or was deleted, among `refs/heads/*`, `refs/tags/*` and every other ref anyone can push, counts.
- **What it leaves out.**
  - `refs/pull/*` and a merge queue's `refs/heads/gh-readonly-queue/*`, which GitHub writes and refuses a push to.
  - **The engine's own writes, from a journal** (`remoteWrites`, `src/checks/remote-writes.ts`). Each writer of the engine notes the ref it writes, by repository, for as long as the write runs: the openPullRequest push (`notedPush`, the branch it pushes) and the claim's create and delete (`notedClaims`, `refs/foedrum/claims/issues/<n>`). The guard opens a window on the repository before its first read and closes it after its second; a ref the engine was writing at any time the window was open, also by a write begun before it, is left out. The journal holds only the writes under way and the open windows, so it does not grow. It lives in the `foedrum serve` process, the only one that runs a driver with effects (one per Brewery, ADR 0037). It is no engine state in the sense of the rule that state changes only by appending events: it remembers nothing past the calls under way, a restart loses nothing a later attempt needs, and what it decides is recorded as the attempt's ending, an event.
  - **The state branch** (`refs/heads/foedrum/state`, `STATE_BRANCH`) of the Brewery's own repository, by name: it is pushed after events, from the Brewery checkout, and its own push already refuses a move the engine did not make and stops the engine (`StateBranchStopError`, ADR 0024), so a brewer's push there is caught where it matters.
  Nothing else is left out. A ref moved by a person, a bot, another Brewery's push or claim, or GitHub's deletion of a merged pull request's head branch looks like a brewer's push, because it can be one: the brewer pushes with the same login.
- **The ending.** A changed ref blocks the attempt on a **divergence**: `the guard noPush: the remote of <repo> changed during the attempt: <ref> moved from <commit> to <commit>` (or `was created at <commit>`, `was deleted at <commit>`), then `(and <n> more)`. A divergence always makes the batch Stuck (`decide`), while a failure, even one not retried, follows its step's `onFail` route and could send the batch back to an earlier step instead of to a human. The ref name is cut at 200 characters, since whoever pushed chose it. The human reads the remote, undoes a push that was the brewer's, and goes on with `foedrum retry` or `skip`; a move that was theirs needs only the retry.
- **A remote it cannot read never passes.** A read that fails, times out or prints anything but `<sha>\t<ref>` lines (a ref listed twice included) blocks the attempt on its **environment**: `the guard noPush cannot read the refs of the remote of <repo> before the attempt: <why>` (or `after`). Before, the brewer never starts. Every read has deadlines: `withOwnGitDir`'s `rev-parse` and `init` git's default 60 s each, and the `ls-remote` 60 s, with 64 MiB of output (a repository with many pull requests lists many refs).
- **Read outside the clone's configuration.** `listRemoteRefs` (`src/workspace/branch-push-git.ts`) runs `ls-remote --refs <url>` in a git directory of its own, by the URL Foedrum names, as the push and its lookup do ([ADR 0096](0096-the-engine-s-git-reaches-the-remote-outside-the-clone-s-configuration.md)): no `url.*.insteadOf`, credential helper or ssh command a brewer planted in the clone takes part, so the clone's configuration cannot point the reads at a remote that never changes. The user's global and system configuration still apply, as for all git Foedrum runs (What it does not see, below). `ServeShell.refs` gives it per repository.
- **Stops and progress.** While it reads, the guard reports the attempt's progress, so its lease holds. A stop before the brewer started aborts the read and ends the attempt `cancelled`, with nothing started. A stop while the brewer runs stops it as before, and the read after still runs, on its own deadline, so a push made before the stop is still found. A stop of `foedrum serve` itself (Ctrl+C) aborts every read of the guard, so no `ls-remote` outlives it; the driver does not record those endings (ADR 0063).
- **It loads.** `noPush` joins `ENFORCED_GUARDS` (`src/engine/recipe-files.ts`), and ADR 0059's refusal of it goes.
- **Not here.** Making git ignore the user's credentials in a brewer's environment, which #173's comment asked to decide, is #299: it narrows what a push can reach, while this check finds one whatever reached it. (Since [0109](0109-a-brewer-s-git-holds-no-push-credential.md), a brewer's git asks none of the user's credential helpers or askpass programs and refuses ssh.)

## Consequences
- A brewer that names `noPush` loads, and an attempt whose brewer moved, created or deleted a ref of its repository's remote leaves the batch Stuck with the ref and both commits, whichever command pushed, within what it sees (below) (`test/unit/push-guard.test.ts`, `test/unit/serve-no-push.test.ts`, a file of its own so `serve.test.ts` stays within the per-file CPU budget).
- A guarded attempt costs two `ls-remote` calls, each with its git directory's `init`, and starts after the first: a round trip more before the brewer.
- **False alarms in a busy repository.** A push by anyone else during the attempt (a merge into main, a bot's branch, another Brewery's claim) makes the batch Stuck too, until a human retries it. A Brewery whose repositories move often under its attempts sees this; telling those moves apart, by who pushed or by the commits a move brings, needs what the remote cannot say, since a brewer pushes with the user's own login. Brewers that do not name `noPush` are not affected.
- **What it does not see.** A push undone before the attempt ended (a ref moved and moved back) leaves the refs as they were. A push to another repository the user can write to is not this repository's remote. A push from a process the brewer detached from its tree (`setsid`, a scheduled task) after the read after the attempt is not compared; the OS sandbox (#190) closes that. And the reads, like every git Foedrum runs, apply the user's global and system git configuration (ADR 0090, ADR 0096): a brewer that can run a command can write `~/.gitconfig`, and with a `url.*.insteadOf` there point the read after at a copy of the remote that never moved. A brewer's reach into the user's home is #135, and git ignoring the user's configuration and credentials in its environment is #299 (since [0109](0109-a-brewer-s-git-holds-no-push-credential.md) it asks none of the credentials; the rest of the user's configuration still applies); until then the guard catches a push that does not also hide itself, which is what a brewer misled into a push, or a script it runs, does. A brewer that writes a ref inside the window in which the engine writes the same ref passes. The engine's pushes are never by force, so a bottle branch the brewer made first refuses the engine's push unless the brewer's commit is one the engine's holds, and the push effect then fails.
- `ServeShell` has `refs`; the test shells answer it.

## Alternatives considered
- **Tell the engine's moves apart by the ledger** (`effect.applied` of the push, with its branch and commit). The ledger records a push after it happened, so an attempt ending in between would see an unknown move, and the claim's create has no ledger entry (ADR 0043).
- **Leave out Foedrum's namespaces by name** (`refs/heads/foedrum/**`, `refs/foedrum/**`). Simpler, and quiet for other Breweries, but a brewer's push to a branch there runs the repository's `push` workflows with its secrets as any branch does, and the bottle branch is what the pull request is made from.
- **Compare only the branch the batch will push** (brewers-and-recipes §1's "the branch moved on the remote"). It misses a push to main, a tag or a new branch, which is where a push does harm.
- **Fail the attempt, not retried.** It still takes the step's `onFail` route.
- **Read the remote only after the attempt and compare with the clone's `refs/remotes/origin/*`.** The clone's tracking refs lag the remote and are the clone's, which a brewer can write.
- **Let a remote that cannot be read pass with a warning.** A brewer that can make the read fail (a planted proxy in the user's global configuration, a network it saturates) would pass every push.
