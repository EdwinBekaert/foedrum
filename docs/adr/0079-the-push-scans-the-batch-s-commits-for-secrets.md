# 0079. The push scans the batch's commits for secrets

Date: 2026-10-20 · Status: Accepted · Amends [0071](0071-the-openpullrequest-action-two-effects-of-the-batch.md) (what the push does before it pushes) and [0084](0084-a-batch-s-commits-end-in-a-pull-request-or-on-a-kept-branch.md) (a refused push leaves its branch unpushed)

## Context
The openPullRequest action ([ADR 0071](0071-the-openpullrequest-action-two-effects-of-the-batch.md)) pushes a batch's task tree, every commit its brewers made, to the target repository. A brewer reads untrusted text. On native Windows, or wherever its file rules are not yet scoped to its worktree (#135), nothing stops it reading a file outside the worktree and committing what it read: `git commit -F ~/.aws/credentials`, a file it writes, or a script an allowed command runs (`npm test`). Rules cannot close that ([ADR 0062](0062-brewers-never-allow-git-with-no-fixed-subcommand.md)). The push is the last point before anything leaves the machine (#209).

Every attempt worktree shares the clone's git directory: its config, its `info/` files, its refs and its object store (#200). A brewer can write there, and so change what a plain `git log --patch` in the clone shows without changing what the push sends: a replace ref or a graft can skip a commit, a shallow file can end history at the tip, a textconv or a diff driver can show a file as nothing. Check output already goes through the same patterns before it reaches the event log ([ADR 0069](0069-check-steps-run-the-repositorys-commands-in-an-attempt-of-their-own.md)).

## Decision
- **Before the push effect pushes, it scans every commit from the base to the task tree's commit**, in the clone, never in a worktree (`BranchPush.secretScan`, `src/workspace/branch-push-git.ts`). It reads each commit's message, its headers, and the lines it adds to each file, with each file's path, through `findSecrets` (`src/formats/secrets.ts`); the pure core is `src/formats/commit-scan.ts`. Removed lines are not read: the base has them. A merge is read against its first parent. A task tree with nothing beyond the base is not scanned: nothing is pushed.
- **The headers are read as stored** (`git log --format=raw`, review of #237): the `author` and `committer` (name, email and date), and every other header but the tree and the parents, which are hashes the push needs, under the place `header <name>`. The headers end where git ends them, at an empty line; a line that is only a carriage return is still a header. So each way a brewer's `git commit` can put text in the pushed object is read:
  - the message: `-m`, `-F`, `-t`/`--template`, `-c`/`-C`, `--fixup`, `--squash`, `--trailer`, `-s`/`--signoff`, `--cleanup` (`message`);
  - the people: `--author`, `--reset-author`, `--date`, the `GIT_AUTHOR_*`/`GIT_COMMITTER_*` variables and the `user.*` settings (`author`, `committer`);
  - a signature: `-S`/`--gpg-sign`, whose text comes from `gpg.program`, a setting of the clone a brewer can write (`header gpgsig`). A signature's armour is base64 by nature, so in `gpgsig` and `gpgsig-sha256` the long-base64 pattern is not applied; every other pattern is;
  - an encoding: `i18n.commitEncoding`, a setting too (`header encoding`);
  - a merged signed tag, if a brewer merges one (`header mergetag`), read with every pattern;
  - the files: `-a`, `-i`/`-o`, pathspecs, `--amend`, `--allow-empty` change only the tree, which the added lines cover.
  The other flags (`--no-verify`, `--dry-run`, `-q`, `-v`, `-u`, `--status`, `--no-post-rewrite`) put nothing in the object. Notes are not pushed, and dates are stored as numbers, which git checks.
- **Git reads the objects as they were committed.** Each scan call runs with `GIT_NO_REPLACE_OBJECTS=1`, `GIT_GRAFT_FILE` and `GIT_SHALLOW_FILE` pointed at the null device, `GIT_NO_LAZY_FETCH=1` and `protocol.allow=never` for the call, so a partial clone never asks the remote for an object it lacks, which would send a hexadecimal word out before the refusal (the setting stops every transport on any git version; a missing object then makes git fail, and the effect is tried again), `core.attributesFile` at the null device, `log.showRoot=true` and the graft hint off for the call, and the flags `--no-ext-diff --no-textconv --no-color --no-renames --no-relative --no-notes --no-show-signature --ignore-submodules=none --submodule=short --src-prefix=a/ --dst-prefix=b/ --diff-merges=first-parent --unified=0 --inter-hunk-context=0`, with `--encoding=UTF-8` for the messages and `--no-decorate --no-mailmap --no-color --no-abbrev-commit --encoding=none` for the headers, so neither `color.ui`, `log.abbrevCommit` nor `i18n.logOutputEncoding` changes how they print. When the headers read shows other commits than the messages read, the scan refuses (`headers git did not show as stored`), so a setting nobody thought of turns the header read off loudly, never silently. What is left of the clone's attributes (`info/attributes`, the checkout's `.gitattributes`, `core.bigFileThreshold`) can only make git show a file as binary, which the scan refuses, so it can stop a push but not hide a line. The core counts each hunk's old and new lines apart from its header, so context lines (which `diff.interHunkContext` would put into a hunk) never make it read a header as part of a hunk, or an added line as a header. An integration test plants each of a replace ref, a graft, a shallow file, a textconv and `diff.interHunkContext`, and the scan still finds the commit.
- **What it relies on.** The clone's object store and its refs are what the brewers committed: the base is the clone's `origin/<base>`, the same ref the task tree started at (ADR 0066), and a brewer that moves that ref, or rewrites objects in the shared store, is #200's to close, as for the push itself. A secret is found only when it looks like one: the scan is the patterns of `findSecrets`, so an encoded or split secret passes, as it passes the check output's filter. The scan catches a brewer that commits what it read, not a brewer set on leaking.
- **A 40-character hexadecimal word is a key unless the clone has it as a commit**, asked once per scan with `git cat-file --batch-check`, so a pinned action or a reverted commit does not stop the push. A package lock's integrity hashes (`sha512-…` in `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock` or `pnpm-lock.yaml`) are not read: they look random and are public. In any other file the prefix is read with the rest, since it could disguise a key.
- **Binary files and large diffs fail closed.** A binary file that any commit adds or changes stops the push, whatever its size: the patterns read text, and a binary file can hold anything. One a commit only deletes does not, as removed lines do not: git's `deleted file mode` header says so, never the path. More than 4 MiB of messages, or of changes, stops it too: the runner's output limit (ADR 0035) kills git there, and the scan does not read further.
- **A finding fails the action for good.** The push effect records a push result with `refused`, at most 50 findings, each a commit, a place (the file's path as git shows it, `message`, `author`, `committer`, `header <name>` (or `a header` when the name is no plain word), `a file whose path looks like a secret` when the path itself matches, or, for more than 4 MiB, `the commits from <base>` on the task tree's commit) and a kind (`GitHub token`, `binary file`, …), and pushes nothing. The action's attempt is then blocked on its environment, so the batch goes Stuck, and its summary names the first three findings and counts the rest: `the push of batch 12-1 stopped before anything left the machine: its commits hold what looks like a secret, or what the scan cannot read (ADR 0079): commit <sha>, notes/aws.txt: AWS access key id; and 2 more`. No event, and so neither the state branch nor the status comment ([ADR 0072](0072-the-status-comment-edits-as-revisions-in-the-ledger.md)), holds the matched text or `findSecrets`' excerpt of it.
- **A refused push leaves its branch unpushed** for the cleanup ([ADR 0084](0084-a-batch-s-commits-end-in-a-pull-request-or-on-a-kept-branch.md)): when the batch is cancelled, its task tree's branch is kept, so a human can take the commits, fix them and push them.

## Consequences
- A credential a brewer commits stays on the machine, in the clone, and the batch waits on a human, who sees which commit and file to look at.
- The ledger keeps the refusal for the batch's life. A rewind after it does not scan again: the batch is cancelled, and the human pushes the fixed commits or orders it again.
- A batch that adds an image, or a file the clone's attributes call binary, goes Stuck. So does a commit whose message or added lines happen to look like a key (a long random test fixture). Both are rare for a brewer's commits, and fail closed.
- In a shallow user clone, the scan walks the real history, which ends at the shallow boundary: it works while the base is at or after that boundary, and when the walk needs a commit past it, git fails, and the effect fails and is tried again each pass, as a failed push is. The managed clone is a partial clone, never a shallow one.
- A signed commit pushes as before: its signature is read, but its armour is not taken for a key. A merged signed tag's armour is, so merging one stops the push; that fails closed, and a brewer's commits merge no signed tags.
- A submodule bump stops the push: the gitlink's commit is not in the clone, so its 40-character hash reads as a key. That fails closed, since a gitlink can carry any 40 hexadecimal characters.
- Paths go into the summary as git shows them; the status comment shows a blocked summary as plain text, escaping Markdown and mentions (ADR 0072).
- Each push costs three `git log` calls in the clone, and a `cat-file` call when a hexadecimal word turns up.

## Alternatives considered
- **Scan in the attempt worktree, or at each step's end:** the worktree is what the brewer controls, and a later step can add a commit the earlier scan never saw; the push is the one point every commit passes.
- **Scan only the diff from the base to the tip:** a commit that adds a secret and a later one that removes it leave a clean diff, and the push still sends both.
- **Read binary files as text (`--text`):** a compressed or encoded secret still passes, and the scan would seem to cover what it cannot.
- **Neutralise every attribute (an empty `attr.tree`):** `info/attributes` is still read, and attributes can only make the scan refuse more, never hide a line, once textconv and external diffs are off.
- **Walk the raw commit objects with `cat-file --batch` instead of trusting git's walk:** exact against grafts and shallow files too, but more code than the three environment variables, which an integration test holds to the same result.
