# 0137. The push, its lookup and the worktree fetch run in the clone again

Date: 2026-10-22 · Status: Accepted · Amends [0096](0096-the-engine-s-git-reaches-the-remote-outside-the-clone-s-configuration.md) (the push, its `ls-remote`, the worktree manager's fetch and the transport part of `IN_CLONE` go back to the clone; the base fetch's git directory and its partial-clone fetch stay), [0012](0012-worktrees-from-local-clones.md) (a `local` repository's worktree fetch reaches its clone's `origin` again), [0029](0029-attempt-worktrees-layout-claims-and-repair.md) (the worktree fetch runs in the clone, with `--prune`, no auto maintenance and no submodules), [0071](0071-the-openpullrequest-action-two-effects-of-the-batch.md) (the push and its lookup run in the clone by its remote, the push with no tags or submodules) and [0130](0130-the-cleanup-removes-the-git-directories-of-its-own-a-stopped-call-left.md) (which calls leave the directories it removes)

## Context
[ADR 0096](0096-the-engine-s-git-reaches-the-remote-outside-the-clone-s-configuration.md) ran every network call the engine makes for a clone in a git directory of Foedrum's own (`withOwnGitDir`, `src/workspace/clone-git.ts`), and every other git call in the clone with `IN_CLONE`, so that a key a brewer wrote into the clone's configuration (`credential.helper`, `core.sshCommand`, `url.*.insteadOf`, `include.path`, …) never runs or redirects the engine's git. Its proof was a review finding (#200), not an incident.

The risk is "a brewer reaching outside its worktree", whose owner is Claude Code's sandbox with the attempt settings Foedrum writes (`docs/trust-boundaries.md`). ADR 0096 was a second layer for that risk with no recorded decision saying what it catches that the owner does not, which the security rule of `CLAUDE.md` asks for. #270, which would have extended it to filter drivers and the checkout's lazy fetch, was closed on 2026-10-22 for that reason: if the sandbox lets a brewer write the clone's configuration, the fix is a `denyWrite` entry in the attempt settings, in one place. The safeguard audit of the same day kept ADR 0090's base fetch, which fixes a wrong answer (the push compared with the clone's stale `origin/<base>`, #202), and dropped the rest of ADR 0096 (#364).

## Decision
- **The push and its lookup run in the clone, by its remote, as before ADR 0096** (`openBranchPush`, `src/workspace/branch-push-git.ts`): `push --no-verify <remote> <sha>:refs/heads/foedrum/…` and `ls-remote --refs <remote> refs/heads/foedrum/…`, where `<remote>` is `origin` unless the caller names another. The push still names the commit by its full sha and never forces, and sends that one ref only: `--no-follow-tags --no-recurse-submodules`, so a user's `push.followTags` or `push.recurseSubmodules` never sends a tag a brewer made or a submodule's commits past the ledger (review of #370).
- **The worktree manager's fetch runs in the clone** (`openAttemptWorktrees`): `fetch --quiet --prune --no-auto-maintenance --no-recurse-submodules <remote>`, one at a time per manager, as before ADR 0096. No maintenance starts that would outlive the call, and no submodule's remote is fetched, as the git directory's fetch had it (review of #370). `--prune` is new: a branch the remote deleted and made again as a folder (`x` gone, `x/y` new) would otherwise stop every later fetch on the ref `x` the clone still tracks (review of #266), and git's prune removes `x` before it writes `x/y`. A `local` repository's worktrees fetch from its clone's `origin` again, not from `https://github.com/<repo>.git`. `fetchIntoClone` and its two-step write-back go.
- **ADR 0090's base fetch keeps its git directory of its own** (`baseTip`, through `withOwnGitDir`), with the partial-clone fetch ADR 0096 added to it (`OwnGitDir.fetch`): the managed clone is blobless, and a fetch of a change to a file it has no copy of fails without a promisor remote in that directory (`unresolved deltas left after unpacking`, review of #266). So the directory, its root `git-dirs/`, the URL Foedrum names and the promisor setup stay.
- **The noPush guard's listing is gone** ([ADR 0133](0133-the-nopush-guard-goes-a-brewer-s-git-holds-no-push-credential.md)), so the base fetch is the one call left in a git directory of its own.
- **`IN_CLONE` keeps what is plain correctness of the engine's calls**: `core.hooksPath` at the null device and `core.fsmonitor=false`, for every local call in the clone and for `worktree add`. The engine's own reads and ref updates must not run whatever hook or fsmonitor the clone has, the user's included: a `reference-transaction` hook that fails would fail the engine's `update-ref`, and an fsmonitor daemon would outlive the call. The push gets the same, as it did before ADR 0096 (`--no-verify` skips only `pre-push`).
- **`IN_CLONE` drops what existed only against planted configuration**: `GIT_ALLOW_PROTOCOL` empty, `protocol.allow=never` and `GIT_NO_LAZY_FETCH=1`. They stopped a lazy fetch through transport keys a brewer planted. Without such a plant, a lazy fetch of an object a partial clone lacks reaches the clone's own remote, which is where that object is. With `IN_CLONE` the same for `worktree add` and every other call, the separate `checkout` git of the worktree manager goes too. The secret scan's own settings ([ADR 0079](0079-the-push-scans-the-batch-s-commits-for-secrets.md)), which include `protocol.allow=never` and `GIT_NO_LAZY_FETCH` so that no word it asks `cat-file` about leaves the machine, stay as they are.
- **ADR 0130's cleanup is unchanged**: it removes the `<uuid>.git` directories a stopped call left in `git-dirs/`, now only those of the base fetch. Its floor of one hour was set by the worktree manager's fetch, the longest holder; the base fetch (300 s) keeps a directory for less, so the floor still holds with more room.

## Consequences
- A key a brewer writes into the clone's configuration takes part in the push, its lookup and the worktree manager's fetch again, and in every other engine call in the clone (`inClone`, `worktree add` included) that reads an object a partial clone lacks, through the lazy fetch a planted promisor or transport key can steer (review of #370). That stays the sandbox's to prevent (`docs/trust-boundaries.md`, row 9).
- **Where the owner does not reach yet** (review of #370). At the permissions-only level (native Windows), and in check steps on every level until #190, a brewer can already run code it wrote as the user: an allowed toolchain command that runs a script it edited. That reaches far more than the clone's configuration (the user's files, gh's login), so a git directory of the engine's own around three calls never closed it. The owner closes it: #190's check sandbox for check steps, and for the brewer a `denyWrite` of the clone's git directory in the attempt settings where the sandbox applies. The engine adds no layer for it (`docs/trust-boundaries.md`).
- A `local` repository's worktree fetch, push and lookup reach the clone's `origin` with the user's own setup (ssh included), as before ADR 0096. Its base fetch still reaches `https://github.com/<repo>.git` (ADR 0090).
- The push, its lookup and the worktree fetch make no git directory, so each is an `init` and a removal cheaper, and a kill mid-call leaves nothing in `git-dirs/`.
- `test/integration/clone-config.test.ts` loses its planted-key tests and its lazy-fetch test, and becomes `test/integration/clone-git.test.ts`: the fetch, `worktree add` and push past hooks of the clone's that fail, the fetch past a branch made again as a folder, and the managed blobless clone's fetch, base fetch and push. The unit tests of `fetchIntoClone` and of the transport part of `IN_CLONE` go.

## Alternatives considered
- **Drop the base fetch's git directory too, and fetch the base in the clone.** It would update `origin/<base>` for the next batch as well, but the decision of #364 keeps ADR 0090 as it is; the one-call gain does not justify reopening it here.
- **Keep the whole of `IN_CLONE`.** Its transport part catches only a planted promisor or transport key, the sandbox's risk; and without a plant it turns a lazy fetch the clone's own remote would answer into a failure.
- **Keep ADR 0096 and record it as a second layer.** Nothing observed needs it, and the sandbox's `denyWrite` for the clone's configuration, if one is ever needed, closes the same paths for every git a brewer can reach, not only the engine's.
