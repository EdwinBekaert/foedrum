# 0097. `npm run demo` is a development script on serve's seams, with the tests' fakes

Date: 2026-10-20 · Status: Accepted

## Context
#193 asks for `npm run demo`: a batch taken from Ordered to On tap, through a crash and a restart, in about a minute and on any machine, with no GitHub, no token and no `claude`. It must use the seams the tests use, not a second engine path: the scripted brewer runner of `test/helpers/fake-brewer-runner.ts`, and a fake code host where `foedrum serve` reaches GitHub through gh (ADR 0073). Three things needed deciding: where the demo's code lives, whether it may import `test/helpers/`, and what keeps those fakes out of the program a user installs.

Serve's machine is already injected: `runServe` takes a `ServeShell` (ADR 0063), and `serveShell` builds the real one. Three of its members are what the demo must replace: `runner` (claude), `gh` (GitHub) and `wait` (so a life can end once the batch is on tap). Serve's git also reaches GitHub: the push fetches the base from `https://github.com/<repo>.git` (ADR 0090), and after #200 the attempt worktrees fetch from there too, from a git directory of the engine's own, never through the clone's origin. And serve commits on the state branch with the clone's configuration, so on a machine with no global git identity (a CI runner, a fresh clone) the commit fails. Everything else (the driver lock, the SQLite store, the state branch, the attempt worktrees of a local clone, the checks, the push of the bottle branch and its secret scan) is the real machine, run against git repositories in a scratch folder.

A crash cannot be played inside one process. The driver lock is held by the process (ADR 0037), so a second Cellar in the same process would be refused; and a stop through the shell's signal is serve's graceful stop, which ends the runs and lets the lock go, not a crash. On macOS and Linux the process runner's kill sends SIGTERM first, which serve also handles as a stop.

## Decision
- **The demo is a development script under `scripts/`, never part of `src/`.** `scripts/demo.ts` is the shell: it makes the scratch Brewery and the target repository, each a clone of a bare remote, under `.foedrum/tmp/demo/` (removed at the start of every run; `--in` names another folder, which must be inside the checkout's `.foedrum/tmp/`), writes the demo's git configuration (below), runs the Cellar twice, and judges the run. `scripts/demo/core.ts` holds the decisions (the scratch folder, the Brewery's files, the git configuration, what counts as a good run), unit-tested with plain data (ADR 0021). It is not a `foedrum` command: a user's Brewery has nothing to gain from it, and a command would ship the fakes.
- **One life of the Cellar is `scripts/demo/cellar.ts`, a process of its own** that runs serve's own `runServe` with `serveShell`'s machine and three members of its own: the scripted brewer for `runner`, the code host for `gh`, and a `wait` that ends the life once the batch is on tap and the status comment's revision that shows it is applied (ADR 0072), or at once when the batch is Stuck or cancelled (`lifeEndOf` in the core decides). Three more members serve only the `wait`: `openStore` keeps the store for the `wait` to read, `signal` adds the `wait`'s own stop to serve's, and `intervalMs` is 100 ms instead of 5 s. The setup is `serveSetup`'s, with a diagnosis that names no `claude` to start and no sandbox.
- **Every git of the demo reads a git configuration of the demo's own**, its global one, with no system one: `scripts/demo.ts` writes `gitConfig` to `<scratch>/gitconfig` and starts its own git and both lives of the Cellar with `GIT_CONFIG_GLOBAL` pointing at it and `GIT_CONFIG_NOSYSTEM=1`. It holds the demo's `user.name` and `user.email`, `commit.gpgsign=false`, `url."<scratch>/web.git".insteadOf=https://github.com/demo/web.git`, and `url."<scratch>/no-such-remote".insteadOf=https://github.com/` for every other GitHub URL (git takes the longest match), so a URL serve names some other way fails on the machine instead of reaching github.com. So serve's own push and fetches reach the scratch remote through the URL serve names, now and after #200, with no seam for them, and serve's state-branch commits have an identity whatever the machine has. None of the machine's own configuration (an identity, signing, a url rewrite, a hook) takes part.
- **The crash is a real one.** In the first life the scripted brewer commits its fixed change in the attempt's worktree, and the Cellar's process then kills itself with SIGKILL, after the line that says so has been written. No `finally` runs: the operating system frees the driver lock, and the attempt is left started, with its lease and its worktree. The second life is serve's own restart: it expires its owner's leases (ADR 0037), loses the attempt, retries it, opens the pull request and puts the batch on tap.
- **The demo may import `test/helpers/`, and only the fakes that are the seams' other sides**: `fakeBrewerRunner` and `behave` (the brewer), `fakeGitHubApi` and `ghOver` (the code host). So the demo and the tests exercise the same doubles. `scripts/demo/brewer.ts` puts the scripted runner behind a fixed commit; `scripts/demo/code-host.ts` puts the fake API behind the fake gh, in the Cellar's process, and keeps every write in a journal file in the scratch folder that the next process plays again, so the pull request and the status comment outlive the crash as GitHub's would. Nothing goes to a socket, not even on loopback.
- **The package ships the program only.** `package.json` lists `files`: `src/`, `defaults/` and `schemas/`, so `scripts/` and `test/` never reach a package, and a unit test (`test/unit/package-files.test.ts`) checks that list and that no module under `src/` imports from `test/` or `scripts/`. The direction is one way: scripts and tests may use the program and the fakes; the program uses neither.
- An integration test (`test/integration/demo.test.ts`) runs `node scripts/demo.ts --in <folder>` and checks the batch on tap in the store, after a lost first attempt, with exactly one pull request and one status comment on the code host and the brewer's commit on the bottle branch of the scratch remote. It starts no gh and no `claude`.

## Consequences
- `npm run demo` runs anywhere `npm run check` does, needing node and git only; it takes about 25 s on a Windows laptop, most of it git and two node starts.
- A change to serve's shell or its seams shows up in the demo, because the demo is serve with three seams replaced (and three members that only let the demo read its store, stop and tick faster), and its git reaches GitHub's URLs only through the demo's `insteadOf`; a change that breaks the demo fails the integration test on every leg of CI.
- If serve's git named the target another way (another case, no `.git`), the catch-all sends it to a path that does not exist: the demo fails at once, on the machine, and the integration test with it.
- The scripts under `scripts/demo/` load `test/helpers/` at run time, so a checkout without `test/` cannot run the demo. A clone always has it.
- The fakes in `test/helpers/` now have a second user: a change to `fakeGitHubApi`'s answers or to `fakeBrewerRunner`'s behaviours must keep the demo working, which the integration test checks.
- The code host's journal is written before its answer goes back to the Cellar, so a write the Cellar saw is never lost with it; a write made in the instant of the kill and never answered may still be replayed. The demo kills the Cellar only once the brewer has committed, when no write is underway.

## Alternatives considered
- **A `push` seam whose base comes from the scratch remote,** as the first version of this pull request had. It needs `openBranchPush`'s base option and `baseFetchRoot`, which #200 removes, and it does not cover the attempt worktrees' fetch from GitHub that #200 adds: the demo would reach github.com.
- **A local `user.name` and `user.email` in the scratch clones,** as `test/integration/serve.test.ts` sets. It fixes the identity of serve's commits, but not where serve's git fetches from, and leaves the machine's own configuration (signing, hooks, url rewrites) in play.
- **A `foedrum demo` command under `src/`.** It would ship the scripted brewer and the fake code host to every user, or need copies of them in `src/`: a second set of doubles to keep in step with the tests'.
- **Moving the fakes from `test/helpers/` to `src/`.** The program would carry code no Brewery runs, and the test-layer guard's reach over `test/helpers/` (ADR 0021, ADR 0086) would no longer cover them.
- **Playing the crash in one process,** by abandoning the first `runServe` without closing it. The driver lock and the SQLite store would still be held by the live process, so the restart would be refused or would share a connection, and it would show nothing a user's crash does.
- **Killing the Cellar from the demo's shell through the process runner.** On macOS and Linux that sends SIGTERM first, which serve handles as a graceful stop; a SIGKILL needs the child's pid, which the runner does not give. The life that crashes kills itself instead, at a point the brewer chooses, so the run is the same every time.
- **A fake code host as an HTTP server in the demo's shell,** reached by the Cellar over loopback, as `test/integration/fake-github-over-gh.ts` is reached by the real gh. It would open a socket for nothing: the journal gives the same survival with no network at all, and serve's `gh` seam takes an in-process runner as it is.
