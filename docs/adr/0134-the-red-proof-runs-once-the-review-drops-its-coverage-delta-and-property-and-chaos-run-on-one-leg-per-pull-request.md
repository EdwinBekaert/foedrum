# 0134. The red proof runs once, the review drops its coverage delta, and property and chaos run on one leg per pull request

Date: 2026-10-22 · Status: Accepted · Amends [0017](0017-test-first-recipes-and-tasting-lenses.md) (what the review of Foedrum's own pull requests runs), [0033](0033-chaos-tests-effects-found-by-key-and-leases-at-start.md) and [0051](0051-chaos-runs-on-the-real-driver-with-two-drivers-and-a-terminal.md) (chaos runs on one leg per pull request) and [0054](0054-test-runs-below-normal-priority-and-review-runs-scoped-to-the-question.md) (the coverage delta and the red-proof check before a push) · Amended by [0150](0150-mutant-tests-drops-its-coverage-option.md)

## Context
On 2026-10-22 one issue session's close ran the same work several times (#361):

- **The red proof twice.** CLAUDE.md asked for `/brew-review --red-proof` before the first push and before every push of new test or implementation commits; then stage 1 of `/brew-review <n>` ran the same red proof again on the same commits. The early run was meant to catch a bad order while the commits could still be redone. Its only catch is a commit order that is wrong, and a session that commits each red test before its implementation, as CLAUDE.md asks, gets the same pass twice; the review's run reports a wrong order too, as a blocker with the failing commits, and the pull request is still a draft then. The second run found nothing the first had not.
- **The coverage delta (stage 5).** It cloned a second scratch tree at the base, installed it and ran the covering tests at the base and at the head with coverage, to report a table of percentages. `npm test` already fails when coverage drops below its thresholds (90 % lines, 85 % branches, 90 % functions), on every check and on every CI leg, and the gate runs that check before every push. The table was never a reason to change a pull request on its own: a gap it showed in new code is a test that is missing, which the test design lens and Brett's survivors already point at with the line and the case. ADR 0017 itself says why coverage alone does not count: it shows code ran, not that a test would fail on a bug.
- **Property ×500 and chaos ×200 on all three legs of every pull request.** The properties and the chaos cases run the engine on generated scenarios: the fold, the store on SQLite, the driver killed at random points. The property tests run on an in-memory store and are the same on every platform: a seed that fails on one fails on the others, since the scenarios are a pure function of the seed. The chaos tests have one platform edge: they run the real driver on an SQLite file and free its lock on restart, and Windows handles open files and locks differently. That edge is also exercised by the 5 chaos runs `npm run check` makes on every leg, and the platform module's own edges (paths, process trees, file-lock retries) by the integration tests, which still run on every leg. Three legs ran three times the seeds of one, at the same moment, for the same code. The nightly run already took chaos to 1,000 runs on every leg; property stayed at 500 there.

## Decision
- **The red proof runs once, in `/brew-review <n>`** (stage 1). The close steps no longer ask for `/brew-review --red-proof` before the push. `--red-proof` stays in the skill for a session that wants the check earlier, for example before the first push of a long branch.
- **The review has no coverage stage.** Stage 5 goes, with its section of the summary; the summary stage is now stage 5. The thresholds in `npm test` stay where they are and are only ever raised (CLAUDE.md, Commands). `scripts/mutant-tests.ts --coverage` keeps working for a coverage run by hand; the review no longer calls it.
- **Property ×500 and chaos ×200 run on one leg per pull request**: `ubuntu-latest`, for `pull_request`, `push` and `workflow_dispatch`. **The nightly run** (`schedule`) runs both on every leg at ×1,000. A failure names its seed on any leg, and `FOEDRUM_SEED` replays it on any platform.

## Consequences
- One red proof per pull request instead of two. A wrong commit order is found at the review, while the pull request is a draft, instead of before the first push. Pushed commits are never rewritten, so such a blocker can only be dismissed with a reason the user gives (stage 1, step 4); a session that is unsure of its order runs `--red-proof` before pushing.
- A review no longer makes a second scratch tree at the base, installs it, or runs the covering tests twice with coverage. A coverage drop below the thresholds fails `npm run check` on the branch, as it did; a drop that stays above them is no longer shown in the summary. A new or changed file with low coverage that does not move the total below the thresholds is no longer measured: it is judged by the test design lens and Brett, not counted.
- Two of three legs of every pull request skip the property and chaos runs, about half a minute to two minutes each (the nightly run of 2026-10-22: property ×500 took 11–23 s, chaos ×1,000 53–122 s per leg). A defect that only a seed beyond the check's few finds, and only on Windows or macOS, is found by the nightly run instead of the pull request, after the merge; that is the risk this accepts, most of all for the chaos tests' SQLite file and driver lock on Windows. None has been seen.
- Property tests run 1,000 seeds per property in the nightly run instead of 500, so the nightly run reaches further than any pull request, as it already did for chaos.

## Alternatives considered
- **Keep `--red-proof` before every push:** it catches a bad order while the commits are unpushed, but the review runs it again on the same commits; the cost was paid on every issue for a failure the review reports anyway.
- **Keep the coverage delta as an advisory table:** cheaper than before ADR 0054, but still a second tree and two test runs per review for a number the thresholds already enforce and the lenses already turn into findings.
- **Raise the thresholds in place of the delta:** a separate decision; the thresholds only ever go up, by hand, when the suite allows.
- **Property and chaos on one leg also at night:** cheapest, but the nightly run is where a platform-specific failure behind a rare seed would show at all.
- **A smaller seed count on the other legs:** keeps a little platform spread on every pull request, but the property tests have no platform edge, and the chaos tests' one edge (the SQLite file and the driver lock) gets `npm run check`'s 5 runs on every leg.
