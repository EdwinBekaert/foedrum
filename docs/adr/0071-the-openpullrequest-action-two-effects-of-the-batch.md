# 0071. The openPullRequest action: two effects of the batch, run by the driver

Date: 2026-10-18 · Status: Accepted · Amends [0053](0053-recipe-files-reach-the-engine-brewer-steps-in-a-line-first.md) (the action step loads) and [0059](0059-attempt-plans-from-the-brewer-of-the-step.md) (on tap without a pull request)

## Context
A batch ends in a pull request: the recipe's `{ "action": "openPullRequest" }` pushes the bottle branch and opens the pull request, and the engine does that itself, never a brewer (brewers-and-recipes §1: pushing is always the engine's job). Until now the loader refused every action step by kind ([ADR 0053](0053-recipe-files-reach-the-engine-brewer-steps-in-a-line-first.md)), and a recipe of brewer steps went on tap with no pull request ([ADR 0059](0059-attempt-plans-from-the-brewer-of-the-step.md)).

The push and the open are external side effects, so each goes through the idempotency ledger and must happen at most once (I4), also when the driver is killed between them or in the middle of one. [ADR 0066](0066-the-task-tree-continues-from-the-latest-succeeded-attempt.md) already says what is pushed: the batch's task tree, resolved in the clone, never from an attempt's worktree. [ADR 0043](0043-target-repository-issues-as-a-work-queue-claimed-by-a-ref.md) says under which name: `foedrum/<brewery>/<rest>`, so two Breweries never push the same branch, and architecture §3.4 that the bottle branch is `foedrum/<batch>/<repo>` and an existing pull request is looked up before one is made.

This is #178. Bottles of several sub-orders (`bottling`), the update of an open bottle after a rewind (§3.4) and the other actions (`comment`, `label`, `blend`) are not.

## Decision

### The action step
- **The loader takes `{ "action": "openPullRequest" }`** with the id `open-pull-request` by default, and a `when` that reads the recipe's settings as any step's may (ADR 0064). It must be the **last step** of the recipe: the pull request holds the commits of the steps before it, and a step after it would commit what no push carries. Otherwise the load fails with `step "<id>" opens the pull request, so it must be the last step of the recipe (ADR 0071)`. The other actions stay refused by kind (ADR 0053).
- Its `Recipe` answers: `action(id)` is `openPullRequest` (`undefined` for any other step); a deadline of **2 hours**, so the effects are tried on every pass of the driver through a GitHub rate-limit pause, which lasts an hour at most (ADR 0052); no stall limit; **3 attempts**; no route back. After it the recipe is done, naming the step: `{ kind: 'done', pullRequests: [], opens: 'open-pull-request' }`.

### The driver runs it
- **An attempt of an action step is the driver's own.** The supervisor schedules it and holds it to its deadline as any attempt (I1, I5), but the driver never starts it on the runner. It records `step.started` with **no lease and no worktree**: no process runs it that a lease could outlive, the push reads the task tree in the clone (ADR 0066), and the effects are applied only by the holder of the batch's lease (ADR 0044). Without a lease the supervisor never loses it, so a pass whose effects fail does not use up an attempt; its deadline still makes the batch Stuck (`deadline_passed`) when the code host stays down.
- **Two effects of the batch, in this order**, through `DriverActions` (`src/engine/driver.ts`), which the driver's pass applies after the batch's other effects, each under the batch's lease and its deadline, one pass at a time, as every effect (ADR 0033, ADR 0050):
  1. `["<batch>","push"]`: the commit `taskTreeStart` names, resolved in the repository's clone with `rev-parse`, pushed to `refs/heads/foedrum/<brewery>/<batch>/<owner>.<name>` of the clone's `origin`, **never by force** and with **no hook of the clone** running: `--no-verify` skips only pre-push, so `core.hooksPath` points at the null device for the call; a brewer's code can write hooks into the clone its worktree shares, and those would run as the engine. When the commit is the base's (`origin/<base>`), nothing is pushed: the result says so (`empty: true`), since the code host refuses a pull request with no commits. It is found when the remote branch is at that commit already (`ls-remote`): a run killed after the push and before its record. A remote branch at another commit is not found, and the push that follows is refused unless it is a fast-forward; the effect fails and is reported. Its result is `{ branch, commit, from }`, `from` being the revision `taskTreeStart` named.
  2. `["<batch>","pull_request"]`: the pull request from that branch into the repository's base. It is found when the code host has a pull request from that very branch, in the repository itself (never a fork's), opened by the Brewery's own login, open or closed: the branch name is predictable, so anyone else's never counts. Its result is the pull request's URL, checked as `batch.on_tap` checks it (`https`, no credentials).

  A pass stops at the first effect that fails, so no pull request is opened before the push is recorded. A kill on either side of either effect leaves the next driver to find what landed and apply only what did not: never two pushes, never two pull requests (I4).
- **The attempt ends once both are in the ledger**, at the end of the pass, under the batch's lease: `succeeded` with `output: { pullRequest: <url> }`. A driver killed after the last record and before the end leaves the end to the next pass of whichever driver holds the batch. A batch with no task tree yet (no attempt that succeeded made a worktree) has nothing to push: its action asks for no effect and fails, not retryably, `batch <id> has no commits to open a pull request with: …`; so does one whose recorded push was empty (`… has no commits beyond <base> …`); so does one whose repository the Brewery does not list. A driver given no actions (a session without a code host) blocks the attempt on its environment at its start.
- **The effects are keyed by the batch, not the attempt.** A retry of the action after a deadline continues where the first attempt stopped, and a batch opens one pull request in its life. The push and the pull request stay as recorded, so a task tree that moved after the push, as a rewind moves it, would never reach the pull request: the action then fails, not retryably, naming the revision it pushed and the one it would push now, and the batch goes Stuck instead of on tap with the old pull request. Updating an open bottle in place (§3.4) is a follow-up.

### On tap only with its pull request
- **A rule in `decide`**: when the recipe is done and names the step that `opens` the pull request, the batch goes on tap with the URL the ledger recorded under `["<batch>","pull_request"]`, and the command is refused while there is none: `batch <id> goes on tap only with the pull request of its step <step>, and the ledger has none`. So a human `skip` of the action is refused; `cancel` stays. A batch whose `when` skipped the action (`step.skipped`) goes on tap without one, as the recipe says.
- **The event schema stays as ADR 0059 left it**: `batch.on_tap` may name no pull request, so the logs of batches that went on tap without one still replay.

### The pull request's text
- **Title**: the title of the order's issue, on one line, at most 256 characters (GitHub's limit); the order (`owner/name#n`) when it has none. Read when the effect applies (`githubOrderTitle`, `src/github/order-text.ts`).
- **Body**: `Brewed by Foedrum from <owner/name>#<n>.`, then what each step reported, the summary and assumptions of its latest out doc that succeeded, in the order the steps were first scheduled, then `Closes <owner/name>#<n>` for the order's issue: a Brewery issue in the Brewery, a claimed issue in its own repository. The reports are model output that read the order, so they go in a fenced `text` block, longer than any run of backticks in them, where GitHub links no issue, mentions nobody and reads no closing keyword: a summary that says `Fixes #3` closes nothing. A run of more than 16 backticks is cut to 16, so the fence, which comes twice, stays short, and the reports are cut short within GitHub's 65,536 characters (`pullRequestText`, `src/engine/pull-request.ts`).
- GitHub's closing keywords name a repository as `owner/name`; the intake's short `alias` (ADR 0050) is Foedrum's own name for it and would close nothing, so the line uses `owner/name`.

### Where it runs
- `pullRequestActions` (`src/engine/pull-request-actions.ts`) works out each effect from the folded state and applies it through two interfaces: `BranchPush`, git in the clone (`openBranchPush`, `src/workspace/branch-push-git.ts`, which refuses a commit that is no full sha and a branch outside `foedrum/` before git runs), and `PullRequestHost`, the code host (`githubPullRequests`, `src/github/pull-requests.ts`: the pulls listed by `head=<owner>:<branch>`, conditional like every read, and `POST /repos/{owner}/{repo}/pulls` with `maintainer_can_modify: false`).
- `foedrum serve` gives the driver the actions: each repository's pushes from the clone its worktrees are added to (the user's for `local`, the managed one for `managed`), into the branch the attempts start from, and the Brewery's login, read once the first pull request is looked up.

## Consequences
- A recipe that ends with `openPullRequest` brews to a pull request in `foedrum serve`. `test/chaos/pull-requests.test.ts` kills the driver before and after the push and the open, once and twice in a run, and every run goes on tap with one pull request from one push; `test/integration/pull-request-push.test.ts` pushes a brewer's commit through `openDriver` and real git to a local bare origin, and shows a bottle branch at another commit is never forced. No test reaches GitHub.
- `Recipe` has `action(stepId)`, and `Continuation`'s `done` may name the step that `opens` the pull request. No event changes.
- A push from a `local` clone uses the user's remote and credentials, as a fetch already does (ADR 0012); a `managed` clone pushes to `https://github.com/<repo>.git` through the user's credential helper. A push that needs a prompt fails, since git never prompts, and the batch goes Stuck at the action's deadline with the reason in the reported effect.
- The pull request opens ready for review, not as a draft; the status comment and the bottle's merge order (§3.2) come later.
- ADR 0059's sentence that a recipe ends without a pull request "until the `openPullRequest` action lands" holds now only for a recipe without the action.

## Alternatives considered
- **A runner for the action, like the check runner.** The driver would not change, but the push and the open must go through the ledger under the batch's lease and within an effect's deadline, which only the driver's effect pass has; a runner's attempt runs under the attempt's lease, which a lost runner lets expire while its push may still land.
- **Effects keyed by the attempt.** A retry after a deadline would push and open again: a second pull request for the same branch, which GitHub refuses, or a second push of a moved task tree. One pull request per batch is what the recipe asks for.
- **One effect for push and open.** One record, but a kill between the two would leave a push with no record and nothing to tell the next driver whether the pull request was asked for.
- **Read the pull request from the action attempt's output in `decide`.** The same URL, but the ledger is where the effect's result is kept; the output repeats it for whoever reads the attempt.
- **Let the action sit anywhere in the recipe.** The steps after it could commit what the pull request never gets; that waits for the updates of an open bottle.
- **Quote the reports as Markdown.** Easier to read, but a model-written `Closes #3` or `@team` would close another issue or ping people.
