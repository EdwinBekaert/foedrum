# 0126. `foedrum resume` opens a finished attempt's session in its worktree

Date: 2026-10-22 · Status: Accepted · Amends [0019](0019-interactive-sessions-and-one-command-layer.md) (how stepping into a finished attempt's session works, and what it leaves out), [0030](0030-only-commands-that-change-state-are-recorded.md) and [0044](0044-batch-leases-held-by-the-driver-and-one-command-log.md) (a read-only command may hold an attempt's lease) and [0055](0055-a-step-waits-for-the-lease-of-its-abandoned-attempt.md) (a finished attempt's lease that a resume renews holds its step back until the session ends or the waiting attempt's deadline)

## Context
[ADR 0019](0019-interactive-sessions-and-one-command-layer.md) lets an engineer step into any brewer's session: `/foedrum:resume <batch> [<step>]` opens the brewer's own session (`claude --resume`) in its worktree, with the same per-attempt settings, so the engineer sees what the brewer saw and did. Since [ADR 0116](0116-the-driver-records-each-attempt-s-session-and-claude-s-report-goes-on-step-finished.md) every brewer attempt records its session id and worktree on `step.started`. This record covers a finished attempt, for inspection or a follow-up (#337). Taking over a running batch by resuming its session is #338.

What Claude Code offers was checked in its docs (code.claude.com, 2026-10-22):

- **CLI reference, `--resume`:** "When you pass a session ID, Claude Code searches the current project directory and its git worktrees, then every other project on this machine." Without `--print`, `claude` is an interactive session; `--max-turns`, `--output-format` and `--permission-prompts` are print-mode flags. `--permission-mode`: "Without this flag …, a new session starts in the permission mode described in which permission mode a session starts in", the mode that asks.
- **Manage sessions, "Where transcripts are stored":** `~/.claude/projects/<project>/<session-id>.jsonl`, under `CLAUDE_CONFIG_DIR` when it is set, kept for `cleanupPeriodDays` (30 days by default), as ADR 0116 found.
- **Environment variables, `CLAUDE_CODE_CHILD_SESSION`:** "Set to `1` in subprocesses Claude Code spawns via the Bash, PowerShell, and Monitor tools, hook commands, and status line commands. … Unlike `CLAUDECODE`, this is only set by Claude Code itself …, so it reliably distinguishes a nested session from a top-level `claude` launched in an IDE-integrated terminal."
- **Skills, "Inject dynamic context":** a command's `` !`<command>` `` "runs shell commands before the skill content is sent to Claude. The command output replaces the placeholder", with the Bash tool's 2-minute timeout. **Interactive mode, "Shell mode with `!` prefix":** "Adds the command and its output to the conversation context". Neither hands the terminal to the program it runs, so a plugin command cannot open an interactive `claude`.

## Decision
- **`foedrum resume <batch> [<step>[#<n>]]`** is a command of the registry (ADR 0019), read-only in the log: it appends no event. Without a step it takes the latest attempt of the batch, in the order of the log, that started with a session and finished; with a step, the latest such attempt of that step; with `#<n>`, that attempt, refused when it has not finished or ran no brewer.
- **A running batch is refused:** an Ordered or Brewing batch is a driver's, and resuming one is #338. A malformed `#<n>` (not a whole number from 1) is refused with its own line.
- **The session must be on this machine.** It is looked for as `projects/*/<id>.jsonl` under Claude Code's config directory (`CLAUDE_CONFIG_DIR`, or `.claude` in the home folder), in any project folder, so Foedrum does not depend on how Claude Code names them. When it is not there, the command says so in one line, with why (sessions stay where they ran, 30 days by default), and starts nothing. ADR 0019's fallback, a fresh attempt with the answers, is for the engine's own resumes; for an engineer it would open a session the brewer never had.
- **The worktree comes back with `recreate`** ([ADR 0029](0029-attempt-worktrees-layout-claims-and-repair.md)): the one that is there, or the attempt's branch checked out again, or a new branch at the commit `step.started` recorded when the cleanup deleted the branch too. The repository and clone are serve's, from `foedrum.jsonc` and `.foedrum/local.jsonc`, so resume needs what serve needs and refuses with serve's lines.
- **The settings file is written again** at the attempt's place in the work root, from the brewer of the step in the batch's recipe and the repository's toolchain rules, through the same function the attempt plan uses (`attemptPermissions`). It holds what the brewer's attempt had unless the Brewery's files changed since.
- **The command line** keeps the attempt's guards and model: `--resume <id>`, `--model`, `--effort`, `--settings`, `--setting-sources ""`, `--tools`, `--disable-slash-commands`, `--strict-mcp-config`, `--safe-mode`. It leaves out the print-mode flags and `--permission-mode dontAsk`: the engineer is there to answer, so what the settings do not allow is asked, and what they deny stays denied. It runs in the attempt's own environment (`buildBrewerEnv`: the brewer's minimal base, the brewer's `env`, the forced variables of [ADR 0109](0109-a-brewer-s-git-holds-no-push-credential.md)), plus the variables a terminal program reads to draw itself (`TERM`, `COLORTERM`, `TERM_PROGRAM`, `LANG`, `LC_ALL`), never the engineer's whole environment. The allow rules still let commands run without asking, and the transcript and the worktree hold untrusted text, so a GitHub token, the engineer's git credentials and npm's lifecycle scripts stay out as they did for the brewer. claude finds its login as the brewer's did.
- **From a terminal**, `claude` starts in the foreground in the worktree with the terminal's stdin, stdout and stderr, and foedrum waits for it and returns its exit code. Ctrl+C is claude's while it runs. Waiting has no deadline: it is a human's session, and the lease below expires when foedrum dies. On Windows, npm's `claude.cmd` runs under cmd.exe (ADR 0031), which also gets each Ctrl+C, so such a session can end with cmd's "Terminate batch job (Y/N)?"; the native installer's `claude.exe` has no such wrapper.
- **From inside a Claude Code session** (`CLAUDE_CODE_CHILD_SESSION=1`), it opens nothing and claims nothing: it names the attempt it found and prints the `foedrum resume <batch> <step>#<n>` line to run in a terminal, with exit code 0. That is what the plugin's `/foedrum:resume` (#336) shows. **Without a terminal on stdin** otherwise (a pipe, or Git Bash's mintty without a console), it refuses with one line that says so, exit code 1, rather than send the engineer to run the same line again.
- **The worktree stays claimed while the session runs, by the attempt's lease alone** (owner `resume-<pid>`). Before anything else changes, one transaction takes it, unless another owner's lease of that attempt is alive: then a second resume of the attempt is refused, naming the holder. The same transaction reads the log again and refuses a batch a driver took up since it was first read. The refusal is per attempt: once attempts of a step hand one session on (ADR 0029, `session.resumes`), the claim must follow that chain as `worktreeClaims` does. **Read-only** still holds for the log: resume appends no event; the lease is the store's mutable state that ADR 0002 already allows, as for a driver. `worktreeClaims` keeps the worktree of a leased attempt, also of an ended batch. It is renewed every third of its 5 minutes while claude runs and released when claude ends, also when it fails, and never when another owner holds it by then. A renewal that finds another owner, or cannot write, is said on the terminal and the session goes on. A foedrum killed with claude still running leaves a lease that expires; a lease of a finished attempt is only released by the supervisor, never lost.
- **The batch's lease is not taken.** A terminal command is not a driver and takes no batch lease ([ADR 0044](0044-batch-leases-held-by-the-driver-and-one-command-log.md)), so the batch's driver, its supervisor and its reminders go on while the session runs (ADR 0025: a Stuck batch nags). What the attempt's lease holds back is a new attempt of the same step, which waits for it ([ADR 0055](0055-a-step-waits-for-the-lease-of-its-abandoned-attempt.md), `stepLeased`) under that attempt's own deadline, so the wait is never silent.

## Consequences
- An engineer can read a brewer's session as it ran, and follow up in it, from the worktree where it ran.
- Nothing the engineer does in a resumed session reaches the log: commits stay on the attempt's branch. A worktree recreated for an ended batch stays after the session, until the next cleanup that covers its batch: a driver's repair at its start, unless it has uncommitted changes. A running driver does not clean it again by itself, since it cleans an ended batch when the batch ends. Writing the out doc and continuing the batch is #338.
- A `retry` or `answer` of the resumed step, issued meanwhile, schedules an attempt that waits for the resume's lease and expires at its deadline if the session outlasts it. Other steps of the batch go on.
- A Brewery whose brewer or recipe changed since the attempt gets today's settings, not the attempt's.

## Alternatives considered
- **Read the attempt plan (`createAttemptPlans`):** it plans only a started attempt and reads every input, the order's issue too, which the settings do not need.
- **Look for the transcript by its project folder name:** depends on how Claude Code names project folders, which ADR 0116 already chose not to.
- **Let `claude` find no session and say so:** the worktree would already be recreated and claimed, and the line would be claude's, not one that says where Foedrum looked.
- **Open claude from the plugin through `!`:** its output goes into the conversation and it has the Bash tool's timeout; it cannot hand the terminal over.
- **Start a fresh attempt when the session is gone (ADR 0019's fallback):** it would look like the brewer's session but hold none of it.
- **Hold the batch's lease too:** it would keep drivers out, but a terminal command would become a driver (ADR 0044 rejected that) and a Stuck batch would lose its reminders for as long as the session stays open.
- **The engineer's whole environment:** claude's login is the same either way, and the allow rules would then run commands with the engineer's tokens and credential helpers.
