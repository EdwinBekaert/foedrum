# 0039. On Windows, a process tree that must not outlive a kill runs in a Job Object

Date: 2026-10-16 · Status: Accepted · Amends [0010](0010-cross-platform-and-isolation-levels.md)

## Context
On Windows the process runner (`src/platform/processes.ts`) kills a tree with `taskkill /T /F /PID <pid>`. taskkill finds the tree through parent pids, starting from a process that must still be alive, so it cannot see a grandchild whose parent has already exited (#92). Such a grandchild keeps running after the kill and holds the runner's output pipes open, which is why the runner answers at its deadline without waiting for them. Node holds the children it starts in a kill-on-close job of its own. That job allows silent breakaway, though, so it holds only node's direct children, and a child started detached (or by cmd.exe, a shell or any other program) is in no job at all. The brewer runner (#11) will hit this: `claude` starts shells, test runners and servers whose parents come and go, and stopping an attempt must end them all (ADR 0028).

Windows's way out is a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`: a process created by a process in the job is in the job too, and when the last handle to the job closes, Windows ends every process in it. Node cannot make one. It has no FFI (`node:ffi` does not exist in Node 24), and a native addon would need lifecycle scripts, which `.npmrc` disables, or a prebuilt binary. Windows has no command-line tool that runs a program in a job.

The spike for this ADR measured these routes on Windows 11 (direct `git --version` takes about 45 ms):

| Route | Per call | Notes |
|---|---|---|
| Windows PowerShell, P/Invoke through `Add-Type` | 1–1.5 s | compiles C# with `csc.exe` into the temp folder on every start |
| Windows PowerShell, P/Invoke emitted in memory | +0.37–0.39 s (median) | nothing compiled or cached |
| A C# helper compiled once with the OS's .NET Framework `csc.exe` | +60 ms, 2 s to compile | an unsigned binary in a per-user cache that differs on every compile (that `csc` has no `-deterministic`), so no hash can be pinned; Smart App Control, AppLocker or Defender may block it |
| Assigning a process to a job after node has started it | small | a grandchild started before the assignment escapes, and a pid that exits first may be reused by an unrelated process |

## Decision
- `ExecOptions` and `RunOptions` take `jobObject`. On Windows, a call with `jobObject: true` starts its program through a helper: `src/platform/job-object.ps1`, run by Windows PowerShell by its full path (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`, `C:\Windows` when `SystemRoot` is unset), as cmd.exe (ADR 0031) and taskkill are. It runs with `-NoProfile -NonInteractive -EncodedCommand`, which no execution policy blocks, and in `System32`, so nothing in a repository's folder takes part in it. The program's path, command line and working directory go into the script as base64 of their UTF-8, so no character in them can change the script. Elsewhere the option is ignored: the runner kills the process group.
- **No race.** The helper creates the job, then starts the program with `CREATE_SUSPENDED`, assigns it to the job, and only then resumes it. Every process the program starts is in the job from the program's first instruction. Assigning a process after node's spawn is not done.
- **Exactly the caller's environment.** The program never inherits the helper's environment, to which Windows PowerShell adds `PSModulePath` and `PATHEXT` when the caller has none (and a later version may add more). The runner builds the caller's environment block from the call's `env` (`windowsEnvironmentBlock`: `name=value` entries sorted by name without regard to case, NUL-separated, ended by two NULs; of names that differ only in case, the first in sorted order, as node's spawn keeps). The helper passes that block to `CreateProcessW` as `lpEnvironment` with `CREATE_UNICODE_ENVIRONMENT`. The block reaches the helper base64-encoded in a variable of the helper's own environment, `FOEDRUM_JOB_ENVIRONMENT`, and not on the command line. There, each character would take about 3.6 of Windows's 32,767: a 3.5 KB environment would take 12,500, and a CI runner's would not fit at all. A variable of 100,000 characters reaches PowerShell intact. The block is built from the call's `env`, so the variable never reaches the program.
- **No module.** The helper calls no cmdlet and turns module autoloading off (`$PSModuleAutoLoadingPreference = 'None'`), so its start never looks through the module path. With autoloading, its first cmdlet (`New-Object`) scanned every module on the machine's module path whenever the caller's environment carried no analysis cache: a brewer's or a check's minimal one (ADR 0063, ADR 0069). On Windows CI that took the check step's integration test from 6 s to 39 s, and once past its 60 s limit (#177); and a module on the path could run its own code in the helper.
- **No way out.** The job has `KILL_ON_JOB_CLOSE` and `DIE_ON_UNHANDLED_EXCEPTION`, so a crash ends a process instead of waiting on an error dialog no one sees. It has no `BREAKAWAY_OK`, so no process can leave it: node's own silently breaking-away jobs nest inside it.
- **The helper holds the job.** It holds the job's only handle (created not inheritable) and stays alive as the program's parent. The program inherits its stdin, stdout and stderr, so the runner reads the program directly, and the helper exits with the program's exit code. The runner's kill is unchanged: `taskkill /T /F` on the helper. Killing the helper closes the handle, and Windows ends the whole tree, orphans included. When the program exits by itself, the helper exits too, and whatever the program left running in the job ends with it.
- **Only what the runner started.** The job holds only the program and its descendants; nothing else can be in it.
- **Fail closed.** When the helper cannot start the program inside a job, it writes `foedrum job object: <why>` alone to stdout and exits with 125 before the program exists. The runner answers that like a program that could not start: `exitCode: null`, with `<program>: cannot run in a Job Object: <why>` in stderr. It never falls back to an uncontained start or to `taskkill /T` alone. The commonest cause is a policy that keeps PowerShell in **Constrained Language Mode** (AppLocker, WDAC), which forbids the P/Invoke the helper needs. The helper checks the language mode first, and the error code of each Windows call is read in the same statement as the call, because anything PowerShell runs in between can overwrite it.
- **Who uses it.** The brewer runner (#11) starts `claude` with `jobObject: true`: a brewer step whose `claude` cannot run in a job does not start, and the attempt ends as one that could not start (ADR 0028). Other callers (git, the gate's checks) keep the direct start, whose short-lived trees taskkill reaches through their parents.
- `foedrum doctor` on Windows starts `node -e ""` with `jobObject: true`. When that fails it reports a required problem, `Windows cannot hold a brewer's processes in a Job Object (<what was said>)`, with the advice to run Foedrum inside WSL2.

## Consequences
- The orphan case of #92 in `test/integration/processes.test.ts` runs on both Windows legs again, without its skip, with `jobObject: true`. A second case kills only the helper (`process.kill`, no taskkill) and checks that every level of a detached tree ends, which only the job can do.
- A call in a job costs a PowerShell start: about 0.4 s more per call (median, measured on Windows 11 for `git --version` and `node -e 0`; the first call of a session, or a busy machine, up to about 1 s). That is fine for a brewer step, which runs for minutes, and too much for every git call, which is why it is per call.
- The helper's script takes about 11,100 of the 32,767 characters Windows allows a command line, and each character of the program's path, arguments and working directory takes about 3.6 more (base64 inside an encoded command). That leaves the program about 6,100 characters; the environment does not count against it. A longer call cannot start (node reports `ENAMETOOLONG`) and answers as not started. Brewer prompts go through stdin and files (architecture §13), not arguments; if a caller ever needs more, the other inputs can move to the helper's environment as the environment block did.
- A program that itself exits with 125, writes nothing to stderr and starts its stdout with `foedrum job object: ` is read as not started. That fails closed: the step ends as one that could not start and is retried, never taken as done.
- The helper uses the 64-bit layouts of the structures it fills. Node 24 has no 32-bit Windows build, so the runner and the PowerShell in its System32 are 64-bit (x64 or arm64); a PowerShell that is not fails closed.
- Processes that a program in a job leaves behind on purpose (a daemon such as git's fsmonitor) end with it. On POSIX they keep running, unless the runner kills the group.
- This amends [ADR 0010](0010-cross-platform-and-isolation-levels.md), which runs brewers on native Windows at the permissions-only level: on a machine where PowerShell runs in Constrained Language Mode, they no longer run natively at any level. The container level does not help there either, because the brewer runner starts the container runtime's CLI through the same runner, with `jobObject: true`. doctor says so and points to WSL2, which ADR 0010 already recommends for untrusted repositories. Native Windows without such a policy keeps every level ADR 0010 gives it.
- If the helper itself is killed between `CreateProcess` and `AssignProcessToJobObject` by something other than the runner, the suspended program is left behind; it never runs. The runner's own kill reaches it, because taskkill walks the tree from the helper, which is still alive at that moment.

## Alternatives considered
- **The csc-compiled helper as the default for every call:** fast enough to contain every call, but it brings an unsigned binary into a per-user cache that cannot be pinned, and that endpoint protection may block; a later ADR can revisit it if many callers need jobs.
- **PowerShell for every call:** contains everything, but adds 0.4 s to each of the many short git calls of the engine and the worktree cleanup.
- **Assigning node's child to a job after the spawn, through a long-lived helper:** cheap per call, but racy, and a reused pid could put an unrelated process into the job.
- **The helper joins the job itself before starting the program:** no race either, but the helper would then be inside the job it guards. Starting the program suspended keeps the helper out, so killing it is what ends the job.
- **Falling back to `taskkill /T` when no job can be made:** keeps brewers running under Constrained Language Mode, but with the orphans this ADR is about; WSL2 is the way there instead.
- **An npm package or a native addon:** needs lifecycle scripts or a prebuilt binary, against ADR 0004 and `.npmrc`.
