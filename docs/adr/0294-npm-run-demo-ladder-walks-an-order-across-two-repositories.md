# 0294. `npm run demo -- ladder` walks an order across two repositories

Date: 2026-11-02 · Status: Accepted · Amends [0097](0097-npm-run-demo-is-a-script-on-serve-s-seams-with-the-tests-fakes.md) (a second part on the same seams, with more lives of the Cellar, and merges and a release the shell makes on the fake code host) and [0283](0283-npm-run-demo-mashes-a-third-order-to-a-plan-waiting-for-its-review.md) (a plan approved and brewed past its review, in a part of its own) · Amended by [0305](0305-a-step-input-of-a-step-the-recipe-lacks-is-left-out.md) and [0321](0321-mash-and-decoction-review-a-plan-through-the-plan-lenses-apart.md)

## Context
M2's exit test reads: "an order across two repositories, where the second needs a release of the first, ends with two linked pull requests and the version bump; routing is visible and overridable" (ROADMAP.md).
Every link of that chain is on main: the plan and its approval (ADR 0281, ADR 0285), the release wait (ADR 0216, ADR 0223), the `release` input (ADR 0291), the sibling sections (ADR 0292, ADR 0300), the close of the Brewery issues (ADR 0293, ADR 0296), the folder of checkouts a Brewery order is planned in (ADR 0301), and a fake code host that merges, releases, tags, compares and edits bodies (#767).
No part of `npm run demo` shows them: its step 12 stops at the plan waiting for its review (ADR 0283).
The maintainer decided on 2026-10-31 that the chain is a part of its own, and that the default demo keeps its twelve steps.

## Decision
- **`npm run demo -- ladder` is the ladder; `npm run demo` stays as it is.** `scripts/demo.ts` takes `ladder` as its one positional argument, makes the scratch folder as before (`--in` and `--no-pause` as before), and hands off to `runLadder` in `scripts/demo/ladder.ts`, which gets the shell's git, CLI, pauses and Cellar processes, so it starts no process itself and its decisions are unit-tested with plain data (ADR 0021).
- **Two repositories and their Brewery.** `demo/lib` holds `@demo/greet` at 1.3.0, and `demo/web` depends on `"@demo/greet": "1.3.0"`; each is a bare remote with a clone, with an `insteadOf` of its own in the demo's git configuration, both public on the fake code host. The Brewery lists them with the aliases `lib` and `web` and no checks, and has a recipe `ladder`: `testFirst: false`, Nip's gauge step under `recipe.testFirst` (so it is skipped and the Cellarman's `tests` input is read as Nip's is without one; without the step the batch goes Stuck at once, #774), the Cellarman, then `openPullRequest`.
- **One order, labelled `recipe:mash`,** so no Innkeeper runs: the status comment says the recipe was "chosen by its label", and the plan comment names each sub-order's recipe; together they are the exit's "routing is visible and overridable".
- **The brewers read what they act on** (`scripts/demo/ladder-brewers.ts`). The Brewmaster reads `lib/package.json` and `web/package.json` in its folder of checkouts and plans a sub-order in each, the second with a `release` dependency on the first; it fails without either manifest. The library's Cellarman changes `greet.mjs`. The application's Cellarman reads the tag from its prompt's `release` input, strips its `v` and writes it into `package.json`; it fails when the prompt names none, so no version is written into the demo.
- **Four lives of the Cellar, each a process of `scripts/demo/ladder-cellar.ts`,** not one per change: `foedrum approve` and the merges are the shell's calls between them, on serve's seams as ADR 0097 has them, each ending on a condition read from its store (`ladderLifeEnd`), on the first tick after it that adds no event, so the effects of the last change are applied first: `plan` (the order's batch Stuck for its review), `lib` (the library's sub-order on tap), `web` (both on tap) and `close` (the order's `close.issue` effect applied). Any other batch Stuck or cancelled fails the life at once.
- **The shell's merges and release stand in for a person and the library's CI.** Between lives, the shell merges a pull request's branch into its remote's main with `--no-ff` and tells the fake code host (`merge`); after the library's merge it commits `package.json` at 1.4.0, tags that commit `v1.4.0`, pushes both and publishes the release (`release`), so the tag and the manifest agree and the release holds the merge.
- **It walks through fourteen steps,** each with what to look for: the order and its plan, `foedrum approve`, the sub-issues, the library's pull request, the merge and the release, the release recorded, the application's sub-order with its `release` input, the bump, its pull request, both pull requests' sibling sections, the second merge, the order's status comment done with the release, the order's issue closed with its comment, and `foedrum status 1`.
- **A good run** has every life ended on its condition, two pull requests whose sibling sections name each other, the order's issue closed, and every CLI call succeeded. A life that fails, a CLI call that fails or a git call the shell makes that fails stops the walk there, and the report names it. An integration test (`test/integration/demo-ladder.test.ts`) runs it once.

## Consequences
- M2's exit test runs offline on any machine `npm run check` runs on, with no gh, GitHub, `claude` or network, in about a minute and a half.
- A change to the plan's application, the intake's ready set, the release reader, the sibling sections or the close shows in the ladder, and a change that breaks it fails its integration test on every leg of CI.
- The fake code host's merges and releases have a second user beside the tests: a change to them must keep the ladder working.
- The ladder's scratch folder is the default demo's (`.foedrum/tmp/demo`), removed at the start of each run, so a ladder run removes the last default run's folder and the other way round.

## Alternatives considered
- **Steps 13 onwards of the default demo.** It would double the default demo's length for every run, and the maintainer chose a part of its own.
- **One life of the Cellar for the whole ladder, with the merges made from inside it.** The life would need a seam in serve's wait that merges and releases, which is no part of serve; the shell between lives plays the person and the CI as the default demo's shell plays the person's label.
- **A Brewmaster, and a bump, with fixed answers.** They would pass whatever the folder of checkouts and the `release` input held, and the ladder would show nothing of ADR 0291 or ADR 0301.
- **An Innkeeper choosing `mash`.** The default demo already shows it (ADR 0283); the label shows the other half of routing, a person's choice the engine keeps.
