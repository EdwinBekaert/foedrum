# 0103. Out docs reach the state branch through the store

Date: 2026-10-21 · Status: Accepted · Amends [0024](0024-state-branch-layout-outbox-and-divergence.md) (how an out doc gets into the commit of its event) and [0081](0081-the-cleanup-ignores-the-steps-own-out-doc.md) (an out doc's body no longer goes with the worktree)

## Context
[ADR 0011](0011-state-in-the-brewery-repository.md) puts each batch's out docs on the state branch next to its `events.jsonl`. [ADR 0024](0024-state-branch-layout-outbox-and-divergence.md) gave them a path, `batches/<batchId>/<stepId>-<attempt>.md` (`outDocPath`), and an order: the engine writes the out doc into the state worktree before it appends the event that refers to it, so that a crash leaves at worst a doc without its event, never an event without its doc. The shell got a `writeOutDoc` for that, and nothing ever called it. Since [ADR 0081](0081-the-cleanup-ignores-the-steps-own-out-doc.md) the cleanup deletes an ended batch's worktrees together with their untracked out docs, so an out doc's body is gone once its batch ends. Only its frontmatter is left, as the outcome in `step.finished` (#215).

Writing into the state worktree from where an attempt ends does not keep ADR 0024's promise. The driver appends `step.finished` in a SQLite transaction, and the supervisor's tick flushes later, so a file written in the worktree before that transaction is on no commit until a flush happens to run. Any flush between the two commits the doc without its event. The file is also outside the store's atomicity, and the in-memory state branch of the chaos tests, which follows the store, could not see it. The out doc is also model output: it can be large, it can hold anything, and nothing may read it as an instruction.

## Decision
- **The text goes through the store.** The runner ends an attempt with the out doc's text as it read it, valid or not (`AttemptEnd.outDoc`; the claude runner, and the fake runner of the tests). `keepOutDocs` (`src/engine/kept-out-docs.ts`), around the step runner in `foedrum serve`, keeps it in the store in its own transaction (`keepOutDoc`, table `out_docs`, schema version 4) before the attempt's end settles. The driver records `step.finished` only after that, so a store that has the event has the doc. The end goes on without the text, so no notice or command carries it. A doc that cannot be kept is reported in one line, and the attempt ends as its runner said.
- **The flush writes it next to its event.** The flush reads the pending events first, then the kept out docs, so every doc whose `step.finished` is pending is in the plan. `planFlush` writes the log files and then each kept doc at its `outDocPath`, in the same commit. The transaction that moves the pushed-through marker also forgets the docs it pushed (`forgetOutDocs`). `writeOutDoc` is removed.
- **A kill anywhere leaves both, or the doc is written again.** A kill after the doc was kept but before `step.finished`: the attempt is lost, the next driver records its `step.finished`, and the doc goes with it. A kill before the push, or after it but before the marker: the store still keeps the doc, and the next start's flush writes it again with the same text. The doc of an attempt that never gets a `step.finished` (Stuck or a cancel abandoned it, and its finish was refused) is written by the next flush that has any pending event, and then forgotten.
- **Stored, never followed.** The text is written byte for byte, at a path built from the attempt's ids only (each a `PathSafeId`), with `* -text` keeping git from converting it. It is never a log file (`isLogPath`), so a rebuild never reads it. Nothing reads it back into a prompt, a command or a decision.
- **A size limit, failing closed.** The state branch keeps at most 256 KiB of an out doc's text (`MAX_BRANCH_OUT_DOC_BYTES`), counted in UTF-8 bytes. Past it, a fixed line takes the text's place, naming the step, the attempt, its size and the limit, and none of the text. The runner's reader already refuses out docs over 1 MiB. The branch is cloned with all of its history, and a plan or a review is a few kilobytes, so the branch's limit is lower.
- **`foedrum replay` points at them.** Once an attempt of the batch finished, its state names `batches/<batch>/<step>-<attempt>.md` on the state branch. It does not say which attempts have one, since only the branch knows.

## Consequences
- An out doc's body outlives its worktree, on the state branch, in the commit of its `step.finished`, and with the batch's history on any machine.
- A doc can reach the branch one flush before its event, when a flush runs between keeping the doc and recording the event. That is the order ADR 0024 allows: a doc without its event, never an event without its doc.
- The store holds an out doc's text, up to the reader's 1 MiB, from the attempt's end until the push. A rebuilt store keeps none, and needs none: those that were pushed are on the branch.
- The text is not filtered for secrets, as the pull request body and the status comment are ([ADR 0088](0088-out-doc-text-that-looks-like-a-secret-is-left-out-of-the-pull-request-and-the-status-comment.md)). The state branch is in the Brewery repository, which already holds the frontmatter of every out doc in `step.finished`, and the brewer wrote the text in a worktree of a repository the Brewery works in. A filter would replace whole documents on a false match and lose what the branch is for.
- A check step's report is not an out doc and does not go to the branch.

## Alternatives considered
- **Call `writeOutDoc` where the attempt ends, as ADR 0024 planned:** no store change, but the file sits outside the store's transactions. A flush between the write and the event commits the doc first, and the chaos tests' state branch cannot see it.
- **Keep the doc in the driver's finish transaction, with `step.finished`:** atomic, but it changes the driver's end loop, where another change is under way (#289), for a gain the order of two transactions already gives.
- **Put the text in `step.finished`:** one write, but every event log, fold and `foedrum replay` would carry whole documents, and the out doc would be a line of JSON, not a file to read on the branch.
- **Refuse the attempt when its out doc is over the branch's limit:** fails closed too, but turns a storage limit into an attempt that failed, and the runner already refuses what it cannot read.
