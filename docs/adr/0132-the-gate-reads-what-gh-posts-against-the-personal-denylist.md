# 0132. The gate reads what gh posts against the personal denylist

Date: 2026-10-22 · Status: Accepted · Amends [0114](0114-the-gate-blocks-words-on-a-personal-denylist-in-what-leaves-the-machine.md) (what gh sends is scanned now; a `gh api` field from a file and `--input` from a file are read, not blocked)

## Context
[ADR 0114](0114-the-gate-blocks-words-on-a-personal-denylist-in-what-leaves-the-machine.md) gave the local gate a personal denylist and scanned what `git push` sends. It left the other way text leaves the machine for a change of its own (#345): what `gh` posts. Since #48 pull request bodies, comments and issues go out without anyone reading them first, the review skill posts its summary with `gh pr comment --body-file` and files issues with `gh api … --input <draft>` ([ADR 0094](0094-reviewers-show-their-evidence-and-mark-pre-existing-defects.md)), and the repository is public. The gate already reads every `gh` call, also inside other shells ([ADR 0045](0045-the-local-gate-reads-commands-as-the-shells-would.md)), and blocks the `gh api` merges it cannot read ([ADR 0108](0108-the-gate-blocks-merges-through-gh-api.md)).

## Decision
- **What is read.** While a list is set, before anything else the gate runs for the command (the push scan, `npm run check`, the `gh pr ready` lookup), it reads, in every command it reads (ADR 0045: `bash -c`, `pwsh -Command`, `eval`, `$( )` and the rest):
  - `gh pr create|new|edit|comment` and `gh issue create|new|edit|comment`: `-t`/`--title`, `-b`/`--body` and `-F`/`--body-file`, as gh's flag parser takes them: the next word, after `=` (`--body=…`, `-t=…`), joined to the short option (`-tTitle`), or after other short options in one group (`-dt Title`). The other options of theirs that take a value (gh's manual: `-a`, `-B`, `-H`, `-l`, `-m`, `-p`, `-r`, `-R`, `-T` and the long ones) are skipped with their value, so a value is never read as an option. Every one given is read, though gh keeps the last ([gh pr create](https://cli.github.com/manual/gh_pr_create), [gh pr edit](https://cli.github.com/manual/gh_pr_edit), [gh pr comment](https://cli.github.com/manual/gh_pr_comment), [gh issue create](https://cli.github.com/manual/gh_issue_create), [gh issue edit](https://cli.github.com/manual/gh_issue_edit), [gh issue comment](https://cli.github.com/manual/gh_issue_comment): "`-F, --body-file <file>` Read body text from file (use "-" to read from standard input)").
  - `gh api`: the `title` and `body` fields, given with `-f`/`--raw-field` (as it is, an `@` too) or `-F`/`--field` (after `@`, read from that file; `@-` is standard input), also joined (`-Fbody=…`, `--field=body=…`) or after `-i` in one group (`-iF body=…`), and `--input <file>`, the request body ([gh api](https://cli.github.com/manual/gh_api): "if the value starts with `@`, the rest of the value is interpreted as a filename to read the value from. Pass `-` to read from standard input"; "`--input <file>` The file to use as body for the HTTP request (use "-" to read from standard input)"). A field whose name is computed at run time may be either, so it counts as one.
- **How a file is read.** A body file, an `@file` field and an `--input` file are read where gh runs: the hook's working directory, then each directory the command changes into before it (ADR 0104's reading, `~` and Git Bash's `/c/…` too). The file's lines are scanned; an `--input` file that is a JSON object is read by its fields, keys and strings decoded as GitHub reads them, so a letter or line break written as a JSON escape does not hide a word. Only a regular file of at most 256 KiB (four times GitHub's 65,536 characters of a body) is read (`ghFileReader`): standard input given as a path (`/dev/stdin`, `/dev/fd/0`), a FIFO or a device would empty or stall the gate, which has already read its own standard input, so it counts as a file the gate cannot read. On Windows a network, device or drive-less path is refused before anything touches it, as for a directory (ADR 0104), so a UNC share is never opened; so is a POSIX path other than Git Bash's `/c/…`, which Git Bash maps elsewhere for `gh.exe` (`/tmp/…`). Nothing in the file runs, so a regular file outside the project may be read.
- **What is blocked because the gate cannot read it**, while a list is set, with one line that names the command and the option and says to give the text inline or in a file the gate can read: a title, body or field computed at run time (`-b "$body"`, `--title "$(cat t)"`, `-F "body=$text"`, `-f "$pair"`); standard input (`-F -`, `--body-file -`, `-F body=@-`, `--input -`); `--input` or a body file named by a variable; a body file in a directory computed at run time (`cd "$d" && gh … -F body.md`); and a file it cannot read or will not open (with the error, unless the path or the error, which names the resolved path, holds a word).
- **What a hit prints.** As for a push (ADR 0114), one line naming up to ten places and counting the rest, never the word: `gh pr create --title line 1`, `gh pr comment --body-file .foedrum/tmp/345/body.md:2`, `gh api field body line 1`, `gh api field body body.md:2`, `gh api --input draft.json, body line 2`. A file whose path holds a word is named `a file whose path holds a denied word`, and a JSON field whose name holds one `a field whose name holds a denied word`.
- **No list, no change.** Without a list, or with one of only comments, nothing is read and nothing more is blocked; the scan's modules load only for a command with a gh text in it. A list that cannot be read blocks every gh text, as it blocks every push.
- **The core is `scripts/denylist/core.ts`** (`textPlaces`, `filePlaces`), the shell `scripts/denylist.ts` (`textRefusal`), and the reading of the command `scripts/precheck.ts`, which collects each text as given, in a file, or unreadable, and has `forbiddenReason` take the scan. Tests inject the list and the files, with fixture words only. `foedrum doctor` says the gate blocks the words in what `git push` and `gh` send.

## Consequences
- The review skill's `gh pr comment --body-file` and its `gh api … --input <draft>` (ADR 0094) keep working with a list set, and are read.
- An inline body over several lines is also read as commands by the gate, as before (ADR 0045), so a body that quotes `gh … --input -` on a line of its own blocks: give such a body in a file.
- Not read yet: other gh commands that post text (`gh pr review -b`, `gh pr close -c`, `gh issue close -c`, `gh release create --notes`, `gh gist create`), `gh api` fields other than `title` and `body` (such as a GraphQL `query`, which may carry a mutation's text), `--template`'s text (a file of the repository, already pushed), `--fill` (commit messages, which the push scan read), and what `--editor` and `--web` let a person type. A later change can add them to the same tables.
- A gh whose name or group is computed at run time (`$gh pr comment …`) is not read for texts: the gate cannot tell which command it is.

## Alternatives considered
- **Block `gh api --input` and `-F field=@file` while a list is set**, as ADR 0114 planned: the review skill files every issue with `--input`, so a list would stop it, while the file is as readable as a `--body-file`.
- **Scan every `gh api` field:** a search or a GraphQL query would block on the word the user looks for, and the issue asked for the title and body; left for later with the other gh texts.
- **Scan inside gh** (a wrapper on the `PATH`): the gate already reads every call a session makes, and a wrapper would need installing outside the repository.
