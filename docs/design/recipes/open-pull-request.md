# The openPullRequest action

**The openPullRequest action** ([ADR 0071](../../adr/0071-the-openpullrequest-action-two-effects-of-the-batch.md)) loads as a recipe's last step.
The driver runs its attempt itself, never on the runner, with no lease and no worktree: two effects of the batch through the ledger, the push of the task tree, resolved in the clone, to `foedrum/<brewery>/<batch>/<owner>.<name>` (never by force), then the pull request from that branch into the base, each found on the code host before it is applied (the remote branch at that commit; a pull request from that branch by the Brewery's own login), so a kill on either side of either never pushes twice or opens two pull requests (I4).
The attempt ends once both are recorded, and `decide` puts the batch on tap only with the pull request the ledger recorded, unless the action's `when` skipped it.
The title is the order's, and the body has one layout for every repository ([ADR 0167](../../adr/0167-a-brewed-pull-request-follows-one-layout-and-opens-as-a-draft-unless-every-taster-approves.md)).
It starts with `## How it works`, holding the sections the latest `pullRequest` out doc wrote, each when it is there: the default Cellarman's `howItWorks` with its picture, a before/after table the engine renders from `beforeAfter`, and `**See it:**`.
Then `## How this was brewed` names the order and the recipe, says whether a person reviews the pull request before it is marked ready, and lists the batch's finished attempts in the order they started, in the engine's words, a failed one's reason in a code span (at most 50 rows).
Then what each step reported, in a fenced block folded in `<details>`, where nothing links, mentions or closes: its summary and assumptions, and a Taster's verdict and findings ([ADR 0161](../../adr/0161-lens-steps-run-a-taster-whose-findings-are-advisory-unless-the-step-blocks.md)).
It ends with `Closes <owner/name>#<n>`, which the engine writes itself.
The sections are model text outside a fence, so the engine takes out the `@` of each mention, and each closing keyword before an issue reference, escapes the `&` of each character reference as `&amp;` (`unlinked`), escapes a table cell's pipes and backslashes, closes a fence `howItWorks` leaves open and starts no HTML block from it, and leaves out a section that grows past its room once made safe.
A summary, an assumption, a finding, a section, a cell or a reason that looks like a secret is left out, a fixed line naming its step in its place ([ADR 0088](../../adr/0088-out-doc-text-that-looks-like-a-secret-is-left-out-of-the-pull-request-and-the-status-comment.md)); the reports get what the rest leaves of GitHub's 65,536 characters, at most 25,000 (`src/engine/pull-request.ts`, `pull-request-actions.ts`, `src/workspace/branch-push-git.ts`, `src/github/pull-requests.ts`).
The pull request opens ready for review only when a Taster tasted the change and every Taster approved; otherwise as a draft, and when GitHub refuses a draft for the repository it is asked again once without one, with the same body.
The engine never marks a pull request ready: a person does.
Before it pushes, the push scans every commit from the base to the task tree's commit in the clone (a merge against its last parent, the base it brought in, ADR 0164), its messages, headers (author, committer, a signature, an encoding) and added lines through `findSecrets`, with git reading the objects as committed (no replace ref, graft, shallow file, textconv or diff driver of the clone); a finding, a binary file or more than 4 MiB of changes records the refusal instead, each commit, place and kind but never the text, and the batch goes Stuck on its environment ([ADR 0079](../../adr/0079-the-push-scans-the-batch-s-commits-for-secrets.md)).
The base the push compares with and scans from is the remote's as it is now, not the clone's `origin/<base>`: fetched from `https://github.com/<repo>.git` in a git directory of Foedrum's own, one per fetch, whose objects are the clone's, so none of the clone's configuration, which brewers can write, takes part ([ADR 0090](../../adr/0090-the-push-fetches-the-base-in-a-git-directory-of-its-own.md)).
That directory is `<work root>/<owner>.<name>/git-dirs/<uuid>.git`, removed after the fetch; in a partial clone the fetch runs blobless, with that URL as the directory's promisor remote (`src/workspace/clone-git.ts`).
The push, which names the commit by its sha and sends that one ref only (no tags, no submodules), and its `ls-remote` run in the clone, by its `origin`, and every engine call in the clone runs with no hook or fsmonitor of the clone's ([ADR 0137](../../adr/0137-the-push-its-lookup-and-the-worktree-fetch-run-in-the-clone-again.md), which amends [ADR 0096](../../adr/0096-the-engine-s-git-reaches-the-remote-outside-the-clone-s-configuration.md)).
Before the recipe's last check step that expects to pass (Nip's `green`), the driver merges the base into that check attempt's worktree, so the checks read the code the pull request will hold ([ADR 0164](../../adr/0164-a-batch-merges-its-base-before-its-last-check.md)).
The base is the remote's as it is now, fetched by the push's own `baseTip`, and git reads the worktree through its record under the clone, never by discovery; the merge is a commit of its own (`Merge <base> before <step>`), an effect of the attempt in the ledger (`["<batch>","<step>",<attempt>,"merge_base"]`), found after a kill as a HEAD that merges the attempt's start, so it never merges twice (`src/engine/base-merge.ts`, `src/workspace/base-merge-git.ts`).
A base the start already holds merges nothing; a conflict is aborted, and the batch goes Stuck, blocked on a divergence: `conflicts with <base> in <files>`.
Main moving between that check and the push is left to CI.
