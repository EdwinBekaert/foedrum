# The openPullRequest action

**The openPullRequest action** ([ADR 0071](../../adr/0071-the-openpullrequest-action-two-effects-of-the-batch.md)) loads as a recipe's last step.
The driver runs its attempt itself, never on the runner, with no lease and no worktree: two effects of the batch through the ledger, the push of the task tree, resolved in the clone, to `foedrum/<brewery>/<batch>/<owner>.<name>` (never by force), then the pull request from that branch into the base, each found on the code host before it is applied (the remote branch at that commit; a pull request from that branch by the Brewery's own login), so a kill on either side of either never pushes twice or opens two pull requests (I4).
The attempt ends once both are recorded, and `decide` puts the batch on tap only with the pull request the ledger recorded, unless the action's `when` skipped it.
After its `onPullRequestFail` route sent the batch back ([open pull requests](../intake/open-pull-requests.md), [ADR 0219](../../adr/0219-a-failing-check-on-an-open-pull-request-sends-its-batch-back-to-a-fix-step.md)), the action pushes the round's task tree under a key of its own, `["<batch>","push.<n>"]`, only onto the commit the round before pushed: it reads the remote tip first and records `moved` or `gone`, pushing nothing, when someone else pushed to the branch or deleted it; it opens nothing again, pushes nothing once the pull request ended, and gets three attempts in each round.
The title is the order's, and the body has one layout for every repository ([ADR 0167](../../adr/0167-a-brewed-pull-request-follows-one-layout-and-opens-as-a-draft-unless-every-taster-approves.md)).
It starts with `## How it works`, holding the sections the latest `pullRequest` out doc wrote, each when it is there: the default Cellarman's `howItWorks` with its picture, a before/after table the engine renders from `beforeAfter`, and `**See it:**`.
Then `## How this was brewed` names the order and the recipe, says whether a person reviews the pull request before it is marked ready, and lists the batch's finished attempts in the order they started, each as a code span (`` `gauge #1` ``) so it links no issue, in the engine's words, a failed one's reason in a code span (at most 50 rows).
Then what each step reported, in a fenced block folded in `<details>`, where nothing links, mentions or closes: its summary and assumptions, a Taster's verdict and findings ([ADR 0161](../../adr/0161-lens-steps-run-a-taster-whose-findings-are-advisory-unless-the-step-blocks.md)) and its risk left, each item on a `risk left:` line ([ADR 0214](../../adr/0214-a-taster-s-out-doc-says-what-risk-is-left.md)), a Gauger's new tests and regression tests ([ADR 0170](../../adr/0170-the-red-proof-accepts-the-regression-tests-a-gauger-names.md)), a Finer's changes or why it had none ([ADR 0166](../../adr/0166-the-finer-simplifies-a-batch-s-change-before-green.md)), and the findings any succeeded attempt of the step marked `pre-existing` in its `dispositions`, each place and why once, as `to file` for the reviewer to file ([ADR 0191](../../adr/0191-the-step-a-findings-route-goes-back-to-records-a-disposition-for-each-finding.md)).
It ends with `Closes <owner/name>#<n>`, which the engine writes itself.
The sections are model text outside a fence, so the engine takes out the `@` of each mention, and each closing keyword before an issue reference, escapes the `&` of each character reference as `&amp;` (`unlinked`), escapes a table cell's pipes and backslashes, closes a fence `howItWorks` leaves open, starts no HTML block from it and leaves it out when a fence starts inside a list, a quote or an indent, and leaves out a section that grows past its room once made safe.
What an inline code span closed on its line holds is kept as written, since GitHub acts on nothing in one; a span left open, on a line with a `<`, a `]` or a `$`, or holding a `|` or after one that does is read as text, and so are the lines after it until a blank line ([ADR 0184](../../adr/0184-a-brewed-pull-request-keeps-what-a-code-span-holds-and-writes-each-attempt-as-one.md)).
Once its fences are paired, each Mermaid block of `howItWorks` has every node label, edge label and subgraph title quoted that is not yet (an edge's text between its dashes moved between pipes, `-->|"x"|`), its `#` written as `#35;` and its `"` as `#quot;`, in a `flowchart` or `graph`, and the `;` and `#` of a message, note, block or alias written as `#59;` and `#35;` in a `sequenceDiagram`; a block of another kind, or with a line it cannot read, is left out whole with `[left out: a diagram Foedrum could not check]` (`quotedDiagrams`, [ADR 0180](../../adr/0180-a-brewed-pull-request-quotes-its-mermaid-labels-or-leaves-the-diagram-out.md)).
A summary, an assumption, a finding, an item of a Taster's risk left, a section, a cell or a reason that looks like a secret is left out, a fixed line naming its step in its place ([ADR 0088](../../adr/0088-out-doc-text-that-looks-like-a-secret-is-left-out-of-the-pull-request-and-the-status-comment.md)); the reports get what the rest leaves of GitHub's 65,536 characters, at most 25,000 (`src/engine/pull-request.ts`, `pull-request-actions.ts`, `src/workspace/branch-push-git.ts`, `src/github/pull-requests.ts`).
The pull request opens ready for review only when a Taster tasted the change, every Taster approved and the body has its How it works; otherwise as a draft (a body without one says `No How it works: the Cellarman wrote none.`), and when GitHub refuses a draft for the repository it is asked again once without one, with the same body.
The engine never marks a pull request ready: a person does.
Before it pushes, the push scans every commit from the base to the task tree's commit in the clone (a merge against its last parent, the base it brought in, ADR 0164), its messages, headers (author, committer, a signature, an encoding) and added lines through `findSecrets`, with git reading the objects as committed (no replace ref, graft, shallow file, textconv or diff driver of the clone); a finding, a binary file or more than 4 MiB of changes records the refusal instead, each commit, place and kind but never the text, and the batch goes Stuck on its environment ([ADR 0079](../../adr/0079-the-push-scans-the-batch-s-commits-for-secrets.md)).
The same scan already ran on each committing brewer's `done` attempt, so its retry could write the text another way; the push's scan stays the last line, for every commit it sends ([ADR 0187](../../adr/0187-a-committing-brewer-s-attempt-is-scanned-for-secrets-when-it-ends-done.md)).
When the repository names `sensitivePaths`, a push that goes, or one found on the remote, records in its ledger result the files of the change that match them, read as committed as the scan reads them, which the status comment names ([configuration](configuration.md), [ADR 0201](../../adr/0201-a-repository-names-its-sensitive-paths-and-a-batch-that-touches-one-says-so.md)).
The base the push compares with and scans from is the remote's as it is now, not the clone's `origin/<base>`: fetched from `https://github.com/<repo>.git` in a git directory of Foedrum's own, one per fetch, whose objects are the clone's, so none of the clone's configuration, which brewers can write, takes part ([ADR 0090](../../adr/0090-the-push-fetches-the-base-in-a-git-directory-of-its-own.md)).
That directory is `<work root>/<owner>.<name>/git-dirs/<uuid>.git`, removed after the fetch; in a partial clone the fetch runs blobless, with that URL as the directory's promisor remote (`src/workspace/clone-git.ts`).
The push, which names the commit by its sha and sends that one ref only (no tags, no submodules), and its `ls-remote` run in the clone, by its `origin`, and every engine call in the clone runs with no hook or fsmonitor of the clone's ([ADR 0137](../../adr/0137-the-push-its-lookup-and-the-worktree-fetch-run-in-the-clone-again.md), which amends [ADR 0096](../../adr/0096-the-engine-s-git-reaches-the-remote-outside-the-clone-s-configuration.md)).
Before the recipe's last check step that expects to pass (Nip's `green`), the driver merges the base into that check attempt's worktree, so the checks read the code the pull request will hold ([ADR 0164](../../adr/0164-a-batch-merges-its-base-before-its-last-check.md)).
So does the attempt an `onPullRequestFail` route scheduled for a failing check on the merged tree, and a retry of it, before its brewer runs (`routedMerge`, [ADR 0226](../../adr/0226-a-failing-check-on-the-merged-tree-sends-its-batch-back-to-the-fix-step.md)).
The base is the remote's as it is now, fetched by the push's own `baseTip`, and git reads the worktree through its record under the clone, never by discovery; the merge is a commit of its own (`Merge <base> before <step>`), an effect of the attempt in the ledger (`["<batch>","<step>",<attempt>,"merge_base"]`), found after a kill as a HEAD that merges the attempt's start, so it never merges twice (`src/engine/base-merge.ts`, `src/workspace/base-merge-git.ts`).
A base the start already holds merges nothing; a conflict is aborted, and the batch goes Stuck, blocked on a divergence: `conflicts with <base> in <files>`.
Main moving between that check and the push is left to CI.
