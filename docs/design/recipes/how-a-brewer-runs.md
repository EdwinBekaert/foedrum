# How a brewer runs

A brewer compiles to one `claude` CLI invocation plus a generated per-attempt settings file, verified against `claude` 2.1.301 ([ADR 0042](../../adr/0042-the-claude-command-line-and-stream-contract.md)):

```
claude --print --verbose --output-format stream-json
       --permission-mode dontAsk --permission-prompts none
       --model <model id> --effort <effort> --max-turns <maxTurns>
       --settings <per-attempt settings file: allow/deny, sandbox>
       --setting-sources ""                           # no user, project or local settings
       --tools <the built-in tools named in tools.allow>
       --disable-slash-commands                       # unless skills (not supported yet, ADR 0046)
       --strict-mcp-config [--mcp-config <file>]      # always; mcp not supported yet (ADR 0046)
       --safe-mode                                    # context: lean
       --session-id <new uuid> | --resume <session id>
       --append-system-prompt-file <the attempt's system prompt file: the engine's fixed rules>
                                                      # the prompt on stdin, no prompt argument
```

- The settings file is written from a strict schema (`AttemptSettings`): `claude` silently drops a settings file that fails its validation, deny rules included.
  It always denies `AskUserQuestion` and `git push` in each shell the brewer has, and refuses an allow rule that reaches git with no fixed subcommand, the toolchain's included (ADR 0062).
  A bare tool name in `deny` removes the tool, a scoped rule denies matching calls.
- File tools reach only the worktree, `claude`'s working directory: the settings file has a brewer's bare `Read`, `Grep` or `Glob` as `Read(./**)`, and a bare `Edit`, `Write`, `MultiEdit` or `NotebookEdit` as `Edit(./**)`, since Claude Code checks file permissions against `Read` and `Edit` path rules only.
  `--tools` still lists the tools the brewer named.
  The schema refuses a bare file-tool allow rule, and a path rule for `Write`, `MultiEdit`, `NotebookEdit` or `Glob`, which Claude Code never consults, naming the `Edit(…)` or `Read(…)` to write instead.
  A brewer file with such a path rule (`Write(brew.md)`: write `Edit(brew.md)`) does not load; a repository toolchain rule with one fails each attempt as `the brewer could not start`.
  A test against the installed `claude` (opt-in) shows `Write`, `Edit` and `Read` denied outside the worktree and through a junction or link, and `Write` and `Edit` through `..` ([ADR 0093](../../adr/0093-brewers-file-tool-rules-are-read-and-edit-rules-scoped-to-the-worktree.md)).
- `--setting-sources ""` makes the runner's file the only one: the user's `~/.claude/settings.json` could otherwise widen the allowlist and add variables, and the repository's settings are untrusted.
  A test against the installed `claude` proves it with a throwaway user settings file ([ADR 0046](../../adr/0046-only-the-runners-settings-the-init-check-and-a-line-by-line-stream.md)).
- The engine's fixed rules for the attempt, which no input changes, go in a system prompt file beside the settings file, `<workRoot>/attempt-settings/<batch>/<step>/<attempt>.system.md`, appended to claude's own with `--append-system-prompt-file` ([ADR 0183](../../adr/0183-the-engine-s-fixed-rules-for-a-brewer-go-in-an-appended-system-prompt.md)).
  `attemptSystemPrompt` words them from the brewer and the attempt's allow rules alone, the same on every platform: the commands of its `Bash` rules (its own, then those `git.commit` grants, then the repository's, once each, without the trailing star; none for PowerShell rules, which have no tool here, or when one rule allows any program), that every other command is refused, git's read-only ones too (`git log`, `git diff`, `git show`, those its rules do not allow), and that a command joined to a refused one is refused whole; with a shell, to write files with the Edit or Write tool it has, never through the shell; for `git.commit: true`, `git commit -m "<subject>" -m "<body>"`; not to push; and that a denial stops that command only (#222, ADR 0085).
  In an attempt's worktree of a bare clone claude allows no read-only git command without a rule, unlike in a plain repository, so a `git add … && git commit … && git log` was denied whole on nearly every brew; no line break or `&&` is refused, and the rules do not say so.
  The brewer's instructions, the out doc contract and the inputs stay in the user prompt (ADR 0041).
  A resumed session keeps the system prompt claude recorded on its first request until it is compacted; the file is passed again for the requests after that.
- Before it reads anything else, the runner checks the `system/init` event against what it asked for: the session id, exactly the tools of `--tools`, permission mode `dontAsk`, and no MCP server, skill or slash command.
  Other `system` events may come first.
  A mismatch ends the attempt as `blocked` + `environment`, never retried (ADR 0046).
- The runner reads `system/init` (session id, model, permission mode, tools, CLI version), `assistant` and `user` messages (tool calls and results), `system/permission_denied` (one denial each, counted live) and the final `result` (`is_error`, `num_turns`, `terminal_reason`, `usage`, and for the receipt `duration_ms`, `duration_api_ms` and `modelUsage`'s tokens, never its cost, [ADR 0181](../../adr/0181-receipts-show-no-cost.md)); it ignores every other event type.
  `is_error`, not `subtype`, says whether the run failed; when the stream ends with a `result`, the exit code is 0 exactly when `is_error` is false.
  A run with no `result` is a crash, except one that wrote no line at all and exited with a code from 1 to 255: when its stderr names a lasting refusal (an unknown option, no login) it is the environment, and otherwise the runner starts `claude` once more after 5 s and makes a second such failure the environment ([ADR 0048](../../adr/0048-retried-pre-stream-failures-commit-detection-and-out-doc-identity.md)).
  Captured streams for the parser: `test/fixtures/claude-stream/`.
- Each attempt whose stream the runner read ends with a **receipt** of what it took: its durations, turns and tokens per model, never a cost (claude reports list prices, not what a user pays), the file-tool calls that came back without an error, the tool errors apart from denied calls, and the denials per tool family with up to five command prefixes a shell was refused (its first one or two plain words, none that looks like a secret); a resumed run's receipt says so, since claude then reports its session's API duration and tokens per model; a run with no `result` gets one of what was seen, marked incomplete, an attempt whose claude never started none, and the driver records it on `step.finished` ([ADR 0172](../../adr/0172-an-attempt-s-receipt-from-its-stream.md), [ADR 0181](../../adr/0181-receipts-show-no-cost.md)).
- The driver chooses the session id and records it in `step.started` as `session: { id, worktree }` before claude starts; the attempt's plan passes it to claude with `--session-id`, or, for a retry or an answered attempt that resumes, records the session it continues (`resumes`) and the plan passes it with `--resume` ([ADR 0117](../../adr/0117-a-retry-resumes-the-session-of-the-attempt-before-it-in-that-attempt-s-worktree.md), [ADR 0118](../../adr/0118-retrymode-resume-loads-and-an-answer-resumes-the-session-that-asked.md)).
  A retry after a turn overrun resumes the session whatever the brewer's `retryMode`, told `The run before this one ran out of turns. Finish what is left of the step, write <out doc> as your instructions say, and end.`, with the full `maxTurns` again; when `resumeOf` says fresh or the worktree cannot be recreated, it fails at once as not retryable, since a fresh start would meet the same budget, except after a resumed run that found no session, whose retry follows `retryMode`.
  It keeps the out doc the run before wrote, also when `foedrum resume` takes the batch over and opens the session ([ADR 0251](../../adr/0251-foedrum-resume-s-runner-keeps-an-overrun-s-out-doc-and-opens-no-session-after-a-stop.md)), which every other resume removes first ([ADR 0118](../../adr/0118-retrymode-resume-loads-and-an-answer-resumes-the-session-that-asked.md)): the runner kept a copy beside the attempt's settings file (`<attempt>.out.md`) as the overrun ended, and writes it back into a recreated worktree that has none, as a new file inside the worktree only, skipped when the worktree lacks the out doc's folder and stopping the attempt before claude starts when it cannot be written there; the status comment says so ([on GitHub](../humans/github.md), [ADR 0175](../../adr/0175-a-turn-overrun-is-retried-by-resuming-its-session-and-keeps-its-out-doc.md)).
  Any other retry after a failed attempt is told why: that attempt's reason as a tagged input, `The attempt before this one, <step>#<n>, failed: <reason>`, left out when it looks like a secret and held to 64 KiB, as the one input of a resumed retry and the last of a fresh one (`retryInputOf`, [ADR 0248](../../adr/0248-a-retry-is-told-why-the-attempt-before-it-failed.md)).
  What claude's init reports, its version and model, goes on `step.finished` as `claude` ([ADR 0047](../../adr/0047-the-claude-brewer-runner-its-stream-endings-and-progress.md), [ADR 0116](../../adr/0116-the-driver-records-each-attempt-s-session-and-claude-s-report-goes-on-step-finished.md)).
- Before claude starts, the attempt of a brewer whose allow list has a `Bash` or `PowerShell` rule (its own or its repository's `tools`) runs its repository's `setup` (`npm ci`) in its worktree, through the check sandbox with the network kept (native Windows: no sandbox, and the reading says `unsandboxed`), in the checks' environment, killed at its `timeout` or 10 s before the attempt's deadline; its reading goes on `step.finished` as a check step's does.
  A setup that does not pass ends the attempt `blocked` on its environment with that reading, and claude never starts; a stop during it cancels the attempt.
  An attempt that resumes a session runs it too, since the driver may have added its worktree again; so does the foreground session `foedrum resume` continues, before claude opens, and a stop reaches that setup.
  While it runs, the attempt reports progress, and claude's stall clock starts when it ends.
  A brewer without a shell, such as a read-only Taster, runs none: it could not use the install.
  So the brewer finds the repository's dependencies, and can run its format, lint, typecheck and tests when `tools` allows them ([ADR 0163](../../adr/0163-a-repository-s-setup-runs-before-a-brewer-attempt.md)).
- The engine owns the child process, reads the event stream live, line by line with a limit per line and none in total (`streamProcess`, ADR 0046), keeps only the facts it needs (progress, tool calls, permission denials, usage, and the receipt, ADR 0172) and kills the process tree on deadline, stall or cancel.

- A setup that does not pass decides the ending before claude starts (above). Otherwise how the attempt ends follows from what the runner saw, by one rule shared with the fake runner (`settleAttempt`, [ADR 0028](../../adr/0028-brewer-runner-outcomes-environment-and-test-first.md)): a session that is not what was asked, or a failure before the model replied (an unknown model, no login, refused arguments) → `blocked` + `environment`; a resume that finds no session to resume → a retryable failure, whose retry starts a fresh session ([ADR 0117](../../adr/0117-a-retry-resumes-the-session-of-the-attempt-before-it-in-that-attempt-s-worktree.md)); an error `result` that says a usage window ran out (`You've hit your session limit · resets 3:45pm`, and the weekly, Opus and Sonnet forms) → `blocked` + `environment` with the limit and its reset as `usageLimit` ([ADR 0091](../../adr/0091-a-run-out-usage-window-blocks-on-the-environment.md)), which the engine does not count and answers by holding the brewers that limit's window holds until it reopens: every brewer for a session or weekly limit, those on its family and those whose family cannot be told for an Opus or Sonnet limit ([the usage window](../engine/usage-window.md)); an error `result` that names a spend limit (`You've hit your monthly spend limit · …`, the individual, org's, channel's, team's and individual usage forms) or says `Credit balance is too low` → `blocked` + `environment`, saying no request goes through until the limit is raised or credits are added ([ADR 0129](../../adr/0129-a-spend-limit-or-a-too-low-credit-balance-blocks-on-the-environment.md)); a process that could not start → a failure; `maxDenials` reached → `blocked` + `environment`, naming the denied tools; `maxTurns` passed → a failure that is not retried, unless claude's init came and the driver can resume the session (a claude step whose worktree manager recreates worktrees, the limits' `resumable`): then a retryable failure marked `overran: "turns"`, whose retry resumes the session ([ADR 0175](../../adr/0175-a-turn-overrun-is-retried-by-resuming-its-session-and-keeps-its-out-doc.md)); a stop within the limits → `cancelled`; a crash, output past the runner's limits, an error the `result` reported, garbage in the stream, or a missing, oversized or invalid out doc → a retryable failure, even next to a valid out doc; otherwise the out doc's status ([ADR 0047](../../adr/0047-the-claude-brewer-runner-its-stream-endings-and-progress.md)).

- On Windows the native `claude.exe` starts without a shell, inside a Job Object (ADR 0039); npm's `claude.cmd` goes through cmd.exe with every argument validated (ADR 0031).
  Either way, prompts, the system prompt and settings travel via stdin and files only, never arguments.
- `--safe-mode` implements `context: lean`: without it, `claude -p` loads the target repository's `CLAUDE.md`, hooks and MCP servers.
  How `context: repo` gives a brewer the repository's instructions without its hooks is open (ADR 0042).
- Claude Code keeps an attempt's session where it ran (30 days by default), so anyone on that machine can step into a finished attempt's session with `foedrum resume <batch> [<step>[#<n>]]` from a terminal (ADR 0126), or into a running step's session, which then ends by the out doc it writes as an attempt of its own (ADR 0127); `/foedrum:resume` prints that line.
  Sessions are not carried to another machine ([a session on another machine](sessions-elsewhere.md)).

## The runner in the engine

A brewer attempt runs through the `BrewerRunner` interface (`src/engine/brewer-runner.ts`), which also reports progress to the supervisor.
A `done` of a brewer that produces commits also needs a commit after its worktree's start commit, which the limits carry: after the stream the real runner asks git on the attempt's branch in the clone its worktree was added to, never in the worktree, whose `.git` file the brewer can write (`countCommits`, `src/workspace/attempt-commits-git.ts`); a stop while it counts ends the attempt cancelled, and no commit is `blocked` + `divergence` with the brewer's summary, a rewritten start commit a retryable failure, and git's failure `blocked` + `environment` ([ADR 0074](../../adr/0074-git-commit-grants-fixed-git-rules-and-done-needs-a-commit.md)); a `fining` out doc that says `unchanged` succeeds without a commit and fails, to be tried again, with one ([ADR 0166](../../adr/0166-the-finer-simplifies-a-batch-s-change-before-green.md)).
Such a `done` with commits is then scanned for secrets, the push's own scan from the start commit to the tip of the attempt's branch in the clone (`scanAttemptCommits`, `scannedIfDone`): a finding fails the attempt retryably with `secrets: true`, naming each commit by 12 characters, kind and place, never the text; git's failure is `blocked` + `environment`, and a stop while it scans ends the attempt cancelled; the step's next fresh retry is told the reason and to build a key-shaped value at run time (`scanRetryOf`, [ADR 0187](../../adr/0187-a-committing-brewer-s-attempt-is-scanned-for-secrets-when-it-ends-done.md)).
The real runner, `claudeBrewerRunner` (`src/brewers/claude-runner.ts`), writes the attempt's settings and its system prompt file, starts `claude` with the `BrewerPrompt` on stdin inside a Job Object on Windows, and reads its stream line by line with `readClaudeStream` (`src/brewers/claude-stream.ts`), a pure reader that also gives the supervisor its progress: when the brewer last wrote a file or made a commit, read from its tool calls (ADR 0047).
The same progress also carries, for display only, the main thread's turn, its latest tool call reduced in the reader to a name and one safe word (a path relative to the worktree the runner passes in, `outside`, `(left out)`, or a shell command's prefix), and whether a denial came after that call; the runner adds `settingUp` while the repository's setup runs, and the driver's `progress(ref)` hands it all to `foedrum brew`'s live line, while the supervisor reads only its two watchdog fields ([ADR 0174](../../adr/0174-foedrum-brew-keeps-a-live-line-on-a-terminal.md)).
Its plan comes from the brewer of the attempt's step (`createAttemptPlans`, `src/brewers/attempt-plans.ts`, over the pure `planAttempt`): the worktree recorded in `step.started`, `buildBrewerEnv`, the brewer's body with the out doc contract and its inputs in nonce tags (for a brewer that asks for house yeast, the rules that match its change, [ADR 0169](../../adr/0169-house-yeast-rules-reach-a-batch-s-brewers-by-scope-and-lens.md)), the model behind its alias in the merged models (the Brewery's `models.jsonc` over Foedrum's `defaults/models.jsonc`, [ADR 0153](../../adr/0153-foedrum-s-defaults-map-their-own-model-aliases.md)), its tools and permissions with the repository's toolchain rules (and, for `git.commit: true`, `Bash(git status *)`, `Bash(git add *)` and `Bash(git commit *)` with a contract line that says to commit, ADR 0074), a settings file under `<workRoot>/attempt-settings/` and the system prompt file beside it (ADR 0183), and a new session with the id the driver chose and recorded in `step.started` as `session: { id, worktree }` before claude started (`brews`, `src/engine/driver.ts`; a check step has none); the version and model claude's init reported go on `step.finished` as `claude` ([ADR 0116](../../adr/0116-the-driver-records-each-attempt-s-session-and-claude-s-report-goes-on-step-finished.md)), and the house-yeast rules its plan selected and cut, with the files it left out as invalid, as `houseYeast` ([ADR 0169](../../adr/0169-house-yeast-rules-reach-a-batch-s-brewers-by-scope-and-lens.md)).
The driver asks for each attempt's limits by the attempt, so they are its batch's brewer's ([ADR 0059](../../adr/0059-attempt-plans-from-the-brewer-of-the-step.md)).
The `order` input is the body of the batch's issue, read through the GitHub reads (`githubOrderText`, `src/github/order-text.ts`), and the brewer's base environment is an allowlist of `serve`'s own that never holds a GitHub token (`brewerBaseEnv`, [ADR 0063](../../adr/0063-foedrum-serve-its-configuration-and-wiring.md)).

An interactive step's attempt runs as a person's `claude` session in `foedrum brew`'s terminal instead, and ends by the out doc it wrote through the same `settleAttempt`: [interactive steps](interactive-steps.md).
