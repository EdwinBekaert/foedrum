# Isolation levels

Claude Code's OS sandbox covers **shell commands only** and is available on macOS (Seatbelt), Linux and WSL2 (bubblewrap + socat); on native Windows, shell commands run unsandboxed.
File tools, MCP servers and hooks are governed by permission rules on every platform.

| Level | Where | What Foedrum does |
|---|---|---|
| **Sandboxed** | macOS, Linux, WSL2 | Per-attempt settings enable `sandbox.enabled` with `allowUnsandboxedCommands: false` and `autoAllowBashIfSandboxed: false`, so the allow rules decide for sandboxed commands too, and `permissions.blockReadsOutsideWorkingDirectories`, so sandboxed commands read none of the user folders but the working directories, git's global configuration and parts of `~/.claude` ([ADR 0160](../../adr/0160-sandboxed-commands-read-only-inside-the-working-directories.md)); they also hide the credential files and variables of ADR 0087, and the logins `GH_CONFIG_DIR`, `XDG_CONFIG_HOME` and `CLAUDE_CONFIG_DIR` move, from them; writable paths limited to the worktree, network limited to an allowlist |
| **Permissions only** | Native Windows | Strict tool allowlists, file-tool rules scoped to the worktree (`Read(./**)`, `Edit(./**)`, [ADR 0093](../../adr/0093-brewers-file-tool-rules-are-read-and-edit-rules-scoped-to-the-worktree.md)), minimal environment, `scope` guard. A warning is shown at start |
| **Container** (optional, any OS with an OCI container runtime: Podman or Docker) | Anywhere | The brewer runner starts `claude` inside a container that mounts only the worktree |

- `foedrum doctor` reports Node, npm, git, `gh` and `claude` (resolved path and version), the effective isolation level, a container runtime (Podman or Docker) when there is one (one that does not report a version, because it fails or does not answer within 3 s, is not usable, and the next is tried), and missing prerequisites (for example `bubblewrap`).
  It exits 1 when a required one is missing: git, `claude`, Node 24.15, `gh` 2.26.0 or later with a login for the GitHub host `foedrum.jsonc` names (`gh auth status`, asked without the token variables), or on Windows a Job Object to run brewers in ([ADR 0039](../../adr/0039-windows-job-objects-through-a-powershell-helper.md), [ADR 0073](../../adr/0073-github-only-through-gh-s-own-login.md)).
  It advises `gh auth setup-git` when the first credential helper git asks for that host is not `gh`.
  Under the isolation level it says what can still read gh's login: a brewer or a check step on the permissions-only level, with what the other levels keep from it for brewers (the sandboxed level hides the user folders, on WSL2 with the Windows user's logins under `/mnt`, gh's hosts file and the token variables, the docs don't say whether it stops a keyring read, and the container level closes both), ADR 0079 and ADR 0088 for a login a brewer did read, and where check steps run: in the OS sandbox outside native Windows, since [ADR 0076](../../adr/0076-check-steps-run-in-an-os-sandbox-with-no-network.md) ([ADR 0082](../../adr/0082-brewers-never-allow-gh.md)); `foedrum serve` refuses to start on the same required problems.
  It also reads `foedrum.jsonc` in the working directory, when there is one, and reports a config that does not pass its schema (two repositories with one alias, for example) as a required problem, and so do recipe and brewer files that do not load ([ADR 0053](../../adr/0053-recipe-files-reach-the-engine-brewer-steps-in-a-line-first.md)); when they load, it lists Foedrum's default files in use ([ADR 0098](../../adr/0098-foedrum-s-defaults-load-under-the-brewery-s-files-and-a-brewer-input-can-name-a-lens.md)), and each brewer's prompt from its instructions and lens inputs, in bytes and estimated tokens.
  Under `Notices:`, which never change the exit code, it names a prompt above 8,000 tokens, a Brewery brewer no recipe names and a Brewery lens that no brewer a recipe names reads, and each Brewery file that replaces a default, with the default's headings and marked lines (a line that starts with a bold phrase) the file no longer has ([ADR 0141](../../adr/0141-doctor-reports-prompt-sizes-unused-files-and-what-a-brewery-file-drops-from-its-default.md)).
  A pure core (`src/cli/doctor.ts`) turns the facts its shell gathers through the process runner into the report.
- On the sandboxed level, a toolchain installed under the home (nvm, Volta, asdf, `~/.local/bin`) is unreadable to sandboxed commands, so a Brewery there installs its toolchain under `/usr`, `/opt` or Homebrew's prefix ([ADR 0160](../../adr/0160-sandboxed-commands-read-only-inside-the-working-directories.md)).
- A Brewery can require a minimum level (`"isolation": { "minimum": "sandboxed" }`).
  For now it holds back only check steps, which make `foedrum serve` refuse to start where they would run below it ([ADR 0076](../../adr/0076-check-steps-run-in-an-os-sandbox-with-no-network.md)); that writing brewers refuse to run below it, and read-only brewers may run at a lower level (ADR 0010), is not built yet.
- Check steps (gravity readings) run in the brewers' minimal environment without claude's credentials ([ADR 0069](../../adr/0069-check-steps-run-the-repositorys-commands-in-an-attempt-of-their-own.md)), and in an OS sandbox of Foedrum's own with no network: `bwrap` on Linux and WSL2 (bubblewrap is needed for check steps there), `sandbox-exec` on macOS.
  Where AppArmor keeps bwrap from making its user namespaces (Ubuntu 24.04 and later), they do not start until the AppArmor profile from Claude Code's sandbox docs is added, which `foedrum doctor` says.
  On native Windows they run without one, their readings say `unsandboxed`, and `foedrum serve` says so at start; a Brewery with `"isolation": { "minimum": "sandboxed" }` and a check step does not start there ([ADR 0076](../../adr/0076-check-steps-run-in-an-os-sandbox-with-no-network.md)).
  A repository's `setup` (`npm ci`) runs in a check step's worktree before its checks, with the network and outside any sandbox, through the same process handling within its own `timeout`; its reading comes first and says `setup` and `unsandboxed`, a setup that does not pass blocks the step on its environment, and a Brewery that requires the sandboxed level does not start with a repository's setup and a check step ([ADR 0140](../../adr/0140-a-repository-s-setup-runs-before-a-check-step-s-checks-with-the-network.md)).
- Recommended setup on Windows for untrusted repositories: run Foedrum inside WSL2.
