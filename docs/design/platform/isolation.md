# Isolation levels

Claude Code's OS sandbox covers **shell commands only** and is available on macOS (Seatbelt), Linux and WSL2 (bubblewrap + socat); on native Windows, shell commands run unsandboxed.
File tools, MCP servers and hooks are governed by permission rules on every platform.

| Level | Where | What Foedrum does |
|---|---|---|
| **Sandboxed** | macOS, Linux, WSL2 | Per-attempt settings enable `sandbox.enabled` with `allowUnsandboxedCommands: false` and `autoAllowBashIfSandboxed: false`, so the allow rules decide for sandboxed commands too, and `permissions.blockReadsOutsideWorkingDirectories`, so sandboxed commands read none of the user folders but the working directories, git's global configuration and parts of `~/.claude` ([ADR 0160](../../adr/0160-sandboxed-commands-read-only-inside-the-working-directories.md)), and the toolchain folders of the driver's PATH that `sandbox.filesystem.allowRead` re-opens ([ADR 0162](../../adr/0162-sandboxed-commands-read-the-toolchain-folders-of-the-driver-s-path.md)); Foedrum hides from a brewer's commands the agent keys it passes to claude (the `ANTHROPIC_*` variables of the brewer's base environment, by name in `sandbox.credentials.envVars`), and names no login place, since which logins sandboxed commands can still reach is Claude Code's sandbox's to say ([ADR 0414](../../adr/0414-attempt-settings-name-no-login-places-the-agent-s-sandbox-hides-the-person-s-logins.md)); writable paths limited to the worktree, network limited to an allowlist |
| **Permissions only** | Native Windows | Strict tool allowlists, file-tool rules scoped to the worktree (`Read(./**)`, `Edit(./**)`, [ADR 0093](../../adr/0093-brewers-file-tool-rules-are-read-and-edit-rules-scoped-to-the-worktree.md)), minimal environment, `scope` guard. A warning is shown at start |
| **Container** (not built) | — | Not built, and doctor does not name it: the container's network, an image per Brewery, git worktrees across the mount and `claude`'s login inside it are each a design of their own. It comes back with a team that already brews in containers ([ADR 0406](../../adr/0406-the-container-level-is-not-built-and-doctor-stops-naming-it.md)) |

- `foedrum doctor` reports Node, npm, git, `gh` and `claude` (resolved path and version), the effective isolation level, and missing prerequisites (for example `bubblewrap`); on Linux also bwrap, socat and the user-mode network stack a setup would use, `pasta` where its resolver works, else `slirp4netns`, else `pasta` with no resolver behind a loopback stub, whose absence is an optional problem that leaves the level as it is: a repository's setup does not start without one, and doctor names the package to install (Debian and Ubuntu `slirp4netns`, Fedora and Arch usually `slirp4netns` or `passt` with Podman) ([ADR 0218](../../adr/0218-a-linux-setup-gets-a-network-namespace-of-its-own-through-a-user-mode-network-stack.md)).
  Under the tools, a `Setup network:` line says which stack a setup uses and whether it is isolated ([ADR 0400](../../adr/0400-pasta-comes-first-for-a-setup-where-its-resolver-works-and-slirp4netns-s-gap-is-recorded.md)).
  When `ANTHROPIC_BASE_URL` is set in doctor's environment, a `Model traffic:` line under the tools, after any `Setup network:` line, names that address, as only its origin, since a key can sit in any other part, and says every brewer started from this terminal sends its prompts there, since `brewerBaseEnv` passes every `ANTHROPIC_*` variable on; an address that is not http or https is not quoted, and the line is never a problem ([ADR 0063](../../adr/0063-foedrum-serve-its-configuration-and-wiring.md), [ADR 0087](../../adr/0087-sandboxed-commands-go-through-the-allow-rules-and-never-see-credentials.md)).
  It exits 1 when a required one is missing: git, `claude`, Node 24.15, `gh` 2.97.0 or later with a login for the GitHub host `foedrum.jsonc` names (`gh auth status`, asked without the token variables), or on Windows a Job Object to run brewers in ([ADR 0039](../../adr/0039-windows-job-objects-through-a-powershell-helper.md), [ADR 0073](../../adr/0073-github-only-through-gh-s-own-login.md), [ADR 0228](../../adr/0228-a-failed-actions-job-s-log-goes-with-the-batch-back-to-its-fix-step.md)).
  It advises `gh auth setup-git` when the first credential helper git asks for that host is not `gh`.
  Under the isolation level it says what can still read gh's login: a brewer or a check step on the permissions-only level, with what the other levels keep from it for brewers (for the sandboxed level, a pointer to Claude Code's sandboxing docs for what it hides, [ADR 0414](../../adr/0414-attempt-settings-name-no-login-places-the-agent-s-sandbox-hides-the-person-s-logins.md); doctor names no container level, which is not built, [ADR 0406](../../adr/0406-the-container-level-is-not-built-and-doctor-stops-naming-it.md)), ADR 0079 and ADR 0088 for a login a brewer did read, and where check steps run: in the OS sandbox outside native Windows, since [ADR 0076](../../adr/0076-check-steps-run-in-an-os-sandbox-with-no-network.md) ([ADR 0082](../../adr/0082-brewers-never-allow-gh.md)); `foedrum serve` refuses to start on the same required problems.
  It also reads `foedrum.jsonc` in the working directory, when there is one, and reports a config that does not pass its schema (two repositories with one alias, for example) as a required problem, and so do recipe and brewer files that do not load ([ADR 0053](../../adr/0053-recipe-files-reach-the-engine-brewer-steps-in-a-line-first.md)); when they load, it lists Foedrum's default files in use ([ADR 0098](../../adr/0098-foedrum-s-defaults-load-under-the-brewery-s-files-and-a-brewer-input-can-name-a-lens.md)), and each brewer's prompt from its instructions and lens inputs, in bytes and estimated tokens.
  A `Tasting:` line after the keep-awake line names the models in use that were never tasted and the steps a cheaper level may do for ([evaluation](../evaluation.md), [ADR 0419](../../adr/0419-doctor-lists-the-untasted-models-in-use-and-the-cheaper-levels-a-tasting-could-try.md)); it is never a problem.
  When the Brewery has a recipe that proves its tests red, it reads each repository's `test` line on this platform with `readTestLine` (`src/checks/test-line.ts`), as `foedrum init` does, and never runs it: a runner Foedrum knows whose line saves no test report is an optional problem whose fix is the line to use, or the packages to add, so doctor no longer ends "Foedrum has everything it needs"; a runner it does not know is a notice that it cannot tell ([ADR 0376](../../adr/0376-foedrum-init-writes-a-test-line-that-saves-its-reports-and-doctor-and-the-maltster-read-it.md)).
  Under `Notices:`, which never change the exit code, it names a prompt above 8,000 tokens, a Brewery brewer no recipe names and a Brewery lens that no brewer a recipe names reads, and each Brewery file that replaces a default, with the default's headings and marked lines (a line that starts with a bold phrase) the file no longer has ([ADR 0141](../../adr/0141-doctor-reports-prompt-sizes-unused-files-and-what-a-brewery-file-drops-from-its-default.md)).
  Under `System map`, it shows the [system map](../intake/system-map.md) whole, each repository read in its clone at `origin/<base>`, with the commit it read or why it could not ([ADR 0317](../../adr/0317-the-planners-read-a-system-map-computed-from-each-repository-s-manifests-with-no-model.md)).
  Under `Tests`, for each repository of a `foedrum.jsonc` that passes its schema, it names the test a check step runs and, when the repository sets `testChanged`, that its pull request's CI must run the full test ([ADR 0242](../../adr/0242-a-repository-can-name-a-fast-local-test-and-its-pull-request-checks-are-the-full-gate.md)).
  A pure core (`src/cli/doctor.ts`) turns the facts its shell gathers through the process runner into the report.
- On the sandboxed level, the attempt settings re-open to reads the toolchain folders of the driver's PATH under the home: nvm's node version (`~/.nvm/versions/node/<v>`), `~/.volta`, `~/.asdf`, Homebrew's prefix on Linux (`/home/linuxbrew/.linuxbrew`), and any other PATH folder under the home as it is, never its parent ([ADR 0162](../../adr/0162-sandboxed-commands-read-the-toolchain-folders-of-the-driver-s-path.md)).
- They re-open a PATH folder under the home whatever it holds, since the PATH is the person's own, never the home itself ([ADR 0414](../../adr/0414-attempt-settings-name-no-login-places-the-agent-s-sandbox-hides-the-person-s-logins.md)), and `denyRead` keeps npm's configuration files (`<folder>/**/npmrc`, `<folder>/**/.npmrc`) hidden in each one.
- A link out of a re-opened folder stays unreadable (pipx and uv tools in `~/.local/bin`, rustup's proxies, fnm's PATH folder), so a Brewery that uses one installs its toolchain with nvm, Volta or asdf, or outside the home.
- A Brewery can require a minimum level (`"isolation": { "minimum": "sandboxed" }`).
  For now it holds back only check steps, which make `foedrum serve` refuse to start where they would run below it ([ADR 0076](../../adr/0076-check-steps-run-in-an-os-sandbox-with-no-network.md)); that writing brewers refuse to run below it, and read-only brewers may run at a lower level (ADR 0010), is not built yet.
- Check steps (gravity readings) run in the brewers' minimal environment without claude's credentials ([ADR 0069](../../adr/0069-check-steps-run-the-repositorys-commands-in-an-attempt-of-their-own.md)), and in an OS sandbox of Foedrum's own with no network: `bwrap` on Linux and WSL2 (bubblewrap is needed for check steps there), `sandbox-exec` on macOS.
  Where AppArmor keeps bwrap from making its user namespaces (Ubuntu 24.04 and later), they do not start until the AppArmor profile from Claude Code's sandbox docs is added, which `foedrum doctor` says.
  On native Windows they run without one, their readings say `unsandboxed`, and `foedrum serve` says so at start; a Brewery with `"isolation": { "minimum": "sandboxed" }` and a check step does not start there ([ADR 0076](../../adr/0076-check-steps-run-in-an-os-sandbox-with-no-network.md)).
  A repository's `setup` (`npm ci`) runs in a check step's worktree before its checks, and in the worktree of a brewer with a shell before claude starts, through the same process handling within its own `timeout`; its reading comes first and says `setup`, and a setup that does not pass blocks the step on its environment ([ADR 0140](../../adr/0140-a-repository-s-setup-runs-before-a-check-step-s-checks-with-the-network.md), [ADR 0163](../../adr/0163-a-repository-s-setup-runs-before-a-brewer-attempt.md)).
  It runs in the same OS sandbox with the network kept: on Linux and WSL2 bwrap with a network namespace of its own, which `pasta` (passt) joins where its resolver works, else `slirp4netns`, else `pasta` with no resolver behind a loopback stub (ADR 0400), so it reaches neither the host's loopback services nor its abstract Unix sockets ([ADR 0218](../../adr/0218-a-linux-setup-gets-a-network-namespace-of-its-own-through-a-user-mode-network-stack.md)); on macOS the Seatbelt profile with IP allowed and every Unix socket but mDNSResponder's denied.
  A Brewery that requires the sandboxed level does not start with a repository's setup on native Windows (ADR 0163); the setup is unstarted where its sandbox or, on Linux, its network stack cannot start, and runs without a sandbox, its reading saying `unsandboxed` and `foedrum serve` saying so at its start, on native Windows only ([ADR 0158](../../adr/0158-a-repository-s-setup-runs-in-the-check-sandbox-with-the-network-kept.md)).
  The refresh of a lockfile a release bump left behind runs as a setup does, after a brewer attempt, in a scratch tree of its branch ([ADR 0412](../../adr/0412-foedrum-refreshes-and-commits-the-npm-lockfile-a-release-bump-leaves-behind.md)).
- Recommended setup on Windows for untrusted repositories: run Foedrum inside WSL2.
