# One command layer

Every action (`brew`, `status`, `stuck`, `answer`, `approve`, `retry`, `skip`, `rewind`, `cancel`, `order`, `rank`, `takeover`, `pause`, `continue`, `bottle`, `recipe`, `refine`, `triage`, `review`, `resume`, `remember`, `doctor`, `brewers`, `replay`, `init`) is one typed command with one schema and one handler in the command registry (`src/cli/commands.ts`).
A command that changes state is recorded by its events, which carry who issued it and from where; read-only commands (`doctor`, `status`, `stuck`, `brewers` and `replay`) append nothing; `resume` changes state, since on a running batch it takes the batch over and records the attempt that continues its session, as a driver (ADR 0127), and on a finished attempt it appends nothing and holds only that attempt's lease while its session runs (ADR 0126); `rank` with no place only prints the order's place in the intake's queue and appends nothing ([ranking](../intake/ranking.md)) ([ADR 0030](../../adr/0030-only-commands-that-change-state-are-recorded.md)).
The registry says which is which; the terminal has `retry`, `skip`, `answer <batch> <answers>...` (one per question, in the order `stuck` numbers them), `recipe`, `rewind <batch> <step> <owner/name=sha>...`, `cancel`, `order <alias>#<n>` (or `#<n>` for a Brewery issue, [target-repository issues](../intake/target-issues.md)), `brew <issue> [--as <name>] [--take]`, `rank <order> [<n> | first] [--why <reason>]` ([ranking](../intake/ranking.md)), `takeover <batch> [--as <name>]`, `pause [<order> | --all] [--by <time>] [--why <reason>]` and `continue [<order> | --all]` ([pause and continue](pause.md)) and `resume <batch> [<step>[#<n>]]`, each with a schema in `src/schemas/commands.ts`.
Every command is decided against every committed event inside the transaction that appends its events (`createCommandLog`, `src/engine/command-log.ts`), so the supervisor, the drivers and a terminal command can write to one store at once ([ADR 0044](../../adr/0044-batch-leases-held-by-the-driver-and-one-command-log.md)).
`foedrum serve` is a program that runs until stopped, not a command of this layer, so it is not in the registry ([ADR 0063](../../adr/0063-foedrum-serve-its-configuration-and-wiring.md)); `brew`, which drives one batch until it stops, is one, for the terminal and the plugin, and opens the store as `serve` does ([ADR 0123](../../adr/0123-foedrum-brew-drives-one-batch-under-an-owner-of-its-own.md)).
`foedrum status` lists each batch with its lane, what it is doing or waiting for, and the sum of its attempts' receipts, in ASCII: their count, duration, turns, tokens and denials, never a cost ([ADR 0172](../../adr/0172-an-attempt-s-receipt-from-its-stream.md), [ADR 0181](../../adr/0181-receipts-show-no-cost.md)).
`foedrum status --watch` keeps a board of the live batches on a terminal, redrawn in place about once a second from the store as `status` reads it, with no lease, and with a line per running attempt; off a terminal it refuses with one line and exit code 1, and it is run by the terminal the command layer is given, as `brew` is, and a read of the store that fails keeps the last board with one line that says so until the next read ([ADR 0188](../../adr/0188-foedrum-status-watch-redraws-a-board-of-the-live-batches.md), [ADR 0189](../../adr/0189-the-status-board-outlasts-a-failed-read-and-counts-rewrapped-rows.md)).
`foedrum init` asks the Brewery's name (default `<login>/foedrum-brewery`) and its target repositories, reads each new target's default branch and, for Node, its checks from `package.json` through gh's own login, proposed for the user to confirm (ADR 0023), writes `foedrum.jsonc`, `models.jsonc`, `.gitignore` and `.claude/settings.json`, each checked against its schema first, and asks before changing a file that is there (so a second run lists what it would change) ([ADR 0199](../../adr/0199-foedrum-init-writes-a-brewery-s-files-in-its-clone.md)).
Outside a clone it also asks private or public (default private), refuses a name GitHub already has or that no folder can have on Windows, and, once every question about the files is answered, creates the repository through gh's login, under the login or the organization that owns the name, and clones it into a folder of its name, where it writes the files; inside a clone it creates nothing ([ADR 0207](../../adr/0207-foedrum-init-creates-the-brewery-s-repository-labels-the-targets-and-pushes.md)).
Then it offers the intake label `foedrum:brew` in each target repository that lacks it (a no prints the `gh label create` command), lists the files git sees as new or changed and the commits origin does not have yet and, after a yes, commits only those files and pushes the branch, with no token anywhere: gh answers git as its credential helper (ADR 0207).
Then it offers the `foedrum` command, a shim that runs this checkout's `src/cli/main.ts` with the `node` on the PATH (`foedrum`, mode 0755, on Linux and macOS; `foedrum.cmd` on Windows, when PATHEXT has `.CMD`), in a folder of the PATH inside the user's home that it can write: it lists them numbered, `~/.local/bin` and `~/bin` first and the folders a tool manages (npm's, nvm's, Python's, cargo's) last, never `WindowsApps`, and an empty answer takes the first ([ADR 0210](../../adr/0210-foedrum-init-writes-the-foedrum-command-into-a-user-folder-on-the-path.md)).
A shim of init's that runs this checkout is kept, one that runs another is named in a question (default no), and any other `foedrum` there is left as it is; a no, or a PATH with no such folder, prints the shim for the user to write by hand, the second with the folder to create and the line that adds it to the PATH, or only to create it or make it writable when the PATH names it already, and with no folder at all for a home that is a root folder; a file there it cannot read or write is named with the system's message, and the shim is printed the same way (ADR 0210).
It runs `doctor` in the clone and ends with its exit code, or 1 when a git call of the push failed; it appends nothing, and is terminal-only until `/foedrum:init` (#530).
`foedrum brewers` reports, per brewer in use, the attempts of its steps, how they ended, the batches Stuck at them now and the tokens they used, from the folded store; a step's brewer comes from the recipe its batch had chosen when the attempt was scheduled, as the files are now, and attempts of a step the files no longer have are listed apart; without a store it lists every brewer with no attempts ([ADR 0159](../../adr/0159-foedrum-brewers-reports-each-brewer-s-attempts-outcomes-stuck-batches-and-tokens.md)).
The plugin (`/foedrum:<command>`), the terminal (`foedrum <command>`), GitHub comments (`/foedrum <command>`) and later the dashboard are thin adapters; how the plugin's skills run the terminal, and the parity test that keeps the plugin and the registry in step: [the plugin](plugin.md).
The dashboard shows each batch's live session output next to its pending questions, which are answered in place.
