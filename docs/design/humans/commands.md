# One command layer

Every action (`brew`, `status`, `stuck`, `answer`, `approve`, `retry`, `skip`, `rewind`, `cancel`, `order`, `takeover`, `pause`, `bottle`, `recipe`, `refine`, `triage`, `review`, `resume`, `remember`, `doctor`, `replay`, `init`) is one typed command with one schema and one handler in the command registry (`src/cli/commands.ts`).
A command that changes state is recorded by its events, which carry who issued it and from where; read-only commands (`doctor`, `status`, `stuck` and `replay`) append nothing; `resume` changes state, since on a running batch it takes the batch over and records the attempt that continues its session, as a driver (ADR 0127), and on a finished attempt it appends nothing and holds only that attempt's lease while its session runs (ADR 0126) ([ADR 0030](../../adr/0030-only-commands-that-change-state-are-recorded.md)).
The registry says which is which; the terminal has `retry`, `skip`, `answer <batch> <answers>...` (one per question, in the order `stuck` numbers them), `recipe`, `rewind <batch> <step> <owner/name=sha>...`, `cancel`, `order <alias>#<n>` (or `#<n>` for a Brewery issue, [target-repository issues](../intake/target-issues.md)), `brew <issue> [--as <name>] [--take]`, `takeover <batch> [--as <name>]` and `resume <batch> [<step>[#<n>]]`, each with a schema in `src/schemas/commands.ts`.
Every command is decided against every committed event inside the transaction that appends its events (`createCommandLog`, `src/engine/command-log.ts`), so the supervisor, the drivers and a terminal command can write to one store at once ([ADR 0044](../../adr/0044-batch-leases-held-by-the-driver-and-one-command-log.md)).
`foedrum serve` is a program that runs until stopped, not a command of this layer, so it is not in the registry ([ADR 0063](../../adr/0063-foedrum-serve-its-configuration-and-wiring.md)); `brew`, which drives one batch until it stops, is one, for the terminal and the plugin, and opens the store as `serve` does ([ADR 0123](../../adr/0123-foedrum-brew-drives-one-batch-under-an-owner-of-its-own.md)).
The plugin (`/foedrum:<command>`), the terminal (`foedrum <command>`), GitHub comments (`/foedrum <command>`) and later the dashboard are thin adapters; how the plugin's skills run the terminal, and the parity test that keeps the plugin and the registry in step: [the plugin](plugin.md).
The dashboard shows each batch's live session output next to its pending questions, which are answered in place.
