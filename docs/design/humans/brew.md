# foedrum brew and the plugin

- **Interactive:** an engineer opens Claude Code and types a plugin command, for example `/foedrum:brew 21`.
  The session drives the batch, without `foedrum serve` running: `/foedrum:brew` runs `foedrum brew --via plugin` in the background, shows where the batch went when it exits, and on `needs_input` asks the engineer each question, runs `foedrum answer` and brews again ([ADR 0125](../../adr/0125-the-foedrum-plugin-is-markdown-skills-that-run-the-terminal-with-via-plugin.md)).
  A recipe's interactive step runs as a person's `claude` session in a terminal ([interactive steps](../recipes/interactive-steps.md)): when brew exits 3 with the batch waiting for a session, `/foedrum:brew` runs `foedrum brew <issue> --new-window`, which opens a new terminal window running `foedrum brew <issue> --take --as <owner>`, without the Claude Code session's variables, through `launchProcess`, which waits for no window (Windows Terminal's `wt.exe new-tab`, else `cmd.exe /c start` by its full path; Terminal through `osascript` on macOS; `$TERMINAL` or `x-terminal-emulator` with `-e` through `setsid -f` on Linux), and tells the engineer to run `/foedrum:status` after closing it; where no window can open (SSH, no display, no launcher) it prints the command to run in a terminal and exits 5 ([ADR 0222](../../adr/0222-a-recipe-s-brewer-step-may-be-interactive.md)).
  Under it is `foedrum brew <issue> [--as <name>]` ([ADR 0123](../../adr/0123-foedrum-brew-drives-one-batch-under-an-owner-of-its-own.md)): a driver of its own, `--as` or `session-<id>` from `CLAUDE_CODE_SESSION_ID`, else `terminal` ([ADR 0259](../../adr/0259-a-driver-with-neither-as-nor-a-session-is-terminal.md); a second driver under one owner is refused by its lock, naming `--as`), on the Cellar's wiring (`wireDriver`, `src/cli/driver-wiring.ts`) with `takes` that one batch; it orders and routes by label an issue with no batch (by a claimed order's Brewery issue, its claimed batch, [ADR 0240](../../adr/0240-order-and-recipe-work-by-the-brewery-issue-on-both-surfaces.md)), ticks until the batch is on tap (exit 0), Stuck (3), needs input (4, with the numbered questions `foedrum answer` takes) or cancelled (6), and refuses (5) a paused order, or any order while the Brewery is paused ([pause and continue](pause.md)), and a batch another driver holds, naming it, unless `--take` takes it over ([ADR 0124](../../adr/0124-foedrum-takeover-hands-a-batch-to-another-driver-as-a-recorded-command.md)), after recording the end of the run it stopped, within a lease, when a takeover that resumes a step took the batch ([ADR 0127](../../adr/0127-foedrum-resume-takes-a-running-batch-over-and-continues-its-step-s-session.md)); a Stuck batch keeps its lease while the engineer answers.
  On tap, its last line names the pull requests, or says `no pull request` ([ADR 0261](../../adr/0261-the-status-path-says-why-a-failed-attempt-failed-and-what-answered-a-question.md)), with the plan comment's link for a batch recorded on tap with a plan before [ADR 0275](../../adr/0275-a-finished-plan-waits-stuck-for-its-review-and-every-comment-links-the-doc-it-sums-up.md); Stuck with a plan ready for review, its last line ends with the plan comment's link, and it exits 3 ([ADR 0275](../../adr/0275-a-finished-plan-waits-stuck-for-its-review-and-every-comment-links-the-doc-it-sums-up.md)).
  It says on tap only there, and prints no lane line for it while the batch's last effects apply; a stop then still names the lane on tap ([ADR 0272](../../adr/0272-the-status-comment-names-a-pull-request-once-and-breaks-its-path-per-round.md)).
  It prints its status comment's link once the comment is made (a claimed issue's on its Brewery issue), and about every 30 s while its lane line stays the same which attempts run and for how long ([ADR 0154](../../adr/0154-lane-labels-on-the-order-s-issue-and-the-status-comment-s-path-line.md)).
  On a terminal (standard output a TTY, `TERM` not `dumb`, `CI` not set) it prints those 30-s lines no more and keeps one live line instead, redrawn about once a second, also while a takeover waits for the runs it stopped: an ASCII spinner, the batch's time since its order (`batch.ordered`'s `at`, or this run's start for an order that has none), then per running attempt its step and attempt, elapsed time, turn, last main-thread tool call as its name and one safe word (a path relative to the worktree; `outside` when that path's first segment is `..` or it is absolute, so a file named `..foo` inside shows by its path; `(left out)` when it holds a secret; or a shell command's prefix), and `denied` after a denial, or `setup` while the repository's setup runs; ASCII only, every other code point escaped, cut from the end to the terminal's width less one; a redraw writes over the old line and then clears to its right, so it never shows blank; a lasting line clears it, prints and draws it again, and it is cleared before any exit ([ADR 0174](../../adr/0174-foedrum-brew-keeps-a-live-line-on-a-terminal.md), [ADR 0179](../../adr/0179-the-live-line-redraws-in-place-and-leads-with-the-batch-s-time.md)).
  While an attempt runs it keeps the machine from sleeping on its idle timer, as `serve` does ([keeping the machine awake](../platform/keep-awake.md)).
  With stdin a terminal and outside Claude Code (`CLAUDE_CODE_CHILD_SESSION` not `1`), brew opens an interactive step's session in the foreground: its lines wait, the live line is not drawn and Ctrl+C is claude's until claude exits, and a batch it finds waiting for a session at its start gets the person's `retry` first; without one it brews the other steps headless and exits 3 at the interactive step with the line to run in a terminal (ADR 0222).
