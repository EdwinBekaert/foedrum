# The check sandbox

A check's command line runs in an OS sandbox of Foedrum's own (`sandboxedChecks`, `src/platform/check-sandbox.ts`): `bwrap` on Linux and WSL2, `sandbox-exec` on macOS, with no network, the home folder hidden, and writes only in the worktree and a temporary folder; where that sandbox cannot start, the check is unstarted, never run without it.
On native Windows it runs as before, each reading says `unsandboxed`, and `foedrum serve` says so at start; a Brewery that requires the sandboxed level does not start there with a check step ([ADR 0076](../../adr/0076-check-steps-run-in-an-os-sandbox-with-no-network.md)).
A repository's setup runs in the same sandbox with the network kept ([ADR 0158](../../adr/0158-a-repository-s-setup-runs-in-the-check-sandbox-with-the-network-kept.md)).
On Linux and WSL2 its bwrap keeps `--unshare-net`, and a user-mode network stack, `slirp4netns` or else `pasta` from the Cellar's PATH (slirp4netns first: Ubuntu runs pasta under passt's confined AppArmor profile), joins that namespace before the line runs: bwrap tells the pid of its child on `--info-fd`, the line waits on `--block-fd` until the stack is up, and the stack ends with the run ([ADR 0218](../../adr/0218-a-linux-setup-gets-a-network-namespace-of-its-own-through-a-user-mode-network-stack.md)).
The namespace is 10.0.2.100 behind the stack's gateway, IPv4 only, with no address mapped to the host's loopback and no port forwarded either way, so a setup reaches the network but not the host's loopback services or its abstract Unix sockets (an X server, a `unix:abstract=` D-Bus bus).
Its `/etc/resolv.conf` is Foedrum's own `nameserver 10.0.2.3`, given read-only at that file's real path, which the stack answers.
Without either stack, or when the stack fails before it is up, the setup is unstarted with the reason, never run in the host's namespace; `foedrum doctor` names the stack on Linux.
The worktree's repository is bound read-only, and with it each object store that repository's `objects/info/alternates` names, only when it names one and the repository's real path is a `.git` directory directly in a repository's `git-dirs/` under the work root, which Foedrum alone writes, the merged tree's `<uuid>.tree` beside it being its check's (`borrowsFrom`, which `foedrum serve` gives; none by default): for the checks on an open pull request's merged tree, a worktree of Foedrum's own git directory that borrows the clone's objects. A brewer or a check writes its worktree, and could plant a record and an alternates file there or in a sibling attempt's ([ADR 0203](../../adr/0203-an-open-pull-request-s-checks-run-on-its-merged-tree-when-its-base-moves.md)).
