# Check steps

A **check step** (a gravity reading) is an attempt like a brewer's, with a worktree of its own at the task tree, that `stepRunner` (`src/engine/step-runner.ts`) starts on the check runner (`src/checks/check-runner.ts`) instead of claude: it runs each check's command line from `foedrum.jsonc` (its platform override, else `run`), or a Brewery's literal `{ "run": … }`, through the platform shell and the process runner, in order, until the first that does not pass, with the step's deadline (its own, else 30 minutes) as the timeout and the brewers' minimal environment (`buildBrewerEnv`, no GitHub token, none of claude's credentials).
A `null` check is skipped.
A check step whose checks name `test`, in a repository whose `checks` set `testChanged`, runs that line in its place, `{base}` replaced by the commit the batch's change starts from (`planChecks`, `src/checks/gravity.ts`), and its reading says `changed: true`; with no start it runs `test` ([ADR 0242](../../adr/0242-a-repository-can-name-a-fast-local-test-and-its-pull-request-checks-are-the-full-gate.md)).
The red proof, a survey's check, Brett's baseline and the checks of an open pull request's merged tree always run `test` (Brett's mutants may run fewer test files, below), and setting `testChanged` is the repository's promise that its pull request's checks run the full test, the full gate before the merge.
The Gauger and the Cellarman get the same line, from the same commit, as their input `testChanged` to run while they work; the checks before the Cellarman's end still run `test` ([ADR 0417](../../adr/0417-the-gauger-and-the-cellarman-read-the-repository-s-testchanged-line-from-where-the-change-starts.md)).
`step.finished` records a reading per check, with the exit code, or the signal that ended it, and the last 4,000 characters of the output, each line that looks like a secret left out (`findSecrets`, `src/formats/secrets.ts`); a check ended by a signal fails as an exit code does; a failed check fails the step without a retry and follows its `onFail` route, whose rounds are counted from the `route` its attempts record, else the batch is Stuck; a check that wrote too much or could not start blocks it on its environment; an attempt that read nothing is tried again, at most 3 times since its latest reading ([ADR 0325](../../adr/0325-a-step-counts-its-attempts-per-round.md)).
A test check that exited with another code than 0 also records the failing tests its reports name, at most 10 with a count of the rest, each on one line, cut to 200 characters and left out when it looks like a secret, read through the test map (`withFailing`, `src/checks/gravity.ts`): a command that writes its reports to files may print nothing ([ADR 0304](../../adr/0304-a-failed-test-reading-names-its-failing-tests-from-the-test-map-s-reports.md)).
The red proof names them from the reports it read, and a check step whose test check failed reads the effective map's reports once more; a TRX report stays unread (#727), and a map or a report that cannot be read names none.
A check on an open pull request's merged tree reads the base's map at the base's tip and the batch's at the head, and its reports only when its test check failed: its worktree is new for each run, so nothing is cleared, and it never waits on a map ([ADR 0307](../../adr/0307-a-failed-check-step-s-reason-and-the-merged-tree-check-name-the-failing-tests.md)).
A Brett attempt's scratch trees run the same `test` check through `testRun`, beside `checkTree`: it clears the effective map's report paths, runs the setup and the check below normal priority ([ADR 0413](../../adr/0413-brett-s-scratch-tree-runs-start-below-normal-priority.md)), and reads every test's outcome from each module's reports with the same parsers ([ADR 0313](../../adr/0313-the-engine-runs-brett-s-mutants-in-scratch-trees-against-a-fresh-baseline.md)).
In a repository whose `checks` set `testFiles`, a command whose every line holds `{files}`, `testRun` is also asked for two things ([ADR 0431](../../adr/0431-brett-s-mutants-on-node-run-only-the-test-files-that-reached-their-line.md)): the baseline's run sets `NODE_V8_COVERAGE` to a folder of its scratch tree for the `test` check, and reads the V8 coverage Node's processes wrote there, one record per test file, after the run; and a mutant's run replaces `test` with the `testFiles` line, `{files}` the test files that reached the mutant's line, sorted, a space between them.
A repository that names no `testFiles` runs the whole `test` check for the baseline and every mutant, with no coverage.
A reading's line in the merge brief, the status comment and the base check names a named check by its name alone and a literal command or the setup cut to 80 characters, then how it ended and the failing tests, their count first so the line's cut at 200 characters keeps it (`readingText`).
A check step's reason names the command and, once its test reading names failing tests, says them after `: `, the count first and at most 3 names within 300 characters, its command then cut to 80 characters (`settleReadings`, settled again after the reports were read; [ADR 0307](../../adr/0307-a-failed-check-step-s-reason-and-the-merged-tree-check-name-the-failing-tests.md)): `the check "test" (npm test) failed with exit code 1: 5 tests failing: a, b, c, …`.
The path gives such an attempt its check and count only, `the check "test" failed, 5 tests failing`, read from its readings; the Stuck and failed-attempt lines show the reason within their cut at 200 characters, the count always kept.
The `route` input of the step it sends back names the failing tests, unescaped as its tail is, and says when the check printed nothing (ADR 0304).
Once its `test` check exited 0, a step in a repository with a [test map](test-map.md) reads the map at the base and at its tip ([ADR 0280](../../adr/0280-a-new-module-is-judged-unreached-only-on-a-passing-test-run.md)): a module only the batch's map adds that wrote no report, a report path that is refused, or a base map that cannot be read, makes the batch Stuck on its environment, and a batch's map that cannot be read fails the step without a retry, along its `onFail` route.
Before its setup and its checks, a step that runs the tests (a red proof, or a step with a `test` check) reads the freshness of the map at its tip ([the test map](test-map.md), [ADR 0282](../../adr/0282-a-stale-test-map-sends-back-the-change-that-made-it-and-the-maltster-surveys-a-new-one.md)): a map in the repository that the batch's change left stale fails the step without a retry, along its `onFail` route, a git read that fails blocks it on its environment, and any other stale map is recorded on `step.finished` as `staleMap` and named in the status comment.
A passing test check also compares the tests the Gauger named with the reports, and fails for none of them ([the red proof](red-proof.md)).
A survey's check ends these cases otherwise: a module no line reaches and a map stale by the run fail it back to the survey, and with no round left it blocks on its environment, as [the test map](test-map.md) says ([ADR 0298](../../adr/0298-the-maltster-s-survey-ends-without-a-session-for-a-fresh-map-and-its-check-sends-a-disagreement-back-once.md)).
A check step that is not a red proof then also reads the test reports and the coverage of the batch's change, and fails along its `onFail` route on a skip its test report places in a line the batch added to a separate test file, then on a changed line no test ran, as [the test map](test-map.md) says ([ADR 0274](../../adr/0274-the-red-proof-reads-line-coverage-of-the-change-and-a-test-map-not-test-names.md)); before its `test` check runs, it clears every coverage report path and every TAP and JUnit test report path either map names, and a path that cannot be cleared blocks it on its environment.

A check step's deadline is its own or 30 minutes; it has no stall limit, and it is tried again only after an attempt that read nothing, at most 3 times since its latest reading ([ADR 0325](../../adr/0325-a-step-counts-its-attempts-per-round.md)).
The recipe's last check that expects to pass, when an openPullRequest step follows it (Nip's `green`), first gets the base merged into its worktree by the driver, before its setup and its checks; a conflict blocks it on a divergence before any reading ([ADR 0164](../../adr/0164-a-batch-merges-its-base-before-its-last-check.md), [the openPullRequest action](../recipes/open-pull-request.md)).
Before its checks, once nothing else blocks the step, it runs the repository's `setup` in that worktree, within its own `timeout`; its reading comes first, and a setup that does not pass makes the batch Stuck on its environment, not along `onFail` ([ADR 0140](../../adr/0140-a-repository-s-setup-runs-before-a-check-step-s-checks-with-the-network.md)).
The setup runs in the checks' sandbox with the network kept, the home folder and its package caches hidden, so each setup downloads what it installs ([ADR 0158](../../adr/0158-a-repository-s-setup-runs-in-the-check-sandbox-with-the-network-kept.md)).
The same setup also runs before the attempt of every brewer with a shell, so check steps never reuse a brewer's install: each worktree installs its own ([ADR 0163](../../adr/0163-a-repository-s-setup-runs-before-a-brewer-attempt.md)).
The same check lines also run inside the attempt of a brewer with `"checksBeforeEnd": true` (the Cellarman and the Finer) once its session ends done: build, typecheck, lint and format, and the red step's test files where the test line takes files, through the same sandbox (none on native Windows) and environment, and a failure goes back to that session once ([how a brewer runs](../recipes/how-a-brewer-runs.md), [ADR 0381](../../adr/0381-a-brewer-that-writes-code-runs-the-quick-checks-before-its-end-and-is-sent-back-once.md)).
They are no reading of a check step: Nip's `green` still runs every check after them, the whole suite included, and is the gate.

**Code, test of the changed code:** a repository's `checks.testChanged` with `{base}` in `src/schemas/brewery-config.ts`, planned in place of `test` by `planChecks` (`src/checks/gravity.ts`) for a plain check step only, read by `ranChanged`, and `testGateOf` for doctor's Tests section; `npm run check -- --base <commit>` (`checkMode`, `scripts/check.ts`), which writes lcov.info, is Foedrum's own ([ADR 0242](../../adr/0242-a-repository-can-name-a-fast-local-test-and-its-pull-request-checks-are-the-full-gate.md)); the Gauger and the Cellarman get it as the `test-changed` input (`testChangedLine` in `src/checks/gravity.ts`, which `planChecks` also uses; built in `createAttemptPlans`, `src/brewers/attempt-plans.ts`), its `{base}` the base the batch merged last on the line to the attempt's head (its branch when it commits), else its start ([ADR 0452](../../adr/0452-green-starts-at-the-merged-base-and-a-merge-counts-only-on-the-heads-line.md), [ADR 0417](../../adr/0417-the-gauger-and-the-cellarman-read-the-repository-s-testchanged-line-from-where-the-change-starts.md))
