# The red proof

> **Decided, not built yet.** [ADR 0274](../../adr/0274-the-red-proof-reads-line-coverage-of-the-change-and-a-test-map-not-test-names.md) replaces how the red proof finds the step's tests by name with rules that read no names, from the runner's reports and the repository's test map; the record's Decision states them with each of their conditions.
> The same record changes what `testsUnchanged` keeps, which is built (below, #711), and adds a check that fails on a changed line that no test runs.
> This page says what the red proof does today. It stays true until the build issues of #618 land.
> Built so far, and not yet called by any check: the coverage readers `src/formats/lcov.ts` and `src/formats/cobertura.ts`, with `src/formats/coverage-files.ts` reading LCOV by file and Cobertura as every `coverage.cobertura.xml` under a folder pattern (each file a regular one of at most 16 MiB, as ADR 0078 reads a test report), into a `CoverageReport` of each file's lines (paths relative to the worktree's root with `/`, its root compared in either case on every system, since a folder beside the worktree that differs only in case is no layout a tool runs in, a file outside it left out, and of several Cobertura `<source>`s the one whose file is in the worktree) with their hits and, where the tool writes them, branches taken of total; reports and classes merge by the most hits per line and the branch count with more taken, so two runs that took different halves of a branch show the higher count, not their union.
> Not in the readers: the cap on how many files a folder pattern may match, and the refusal of a report path or pattern that leads out of the worktree by its real path (ADR 0274), which the test map and the uncovered-line check (#706, #710) put around them.

Recipes with `testFirst` run the Gauger (failing tests), a red proof (a gravity reading with `"expect": "fail"`, read from the repository's structured test report), then Cellarman, whose `testsUnchanged` guard protects the red tests' assertions ([ADR 0017](../../adr/0017-test-first-recipes-and-tasting-lenses.md)).

A red proof's `of` must name a step whose brewer commits; it runs the `test` check and judges the repository's test report, never the exit code, and a brewer with the `testsUnchanged` guard keeps the proven step's tests ([ADR 0078](../../adr/0078-the-red-proof-reads-the-test-report-and-testsunchanged-compares-lines.md), below).

**Red proof needs a test report.** A red proof reads a structured test report, not an exit code: each repository in `foedrum.jsonc` declares `testReport` (TAP or JUnit XML, and where to find it).
A recipe that needs red proof on a repository without one stops at the start of the batch as Stuck (`environment`), naming the fix, before any brewer runs.

**What the red proof reads** ([ADR 0078](../../adr/0078-the-red-proof-reads-the-test-report-and-testsunchanged-compares-lines.md)).
The engine runs the repository's `test` check, removing a report file of a previous run first, then reads the report and what the `of` step committed, from where its first attempt started to its latest success.
The `of` step's tests are the report's tests whose names a line the step added writes as a declaration does: a whole string literal (`test('adds two numbers'`), a name before `(` or after `def`, `fn` or `func` (`def test_adds`), a GoogleTest macro's test, or a Gherkin scenario's line; a bare word in code (`key: null,`) declares nothing ([ADR 0176](../../adr/0176-a-test-s-name-is-declared-only-where-a-declaration-writes-it.md)), so give tests names the runner reports as written.
A string literal declares a test only in a test file: a file the step changed that declares a test at its tip (`test(`, `def test…(`, `@Test`, `t.Run(`, …), read in the clone at the branch its commits end at when its added lines declare none, so a row added to an existing table counts; elsewhere, as in a regenerated schema's `"type": "array"`, it is data, and every other form counts in any file ([ADR 0262](../../adr/0262-a-string-literal-declares-a-test-only-in-a-file-that-declares-a-test-at-the-step-s-tip.md)).
It reads at most 50 such files, 10 s each; one past that count is none, and a read git was killed for blocks the red proof on its environment.
The list reads text, so a source or data file with declaration-like text (`it (` in a comment or a `.describe()` text, zod's `.describe(`) is a test file too, as every file was before; a table row cannot be a named regression test, since regression names still match only in files whose added lines declare a test.
A name before `(` counts only where no call can stand: after a declaration's words (`void adds(`, `@Test public void adds(`, `func (s *Suite) TestAdds(`), not at the line's start nor after the pairs, characters and words that open an expression (`=`, `,`, `(`, `->`, `return`, …: `const tree = parse(input);`), among them `<` and `}` (`if (limit < parse(input)) {`, `} parse(input);`, [ADR 0182](../../adr/0182-a-call-after-a-less-than-or-a-closing-brace-declares-no-test.md)); a call after a mark a declaration also writes (`*`, `&`, `>`, `)`) or after a character or word not on that list still counts ([ADR 0178](../../adr/0178-a-name-before-a-parenthesis-declares-a-test-only-where-no-call-can-stand.md)).
A name also counts without a runner's parameters (`adds(int, int)[1]` as `adds`), as its part after suite titles (`the calculator > adds two numbers`), and as that part's last part after a class or module (`com.acme.AddTest.adds` as `adds`), which holds no space, so a sentence that ends in a dotted word (`… with git.commit`) counts only as a whole (#406).
The red proof passes when every one of them fails, none passes (a stub must throw, not return a value) or is skipped, and nothing in the report names a load, compile, import or collection error (`SyntaxError`, `Cannot find module`, `ImportError`, `error TS2304`, `errors during collection`, `System.IO.FileLoadException : Could not load file or assembly`, …; .NET's load failures as an exception's text, by full type name, [ADR 0269](../../adr/0269-the-red-proof-refuses-net-s-assembly-and-type-load-failures.md)), not even in one of those tests' own failure: test such an error by asserting on it.
Tests the step did not add may pass or fail on an assertion.

**Regression tests** ([ADR 0170](../../adr/0170-the-red-proof-accepts-the-regression-tests-a-gauger-names.md)).
A test that pins behaviour the order keeps passes before the change, as it should; the step names it in its out doc's `regressionTests` (the Gauger's schema `gauge`), by the name the runner reports.
Each named test must be one the step added, matched by its whole reported name, in a file where it declared a test and not in a comment, and pass; one that fails, is skipped or is no test the step added fails the proof.
The step's other tests must still fail as above, and there must be at least one, so a run with regression tests only proves nothing.
`testsUnchanged` keeps a regression test as it keeps the step's other tests, and the test-design lens checks that each one pins behaviour the order keeps: a Taster that reviews a diff gets the list in its change input ([tasting](../recipes/tasting.md)).

**What `testsUnchanged` keeps** ([ADR 0078](../../adr/0078-the-red-proof-reads-the-test-report-and-testsunchanged-compares-lines.md), [ADR 0274](../../adr/0274-the-red-proof-reads-line-coverage-of-the-change-and-a-test-map-not-test-names.md)).
After an attempt of a brewer with the guard succeeds, the engine compares its commits with what the step its recipe's red proof proves committed.
In a repository whose [test map](test-map.md) lists modules, at the base the batch's change starts from or at the proven step's tip, every line that step added to a separate test file of the effective map must still be there as often as before, compared trimmed, blank lines aside: imports and helpers included, so an edited import line fails the attempt too.
The guard counts each line in the file as the attempt's branch holds it, read in the clone (`git ls-tree`, then `git cat-file` of the blob it names, each bounded as a diff is), so a later step that removes its own copy of a red line, such as a `});` of a test it added, keeps the red step's copy; a file gone at the tip loses every line.
The effective map keeps every module the base lists, and the proven step's map may add modules, so a later attempt's edit of the map narrows nothing.
A file in no test area of the map, and a module whose tests are `inline`, are not guarded by its lines; the test-design lens judges inline tests against the red diff.
Where only the proven step's map lists modules, the base having none, those files keep what ADR 0078 keeps (below): a map the brewers under check wrote never guards less than no map does.
A map that cannot be read at either commit blocks the attempt on its environment.
In a repository with no map at either commit, until a batch's first step proposes one (#708), the guard keeps what ADR 0078 keeps: in each file where the step declared a test, the lines it added that declare a test or assert.
Either way, moving or reindenting a line within its file is fine, moving it to another file is a change, and fixtures, the stubs and new tests change freely.
An attempt that changed them fails, and is retried; a brewer that thinks a test is wrong reports `blocked` with `findings` instead.

## In the engine

Each recipe goes through `resolveRecipe` (ADR 0028), and one that resolves to test-first needs a red proof whose `of` is its first writing step, before any other writing step ([ADR 0064](../../adr/0064-test-first-recipes-when-onblocked-and-a-red-proof-required.md)); the red proof (`"expect": "fail"`) runs the repository's `test` check, ignores its exit code, and reads its structured test report (`testReport` in `foedrum.jsonc`: TAP on stdout or in a file, or JUnit XML) against what its `of` step committed (`git diff` from that step's first attempt to its latest success, in the clone the worktrees were added to, never in an attempt's worktree): it passes only when every test whose name a line the step added declares (ADR 0176; a string literal only in a file that declares a test at the step's tip, ADR 0262) fails, but for the regression tests the step's out doc names, which must pass ([ADR 0170](../../adr/0170-the-red-proof-accepts-the-regression-tests-a-gauger-names.md)), none passes or is skipped, and nothing in the report names a load, compile, import or collection error; otherwise it fails and follows its `onFail` route.
A brewer with the `testsUnchanged` guard runs inside `guardTests` (`src/checks/tests-guard.ts`), which fails a succeeded attempt, retryably, that removed a line the proven step added to a separate test file of the test map, or without a map a test declaration or assertion it added to one of its test files, compared line by line with the test files at the attempt's tip, or without a map from diffs, all read in the clone, with the maps (`testMaps`, `src/checks/test-map.ts`); and `foedrum serve` refuses every attempt of a batch whose red proof would run in a repository without a `testReport`, so it is Stuck on its environment before a brewer starts ([ADR 0078](../../adr/0078-the-red-proof-reads-the-test-report-and-testsunchanged-compares-lines.md)).
