# Open pull requests

What the intake does with a batch's pull request after it opens: it records its end, it records the checks GitHub runs on its head once they finish ([ADR 0213](../../adr/0213-an-open-pull-request-s-checks-on-its-head-are-recorded-once-they-finish.md)), and it checks it against its base whenever the base moves ([ADR 0198](../../adr/0198-an-open-pull-request-is-merge-tree-checked-when-its-base-moves.md)), the repository's checks on the merged tree included ([ADR 0203](../../adr/0203-an-open-pull-request-s-checks-run-on-its-merged-tree-when-its-base-moves.md)).

- **The end is recorded for every batch On tap**, a Brewery issue's and a claimed issue's alike: `pull_request.ended`, appended when a pass reads a merge or a close (`recordEnds`, `src/engine/intake.ts`).
  So is the end of the pull request a batch Brewing or Stuck brews a fix of (below), so that its action pushes nothing to it ([ADR 0219](../../adr/0219-a-failing-check-on-an-open-pull-request-sends-its-batch-back-to-a-fix-step.md)).
  A claimed batch's release waits for it ([target-repository issues](target-issues.md)); for a Brewery issue's batch it only ends the checks below.
- **Each pass then reads the checks on each open pull request's head** (`recordChecks`, `src/engine/pr-checks.ts`, [ADR 0213](../../adr/0213-an-open-pull-request-s-checks-on-its-head-are-recorded-once-they-finish.md)): for each batch On tap, the pull request its ledger opened with no recorded end and no recorded push by someone else (`openOf`, as the base check decides), its head as GitHub has it now, then every check run and commit status on that head, page after page (`githubCheckReader`, `src/github/checks.ts`), given by `foedrum serve` (`IntakeOptions.checks`).
  The first pass that sees a check running, or none at all, records `pull_request.checks_pending` with its own time, unless the latest record is already pending on that head; once every check finished, `pull_request.checks_finished` records each one's name, kind, conclusion and https link of at most 2,000 characters, at most 100, failed first, with a count of the rest, unless the latest record is finished on that head with the same checks (`sameHeadChecks`).
  A record about to be written with a failed check also reads the log of each of the first five failed checks that is a GitHub Actions job (a check run of `github-actions`, whose `id` is its job's), one at a time, as text through `gh api --allow-escape-sequences` and outside the cached reads, up to 32 MiB (`client.text`), and keeps on that check `log`: the failing step's lines from its `##[group]Run` line to the first `##[error]` line, without timestamps and escape sequences, else the log before `Post job cleanup.`, read for secrets and cut to 4,000 characters from its end (`jobLogExcerpt`, `src/checks/job-log.ts`), or one line why it could not be read (404, 410, 403, an empty answer, a failed read, or the pass's minute for job logs was up after the record's reads began, while a record whose first read would start after it waits for the next pass; a read GitHub's rate limit holds is tried again on a later pass, with no record of that head until then) [ADR 0228](../../adr/0228-a-failed-actions-job-s-log-goes-with-the-batch-back-to-its-fix-step.md).
  An unchanged record reads no log again, and a log never makes two records differ.
  No check at all is recorded finished only by a pass after one that recorded that head, since the repository's workflows may not have registered theirs yet.
  Every check counts: `success`, `neutral` and `skipped` pass, every other conclusion fails (`checkPassed`); a check run not completed and a commit status `pending` run.
  Every open head is read on every pass, one recorded finished too: a re-run that passed is recorded on the same head, and a check that registers after the others finished records it pending again; the latest record is how the checks stand now, never for good.
  A head that moved is read from the start, and a record of another head never counts for it.
  **There is no deadline**: the engine waits as long as the checks run, and the status comment says since when (a written exception to "every wait has a deadline" beside a person's pause, an open interactive session and a blocked sub-order, [invariants](../engine/invariants.md)).
  A read that fails is reported and records nothing; the next pass tries again.
- **Each pass then checks the open pull requests against their base** (`checkBases`, `src/engine/base-check.ts`): for each batch On tap, the pull request its ledger opened with no recorded end, and the commit its push recorded.
  It reads each base's tip once per pass, as the push's own fetch reads it (`BranchPush.baseTip`, [ADR 0090](../../adr/0090-the-push-fetches-the-base-in-a-git-directory-of-its-own.md)), so a merge into the base by anyone counts.
  A tip the pull request was last checked against, or else the base the batch's last merge read ([ADR 0164](../../adr/0164-a-batch-merges-its-base-before-its-last-check.md)), runs nothing.
  When the tip moved, the bottle branch's tip on the remote is read first (`BranchPush.remoteTip`): when someone else pushed to it, no merge-tree runs and nothing is posted, the check is recorded once with that tip (`branchMoved`), and the pull request is checked no more.
  A tip that moved is merged with the head by `git merge-tree --write-tree` in a git directory of Foedrum's own with the clone's objects, so no hook or merge driver of the clone's takes part (`openMergeTree`, `src/workspace/merge-tree-git.ts`).
  Each check is recorded as `pull_request.base_checked`, with the tip and the conflicting files, at most 50, when there are any.
  A tip or a merge-tree that fails records nothing and is reported; the next pass tries again.
- **A clean merge of a batch with checks to run is handed to the merged-check run**, which records it instead (`BaseCheckRepository.checks`, [ADR 0203](../../adr/0203-an-open-pull-request-s-checks-run-on-its-merged-tree-when-its-base-moves.md)).
  The checks are those of the batch's recipe's check step that merges the base (`mergedCheckStep`, `src/engine/merged-checks.ts`), Nip's `green`.
  The run (`createMergedChecks`) runs beside the ticks and the pass in `foedrum serve`, one at a time in the Cellar, from a queue of each pull request's newest due tip; just before a run and again before its record the log is read again, and a run is dropped when its pull request ended, left the lane, or was checked since it was handed on (a newer tip, a moved branch).
  It reads the checks as a check step's attempt does, setup first (`checkTree`, `src/checks/check-runner.ts`; `mergedCheckRun`, `src/cli/merged-check-run.ts`), in a worktree of a commit of the merged tree on head and tip, made from a git directory of Foedrum's own that borrows the clone's objects and holds a copy of its tags and remote-tracking refs (`openMergedTree`, `src/workspace/merge-tree-git.ts`); no hook or configuration of the clone's takes part, and the check sandbox binds the clone's objects for it only because that git directory is a direct `.git` child of `git-dirs/`, which Foedrum alone writes ([the check sandbox](../checks/sandbox.md)).
  `foedrum serve` stops the run underway and waits for it on every way out, before it closes the store.
  Its deadline is that step's, at most 55 minutes, so the cleanup's floor of an hour holds for the `<uuid>.tree` a killed run leaves.
  The check records the first reading that did not pass (`failed`), or why the checks did not run (`unchecked`), so each tip is run at most once; a stop records nothing, and a kill leaves nothing recorded, so the next pass hands the run on again.
- **A conflict is posted on the pull request** when it first appears or its set of files changes, one comment through the ledger, `[batch, "base_conflict.<n>"]`, found by its marker (`baseConflictEffects`).
  A new tip with the same files, and a clean merge, post nothing.
- **A check that fails on the merged tree is posted on the pull request** when it first fails: the check before it was clean, conflicted, unchecked or failed another check, one comment through the ledger, `[batch, "base_check_failed.<n>"]`, numbered apart from the conflicts and due from the same effect ([ADR 0209](../../adr/0209-a-check-that-fails-on-an-open-pull-request-s-merged-tree-is-posted-on-it.md)).
  It names the check as the status line does (`checkOf`, `readingText`) and the base's tip, and holds the recorded tail, already cut and read for secrets, in a fence longer than any run of backticks in it, with each `<!--` opened so no marker is posted.
  The same check failing again, an `unchecked`, and a pass post nothing.
- **The status comment shows the latest check** under its pull requests: the tip and files of a conflict, that it merges cleanly again after one, the check that fails on the merged tree and how, why the checks did not run there, that it passes its checks again after either, or that it is not checked since someone else pushed to its branch; and, on a line of its own, that it waits for its checks on the head since when, passed them, failed them with the first failing check with a link (else the first), its conclusion and how many more failed (at least, when the record left checks out), or has none (`checkLines`); no checks line once someone else pushed to its branch; nothing once the pull request ended ([GitHub](../humans/github.md)).
- **A failing check on the head the batch pushed sends it back to a fix step**, when its recipe's `openPullRequest` step has `onPullRequestFail` ([ADR 0219](../../adr/0219-a-failing-check-on-an-open-pull-request-sends-its-batch-back-to-a-fix-step.md)).
  The supervisor's tick, not the intake, issues `fix_pull_request` for a batch On tap whose latest record finished on the commit of its latest push with a check `checkPassed` refuses and that a person's skip did not leave as it is, unless a pause holds its order or the whole Brewery ([pause and continue](../humans/pause.md)) (`failedPullRequest`, `src/engine/pull-request-fix.ts`); a record a re-run turned green, a pending one, and a head someone else pushed send nothing.
  `decide` schedules the route's `goto` with `route: { from, why: 'pull_request', pullRequest, head }`, and the attempt gets the failed checks as its `route` input, each with the excerpt of its job's log or why it could not be read ([ADR 0228](../../adr/0228-a-failed-actions-job-s-log-goes-with-the-batch-back-to-its-fix-step.md)); once the rounds are used, or when the route's step was skipped by its `when`, the batch is Stuck (`pull_request_failed`) with the first five failed checks.
  The recipe's steps run again, the last check merging the base, and the action pushes the round's task tree to the same branch under `[batch, "push.<n>"]`, never forced, without opening the pull request again, then renders its body again unless someone edited it ([the openPullRequest action](../recipes/open-pull-request.md), [ADR 0227](../../adr/0227-a-later-round-renders-the-pull-request-s-body-again-unless-someone-edited-it.md)); a branch someone else pushed to or deleted since gets no push, which the round's push result records (`moved`, `gone`), and the pull request is passed over from then on.
  The cleanup keeps the task tree's branch of a batch On tap while its pull request is open, so a fix round has a tree to start from.
- **A record that finished with none failed on the head the batch pushed, with no conflict and no failing check on the merged tree, gets a merge brief on the pull request**, one per ready record, which the status comment links ([GitHub](../humans/github.md), [ADR 0225](../../adr/0225-a-ready-pull-request-gets-a-merge-brief.md)).
- **A conflict with a moved base or a failing merged-tree check leaves the batch On tap**: sending it back along the same route is #547.
- **It needs git 2.38**, for `merge-tree --write-tree`: `foedrum doctor` requires it, so `foedrum serve` does not start on an older git ([ADR 0200](../../adr/0200-foedrum-requires-git-2-38.md)).
