# Working on Foedrum

Foedrum is a GitHub-native orchestrator that runs Claude agents (brewers) through user-defined pipelines (recipes) and turns issues into pull requests. These are the rules for working on Foedrum's own code.

## Where things are

- Design: `docs/architecture.md` (the map), the pages under `docs/design/` (one concept per page), `docs/glossary.md` ([ADR 0149](docs/adr/0149-docs-layout-a-map-and-one-page-per-concept.md))
- Decisions: `docs/adr/` — read the relevant ADR before changing a design decision; a change of mind is a new ADR
- Plan: `ROADMAP.md` and the GitHub milestones/issues
- Dependencies: `DEPENDENCIES.md`, `.npmrc`
- Defaults: `defaults/` (brewers, recipes, lenses) loads under every Brewery's own files, found from the install, never the working directory; a Brewery file of the same name replaces the default, except `defaults/models.jsonc`, which the Brewery's `models.jsonc` merges over by alias ([ADR 0153](docs/adr/0153-foedrum-s-defaults-map-their-own-model-aliases.md)) (`loadRecipes`, [ADR 0098](docs/adr/0098-foedrum-s-defaults-load-under-the-brewery-s-files-and-a-brewer-input-can-name-a-lens.md))

- Plugin: `plugin/` (one Markdown skill per `/foedrum:<command>`, each running `foedrum <command> … --via plugin`; `/foedrum:init` runs a checkout's `src/cli/main.ts` until `foedrum` is on the PATH, ADR 0212) with this repository as its marketplace (`.claude-plugin/marketplace.json`); a command of the registry has a skill or a `terminalOnly` reason, which `test/unit/plugin-parity.test.ts` checks ([ADR 0125](docs/adr/0125-the-foedrum-plugin-is-markdown-skills-that-run-the-terminal-with-via-plugin.md))

Use the glossary terms (Brewery, order, sub-order, brewer, recipe, batch, step, attempt, out doc, gravity reading, bottle, Conditioning, Stuck) consistently in code, docs and messages.

## Commands

- `npm ci` — install (never `npm install` in CI; lifecycle scripts are disabled)
- `npm run check` — typecheck, lint, test, the test-layer guard (`scripts/check-test-layers.ts`: unit, property and chaos tests and `test/helpers/` never import `node:child_process` or the real process runner; integration tests and helpers never start the real `gh`, except the opt-in end-to-end serve test, ADR 0086) and the offline dependency guard, in one command. It runs only the test files the change reaches (the files that differ from the merge base with `origin/main`, followed through their imports; `package.json`, the lock file, `tsconfig.json`, `scripts/`, `test/helpers/` and `test/fixtures/` reach every test, docs none), without coverage, and names them first; `npm run check -- --all` runs every test file with coverage, as CI does ([ADR 0241](docs/adr/0241-each-test-runs-at-the-stage-where-it-pays-the-check-runs-the-test-files-a-change-reaches.md)). Run it while coding and before the push; the push gate runs `npm run check -- --no-tests` (every step but the tests), and CI runs every test ([ADR 0249](docs/adr/0249-the-push-gate-runs-no-tests.md)). When `node_modules` does not match `package-lock.json` it fails at once with `run npm ci`. A step is killed with every process it started after 300 s or past 4 MiB of output (ADR 0035). How it works: `.claude/rules/check-and-tests.md`
- `npm run typecheck` · `npm run lint` · `npm test`. `npm test` fails below the coverage thresholds in `package.json`'s `test` script (only ever raise them) and, in CI only, when a file in `test/unit/` uses more than 5 s of CPU time (15 s in `test/property/` and `test/chaos/`); a file over its limit is measured again alone and the lowest reading counts, and outside CI it is only listed in the "test file times" block (ADR 0036, ADR 0089, ADR 0136). Every test process refuses to start a process, through any import (ADR 0038)
- `npm run check:deps` — the dependency guard with publish dates (needs the registry; `npm run check` runs it offline)
- `npm run demo` — a guided walk-through in `.foedrum/tmp/demo/`: one order brewed by `foedrum serve` with Nip's steps and a parallel group of three lens steps, one of which blocks once and sends the batch back (the demo Brewery's own recipe; ADR 0185, ADR 0193), killed mid-attempt and restarted, until it is on tap; then `foedrum lenses` (ADR 0221), `foedrum brew`, `resume` and `replay`. No gh, GitHub, `claude` or network. `--no-pause` runs straight through; `--in <folder>` uses another folder in `.foedrum/tmp/`. It imports the tests' fakes, so it stays a script and is not shipped (ADR 0097, ADR 0139, ADR 0185, ADR 0193; details in `.claude/rules/demo.md`)
- `npm run schemas` — regenerate the JSON Schema files in `schemas/` after changing a zod schema (a test fails until you do)
- `npm run test:integration` — the tests against real tools in `test/integration/` (not part of `npm run check`; CI runs them)
- `npm run deps:sync` — run `npm ci` when `node_modules` no longer matches `package-lock.json` (runs automatically at session start, see Session start hooks)
- `npm run worktrees:clean` — remove worktrees and branches of merged pull requests (runs automatically at session start, see Session start hooks)
- `scripts/remove-scratch.ts`, `mutants.ts`, `mutant-verdict.ts`, `mutant-tests.ts`, `citations.ts`, `issue-draft.ts` and `house-yeast.ts` — the tools `/brew-review` runs; `scripts/adr-index.ts [--check]` — rebuilds `docs/adr/README.md`'s table and the older records' back links, run by `/brew-last-call`, not by `npm run check`, since the table lags between milestones. Their contracts are in `.claude/rules/review-scripts.md`
- CI (`.github/workflows/ci.yml`) runs `npm run check -- --all`, `npm run test:integration` and `npm audit signatures` on Windows, macOS and Linux, each on the newest Node 24, for every pull request, the property tests again with `FOEDRUM_RUNS=500` (500 seeds per property instead of the check's few) and the chaos tests with `FOEDRUM_RUNS=200` on the Linux leg (on every leg with 1,000 each in the nightly run, ADR 0134), `npm run check:deps` on one leg, and `npm run audit:advisories` (`npm audit --omit=dev`, one retry when the advisory endpoint fails, never read as clean) once per run in a job of its own ([ADR 0119](docs/adr/0119-npm-audit-runs-once-per-ci-run-with-one-retry-on-an-outage.md)); the required check is `ci-ok`, which needs both
- `/brew-review [pr-number | branch] [--base <ref>] [--no-comment] [--red-proof]` — in Claude Code, review a draft pull request (or the current branch) with `.claude/skills/brew-review/`
- `/brew-sheet [topic | #issue | #pr] [--mermaid]` — in Claude Code, explain a part of Foedrum with one verified picture (`.claude/skills/brew-sheet/`); also how pull request and issue descriptions explain themselves
- `/brew-audit [--since <sha> | --full]` — in Claude Code, a read-only audit of the code and the ADRs at `origin/main` (security, architecture, over-engineering, complexity, smells, AI slop, tests): the workflow `.claude/workflows/brew-audit.js` runs an auditor per area and a skeptic per auditor; its report stays under the main checkout's `.foedrum/tmp/audits/<sha>/` and it files nothing. `/brew-last-call` runs it since the previous last call
- `/brew-last-call <milestone>` — in Claude Code, by hand only, before a milestone closes: its open issues, a prompt audit and sizes of Foedrum's instruction files (with `.claude/rules/`), and one draft pull request with the proposals (`.claude/skills/brew-last-call/`); `node scripts/instruction-sizes.ts [--since <commit>]` prints the sizes
- Run TypeScript directly with `node` (built-in type stripping); no build step for development
- `node src/cli/main.ts <command>` — the `foedrum` program (its `bin`) from a checkout: `serve` (the Cellar, until Ctrl+C; ADR 0063), `doctor`, `init [--<question> <answer>]... [--no-input]` (a Brewery's files from a few questions, each answerable by its option, `--no-input` refusing a question no option answers, ADR 0212; outside a clone it creates and clones the Brewery's repository, then the intake labels after asking, a commit and push after asking, the `foedrum` command in a user folder on the PATH after asking, and doctor; ADR 0199, ADR 0207, ADR 0210), `status [--watch]` (a board of the live batches on a terminal; ADR 0188), `stuck`, `brewers` (each brewer's attempts, outcomes, Stuck batches and tokens; ADR 0159), `lenses` (each lens's rounds, findings and how they ended, and its tokens; ADR 0221), `replay <batch>`, `resume <batch> [<step>[#<n>]]` (a finished attempt's session in its worktree, ADR 0126; on a running batch, a takeover that continues its step's session until its out doc, ADR 0127), `brew <issue> [--as <name>] [--take] [--new-window]` (one batch as a driver of its own, ADR 0123, owned by `--as`, else the Claude Code session, else `terminal`, ADR 0259; on a terminal it opens an interactive step as a `claude` session in the foreground, and `--new-window` starts it in a new terminal window, ADR 0222), `takeover <batch> [--as <name>]` (hand a batch to another driver; ADR 0124), and the commands that change state (`retry`, `skip`, `answer`, `recipe`, `rewind`, `cancel`, `order`, and `pause [<order> | --all] [--by <time>] [--why <reason>]` and `continue [<order> | --all]`, ADR 0202; `stop <order> [--why <reason>]`, ADR 0205; `rank <order> [<place>] [--why <reason>]` (a place `n` or `first`), ADR 0208); `--help` lists them

## Local gate

A project hook in `.claude/settings.json` runs `npm run check -- --no-tests` (typecheck, lint and the guards, no tests; CI runs every test on the pull request, [ADR 0249](docs/adr/0249-the-push-gate-runs-no-tests.md)) before every `git push` in a Claude Code session, through both the Bash and PowerShell tools. If the check fails, the command is blocked and the failure output is shown. `gh pr create` gets no check of its own: the push before it checked the tree it opens ([ADR 0135](docs/adr/0135-the-gate-drops-the-check-on-gh-pr-create-the-graphql-readers-and-the-alias-rule.md)). It also refuses `gh pr ready` until the pull request has the /brew-review summary for its head ([ADR 0060](docs/adr/0060-the-gate-refuses-gh-pr-ready-without-the-review-summary.md)), unless it changes only plain documentation ([ADR 0067](docs/adr/0067-a-pull-request-of-only-plain-docs-needs-no-review-summary.md)), and blocks `npx` and its relatives when they would download a package that isn't in `package-lock.json` ([ADR 0065](docs/adr/0065-the-gate-refuses-npx-of-packages-not-in-the-lockfile.md)).

- The hook is `scripts/precheck.ts` and runs as `node "${CLAUDE_PROJECT_DIR}/scripts/precheck.ts" || { s=$?; [ "$s" = 2 ] || echo "Foedrum gate could not run (exit $s); command blocked." >&2; exit 2; }` in bash (Git Bash on Windows), so it behaves the same in PowerShell, Git Bash, macOS and Linux sessions. Its logic is in `scripts/precheck/`, one file per part ([ADR 0252](docs/adr/0252-the-push-gate-is-a-pre-filter-a-reader-and-a-pure-core-beside-a-thin-hook.md)): `prefilter.ts` (the pre-filter, which imports nothing and is the hook's only static import), `read.ts` (the lexer and the reader, with the refusals it makes as it reads), `core.ts` (the pure policies on what the reader found, and `gate`); `precheck.ts` keeps the shell functions that start git, gh and npm, and loads `core.ts` only after the pre-filter. Put a reading rule in `read.ts`, a policy in `core.ts`, a process in `precheck.ts`.
- node runs the script directly, without npm, which would add about 0.4 s to every call (#41). For the check, precheck runs `npm run check -- --no-tests` with npm's CLI found next to that node (`findNpmCli` in `src/platform/executables.ts`): `<node dir>/node_modules/npm/bin/npm-cli.js` on Windows; on macOS and Linux `<prefix>/lib/node_modules/npm`, then `<prefix>/libexec/lib/node_modules/npm` (Homebrew), then `<prefix>/share/nodejs/npm` (Debian's npm package), each with `bin/npm-cli.js`. When it is in none of them, the gated command is blocked with every path it tried.
- The command is anchored to the project root, so the gate runs even after a `cd` into a directory with another `package.json`.
- The hook fails closed. If node or `scripts/precheck.ts` is missing, or the script crashes, `|| exit 2` blocks the command with node's error and the exit code, and `onFailure: "block"` does the same on Claude Code ≥ 2.1.295. precheck's own block (exit 2) passes through as it is.
- The hook runs before every Bash and PowerShell call, with no `if` filter: a filter only sees the start of a compound command, so `mkdir x && git push` would slip through. precheck finds the push anywhere in the command, and exits at once when the command mentions none of `git`, `gh`, `push`, `merge`, `ready`, `pwsh`, `powershell`, `npx`, `npm`, `dlx` and `bun`, and does not both mention one of `rm`, `rd`, `ri`, `del`, `erase` and `remove` and hold a `$`, `%`, backtick, `(` or `@`: the checkout's path and the call's description do not count ([ADR 0056](docs/adr/0056-the-gate-pre-filter-reads-the-command.md), [ADR 0065](docs/adr/0065-the-gate-refuses-npx-of-packages-not-in-the-lockfile.md), [ADR 0102](docs/adr/0102-the-gate-blocks-a-recursive-delete-of-a-path-built-from-a-variable.md), [ADR 0138](docs/adr/0138-the-gate-reads-four-more-forms-of-a-recursive-delete-of-a-computed-path.md)).
- precheck reads a command the way its tool's shell would, and what that command runs in turn both as bash and as PowerShell ([ADR 0045](docs/adr/0045-the-local-gate-reads-commands-as-the-shells-would.md)). Quotes and escapes count, so text in a one-line string is not a command; the lines of a multi-line string are read as commands too. It skips environment assignments, reserved words (`then`, `do`, …), PowerShell assignments and wrapper words (`command`, `env`, `time`, `xargs`, `Start-Process`, …). It reads `npx` and its relatives as wrappers too, but lets them run only a binary the lockfile installed (see below). It reads what other shells, evaluators and interpreters run (`bash -c`, `pwsh -Command` and `-EncodedCommand`, `cmd /c`, `eval`, `iex`, `node -e`, `python -c`) and `$( )` substitutions. A program or git subcommand computed at run time counts as git push, and a `gh pr` action computed at run time is blocked. It knows git's own options before the subcommand, with and without a value; an option it does not know may take the next word, so the command counts as a push to check: held to every remote's configuration, refused by the denylist scan while a list is set, with force and delete read over every word after it, a later `-C` blocking it as a directory the gate cannot tell, and a later `-c` or `--config-env` that sets a push setting counting as configuring git ([ADR 0256](docs/adr/0256-the-push-gate-reads-git-s-option-values-and-checks-a-push-behind-an-option-it-does-not-know.md)). Arguments computed at run time are not evaluated: run `git push` as a plain command. Aliases are not read: a git or gh alias defined in the session is not followed, nor its definition blocked (ADR 0135). The gate guards against mistakes by sessions, not against a determined adversary; GitHub's ruleset on `main` is the real protection.
- A check that times out also blocks. The gate gives the check 540 s, after its steps' own 300 s and before the hook's 600 s, and kills the check's whole tree at that deadline or when the gate is stopped (Ctrl+C, the end of the hook). A pushed tree whose `scripts/check.ts` does not know `--no-tests` fails with a line that says to merge `origin/main`.
- Before the check, the gate compares `node_modules` with `package-lock.json` in the checkout it runs in (the same check as `deps:sync` and `npm run check`) and, when they differ, blocks with one line: `node_modules is out of date with package-lock.json (<why>); run npm ci`.
- The gate checks the tree a command pushes ([ADR 0104](docs/adr/0104-the-gate-checks-the-tree-a-command-pushes.md)): the detached-HEAD check, the `node_modules` check and `npm run check` for `git push`, and the lookup for `gh pr ready`, run in the directory the command changes into before them (`cd`, `pushd`, `Set-Location` and their aliases, lasting for the rest of the command; `env -C`, `sudo -D`, read as getopt does; git's `-C`, the last one winning, each resolved against the ones before it), resolved against the hook's working directory, with `~` and Git Bash's `/c/…` read as the shell would. A push whose directory is computed at run time (`cd "$d"`, `git -C $d`, `cd -`, `popd`, a bare `cd`, `wsl --cd`, or a nested command after a change of directory) is blocked with one line: push from inside the worktree; so is a `gh pr ready` without a number (give the number). A directory outside `CLAUDE_PROJECT_DIR` (by real path; on Windows a network, device or other-drive path is outside without being touched), or in a review's scratch folder under `.foedrum/tmp/`, is blocked with one line before anything runs there, since the gate would run that tree's check script before the command is approved; so is any change of directory when `CLAUDE_PROJECT_DIR` is not set. A command that pushes from two directories is blocked too: one tree per command.
- Before the check, a `git push` from a checkout whose HEAD is detached (`git symbolic-ref -q HEAD` exits 1 in that directory) is blocked with one line: commits made on a detached HEAD are on no branch, so the push would stop short (#80). Switch to the branch, move it to those commits, and push again. That git call gets 10 s; when it times out or is killed, the push is blocked with one line too (#42).
- After the detached-HEAD check, a `git push` is checked against your personal denylist, when you have one ([ADR 0114](docs/adr/0114-the-gate-blocks-words-on-a-personal-denylist-in-what-leaves-the-machine.md)): the file `FOEDRUM_DENYLIST` names, or else `~/.config/foedrum/denylist.txt`, one word per line, `#` for comments; it never goes into the repository. The gate reads, from git's stdout, the commits `HEAD --not --remotes=<remote>` that the remote the push goes to does not have (the remote the command names, else the branch's push remote by name, else `origin`; 15 s per git call, three at most), merges as the lines added against every parent: their authors, committers, messages, file paths and added lines, binary files as text; and the pushed branch's name and every refspec destination, reported as `branch name` ([ADR 0246](docs/adr/0246-the-push-gate-reads-option-prefixes-git-s-configuration-branch-names-and-the-starting-directory.md)). A word matches case-insensitively, on word boundaries and inside identifiers (camelCase, kebab-case, snake_case and dotted names are split). A hit blocks the push with one line naming up to ten places (commit and file and line, or field) and counting the rest, never the word. So does a list that is there, or that `FOEDRUM_DENYLIST` names, but cannot be read; a command that pushes to more than one remote; a remote computed at run time or given as a URL or path; and a git log that fails. Tags and other refs a push sends besides `HEAD` are not read: push the branch of the checkout you changed. What gh posts is read against the same list before anything else runs ([ADR 0132](docs/adr/0132-the-gate-reads-what-gh-posts-against-the-personal-denylist.md)): the `-t`/`--title`, `-b`/`--body` and `-F`/`--body-file` of `gh pr` and `gh issue` `create`, `edit` and `comment`, and the `title` and `body` fields (`-f`, `-F`, `--field`, `--raw-field`, `@file` read) and `--input` file of `gh api`, files read where gh runs (a regular file of at most 256 KiB, never a `~` path; on Windows no network, rooted or drive-relative path: give it relative or as a full Windows path), a JSON `--input` by its fields; a hit names the field or the file and line. A title or body computed at run time, read from standard input (`-`, `@-`), holding a PowerShell escape such as `` `n ``, or from a file it cannot read blocks while a list is set: give it inline or in a file. The file is read before the command runs: write it with the file tool first, never in the same command. Without a list nothing runs. `foedrum doctor` says whether one is set. Tests use fixture words and never read the real list.
- Before `gh pr ready <n>` (also with `-R`/`--repo`, or without a number for the current branch's pull request), the gate looks the pull request and its files up with `gh pr view` and its commits with `gh api`, 30 s each. It lets the command through only when a comment headed ``## Review: `<branch>` @ `<sha>` `` (`summary-template.md`) names the head, or a commit after which the branch has only merges, as when origin/main was merged after the summary was posted (#146), or when every file is `*.md` in a subfolder of `docs/` other than `docs/adr/` (#183); a file list it cannot read, one cut off at gh's 100 files, or one with a renamed or copied file (listed by its new path only) counts as not exempt. Otherwise it blocks with one line: no summary, a summary for an older head, or a pull request it could not read. The remedy is `/brew-review <n>`, never a way around the gate. `gh pr ready --undo` always passes. Run `gh pr ready` as a command of its own: in the same command as `git push` it is blocked, because the lookup runs first and would see the old head; so it is in a command that mentions `GH_REPO` or `GH_HOST` (use `-R`; the last one counts, as in gh). Any argument computed at run time (or splatted, `@args`) is blocked, since it may name another repository. Give the number.
- The check runs on the working tree of that directory, not on the commits being pushed. Commit everything before pushing, and push the branch of the checkout you changed: pushing another branch (`git push origin other`), or a push whose checkout the gate cannot see (`git --git-dir`, `Start-Process -WorkingDirectory`), checks the wrong tree.
- Always blocked, without running the check:
  - force pushes in any form (`--force`, `--force-with-lease`, `--force-if-includes` and their prefixes such as `--forc`, `-f`, a `+refspec`);
  - pushes that delete, prune or mirror remote refs (`--delete`, `--prune`, `--mirror` and their prefixes such as `--del`, `-d`, a `:branch` refspec), also when git's configuration asks for it: `-c` or `--config-env` setting `remote.*`, `push.*` or `include*`, any `GIT_CONFIG*` in the command, a command that also runs `git config` or `git remote`, or a configured `remote.<r>.mirror` or a `+` or `:` push refspec of the remote ([ADR 0246](docs/adr/0246-the-push-gate-reads-option-prefixes-git-s-configuration-branch-names-and-the-starting-directory.md)); `git push -h`/`--help` alone is help, not a push;
  - a `git push` whose starting directory, not only one it changes into, is outside the project or in a review's scratch folder under `.foedrum/tmp/` ([ADR 0246](docs/adr/0246-the-push-gate-reads-option-prefixes-git-s-configuration-branch-names-and-the-starting-directory.md));
  - `gh pr merge`, also with `-R`/`--repo`;
  - merging a pull request through `gh api` ([ADR 0108](docs/adr/0108-the-gate-blocks-merges-through-gh-api.md)), with the `gh pr merge` message: a `PUT` (`-X PUT`, `-XPUT`, `-iX PUT`, `--method PUT`, `--method=put`, any case, the last one counting as in gh; or a method computed at run time) to a path or URL ending in `pulls/<n>/merge` before any query string (`repos/{owner}/{repo}/…`, a full `https://` URL, a prefix computed at run time). A `GET` of `…/pulls/<n>/merge` only asks whether it is merged and passes. GraphQL is not read (no mutation names, no endpoint forms, no unreadable queries), and merging branches (`mergeBranch`, `POST repos/<owner>/<repo>/merges`) is not either: the ruleset on `main` and the maintainer's merge own merging (ADR 0135);
  - commands nested too deeply to check (more than 8 levels of shells and substitutions);
  - a recursive delete whose path is built from a variable or a substitution, with one line that says to write the literal path: `rm` with `-r`, `-R` or `--recursive` in any flag form, `Remove-Item` and its aliases (`rm`, `ri`, `del`, `erase`, `rd`, `rmdir`) with `-Recurse`, or cmd's `rd`, `rmdir`, `del` and `erase` with `/s`, given `$x`, `${x}`, `$env:X`, `%X%`, `$( )`, backticks, or in PowerShell `@( )` or a `( )` argument, also cmd's switches written onto the name (`rd/s/q %X%`) and a PowerShell pipeline from such a stage (`$p | Remove-Item -Recurse`); and any splat into a delete, with or without recursion (`Remove-Item @o`, also bash's `rm @o`). Literal paths, globs and deletes without recursion pass ([ADR 0102](docs/adr/0102-the-gate-blocks-a-recursive-delete-of-a-path-built-from-a-variable.md), [ADR 0138](docs/adr/0138-the-gate-reads-four-more-forms-of-a-recursive-delete-of-a-computed-path.md));
  - `npx`, `npm exec` and `bunx` of anything but a binary the lockfile installed (`node_modules/.bin/<name>` in the package around the hook's working directory; never a `-p`/`--package` value), and `pnpm dlx`, `pnpx` and `yarn dlx`, which always download, with one line: they would download a package that isn't in `package-lock.json`, past the dependency guard. In a command that also changes directory (`cd`, `pushd`, `popd`, `Set-Location`, a drive letter, `env -C`, `sudo -D`, `wsl --cd`, npx `--prefix`) they are blocked too, since npx would look in another `node_modules` ([ADR 0065](docs/adr/0065-the-gate-refuses-npx-of-packages-not-in-the-lockfile.md)).

  The deny rules in `.claude/settings.json` are the first layer; the hook also catches forms the rules miss, such as `git -C <dir> push -f`, `gh -R owner/repo pr merge` or `bash -c "git push -f"`.
- `npm run check` fails on a permission rule in `.claude/settings.json` that Claude Code warns about at startup or skips (`scripts/startup-warnings.ts`, which links the docs it follows; update it when they change).
- Never bypass the gate. Fix the failure, or ask the user.
- Format with `npm run lint -- --write` (Biome), never with `npx prettier` or another formatter: `npx` only runs what the lockfile installed.
- There are no git hooks: they would need an install script, and lifecycle scripts are disabled. Outside Claude Code, run `npm run check` yourself before pushing.

## Read guard

The read-only agents (`taster`, `brett`, `auditor`) read only inside the checkout ([ADR 0049](docs/adr/0049-reviewers-read-only-inside-the-checkout.md)). A `PreToolUse` hook in their frontmatter runs `scripts/read-guard.ts` before every `Read`, `Grep` and `Glob`, failing closed like the local gate.

- A path gets through only when it resolves inside `CLAUDE_PROJECT_DIR`. `~` and the working directory are applied first, and then the real path of its deepest existing part (`src/platform/real-path.ts`), which resolves links, junctions, short names and case. On Windows, network, device and drive-less paths, and paths on another drive than the checkout's, are blocked without touching them. Anything else is blocked with one line.
- Every agent whose only tools are `Read`, `Grep` and `Glob` must carry the same hook block; a unit test checks it. Main sessions do not run the guard: they have a shell, and they read Claude Code's own files outside the checkout.
- Brewers cannot use the hook, because `--safe-mode` turns it off. They get the rule from file-tool allow rules scoped to the worktree in their attempt settings.

## Session start hooks

Two `SessionStart` hooks in `.claude/settings.json` run when a session starts or resumes; how they work is in `.claude/rules/deps-sync.md` and `.claude/rules/worktrees-clean.md`.

- First, synchronously, `npm run deps:sync` in `${CLAUDE_PROJECT_DIR}`: it runs `npm ci` when `node_modules` no longer matches `package-lock.json`, so no gate runs against a half-installed tree after a `git pull`. It never fails the session, never runs `npm install` and never changes the lock file.
- In the main checkout only, in the background, `npm run worktrees:clean`: it removes worktrees directly under `.claude/worktrees/` and local branches whose pull request was merged (tip merged into `origin/main`, own upstream gone), and stale worktree records. It keeps worktrees with uncommitted or untracked changes, worktrees locked by a live session, and locked records whose folder is gone, so lock a worktree on a removable or network drive that may be absent at session start. It never deletes remote branches, never prompts and never fails the session.
- Run either by hand from any checkout.

## Temporary files

Everything a session or a test creates stays inside the checkout, so it is visible and easy to clean up.

- Never write to the system temp directory (`%TEMP%`, `/tmp`, `os.tmpdir()`, or a tool's own scratch directory) while working on Foedrum.
- Use `.foedrum/tmp/` at the root of the current checkout or worktree (git-ignored); create it when missing. Group files per issue: `.foedrum/tmp/<issue-number>/` for scripts, scratch files, captured output and logs.
- Tests that need a directory create it under `.foedrum/tmp/tests/`, through a shared test helper, and remove it afterwards.
- `npm test` and `npm run test:integration` run through `scripts/with-checkout-tmp.ts`, which points `TEMP`, `TMP` and `TMPDIR` at a fresh `.foedrum/tmp/tests/tmpdir-*` folder and removes it afterwards, so node's coverage files, the temp files of the git and npm processes the integration tests start, and anything that uses `os.tmpdir()` stay in the checkout. `NODE_V8_COVERAGE` would not do this: the test runner always works in `os.tmpdir()` and only copies the files there at the end.
- Delete what you no longer need before opening the pull request.
- Never `rm -rf` or `Remove-Item -Recurse` a path built from a variable or a substitution (`rm -rf "$dir"`, `rm -rf "$(…)"`): write the literal path, such as `rm -rf .foedrum/tmp/218/run`. An empty or wrong variable removes the wrong tree; the gate blocks such a command (see Local gate, "Always blocked").

## Dependencies

- Built-in Node first: `node:sqlite`, `node:test`, `fetch`, `node:crypto`, `node:child_process`, `util.parseArgs`, `node:http`.
- Runtime dependencies: `zod` only. Never add a package without completing the admission checklist in `DEPENDENCIES.md` in the same pull request.
- Never weaken `.npmrc` (`ignore-scripts`, `min-release-age`, `save-exact`, `allow-git=none`, `allow-remote=none`, `omit=peer`, `engine-strict`).
- No `pre*`/`post*` scripts in `package.json`.
- Wrap every dependency behind an internal module.

## TypeScript

- Node ≥ 24.15. `strict`, `erasableSyntaxOnly`, `verbatimModuleSyntax`.
- No `enum`, no namespaces with runtime code, no parameter properties, no decorators. Use `import type` for types and explicit `.ts` extensions in relative imports.
- Zod schemas in `src/schemas/` are the single source of types, runtime validation and generated JSON Schema.
- Discriminated unions with exhaustive `switch` and a `never` check for every state, event and step outcome.

## Engine rules

- The engine is deterministic code; it never asks a model to decide what to do next.
- State changes only by appending events; current state is a pure fold. No mutable state outside the event store, except leases, the state branch's pushed-through marker (ADR 0024), the out docs the store keeps until a flush pushes them (ADR 0103), the work root's Brewery marker and driver locks (ADR 0037), the state worktree's writer lock (ADR 0107), and the time of each status comment's last edit, which a driver keeps to edit an order at most once a minute (ADR 0072).
- Every external side effect (git push, pull request, comment, label) goes through the idempotency ledger, except the state-branch push itself, which is idempotent through the pushed-through marker (ADR 0024), and the claim ref of a target-repository issue, which only one Brewery can create and the claimant finds by its record (ADR 0043).
- Every wait has a deadline. A batch must never be able to sit silently. The exceptions are a person's pause, which the status comment shows (ADR 0202); a sub-order blocked by another, which has no batch until its blockers' pull requests merge (ADR 0211) and, for a `release` blocker, until a release of its repository is recorded after that merge (ADR 0216): before the merge the blocker's open pull request is what waits on a person, after it the release; an open pull request's checks on its head, waited for as long as CI runs, with the status comment saying since when (ADR 0213); and an interactive step's open session, a person at work, with the status comment saying since when it is open (ADR 0222).
- Brewers never ask questions mid-run; `AskUserQuestion` is always denied. Questions are a `needs_input` outcome. An interactive step's brewer talks with the person in its session, and still never calls `AskUserQuestion` (ADR 0222).
- Keep orchestration token-free; anything sent to a model must justify its tokens.

## Cross-platform

Foedrum runs on Windows, macOS and Linux; CI tests all three.

- Paths only through `node:path`, `os.homedir()` and `os.tmpdir()`; never string-built paths or `~`. (`os.tmpdir()` is for product code at run time; development and tests use `.foedrum/tmp/`, see Temporary files.)
- In `src/` and `scripts/`, spawn git and other tools with argument arrays and no shell, through the process runner in `src/platform/processes.ts` (`execProcess`, or `spawnProcess` in scripts; `streamProcess` for a long stream such as `claude`'s, line by line with a limit per line and input on stdin, ADR 0046, and on Windows only with `jobObject: true`, ADR 0047). Integration tests may also start a node fixture with `spawnSync` and a `timeout` when the test is about something other than the runner. The runner kills the whole tree at a deadline, when stopped, or when the output passes its limit (`maxOutputBytes`, 4 MiB by default; ADR 0035), which `execFile` cannot, since it waits for every output pipe to close. A program a person drives in the foreground (a resumed claude session, ADR 0126, or an interactive step's session, ADR 0222) starts through `foregroundProcess`, with the terminal's stdio, an environment it is given and no deadline; a new terminal window (`brew --new-window`) starts through `launchProcess`, detached with its stdio ignored, settled on exit (ADR 0222). The only shell spawns are `.cmd` and `.bat` files on Windows (npm's `claude.cmd`, `npm.cmd`), which the runner starts through cmd.exe by its full path, with `NoDefaultCurrentDirectoryInExePath` set and every argument validated and quoted (`windowsCommandLine`; ADR 0031); prompts go via stdin. The one other is a check step's command line from `foedrum.jsonc` or a Brewery's recipe, which `execProcess` with `shell: true` starts as it is through `/bin/sh -c`, or cmd.exe by its full path with `NoDefaultCurrentDirectoryInExePath` (`shellCommand`; ADR 0069); outside native Windows, `serve` hands the check runner `sandboxedChecks` (`src/platform/check-sandbox.ts`), which starts that line as `/bin/sh -c <line>` inside bwrap or sandbox-exec, without a shell of its own (ADR 0076); the check runner also passes `jobObject: true`, so on Windows it runs inside a Job Object. A repository's `setup` line from `foedrum.jsonc` starts the same way, with `shell: true` and `jobObject: true`, through the check sandbox with the network kept (`sandboxedChecks` with `network: true`), outside native Windows (ADR 0158). A caller whose tree must not outlive a kill on Windows (the brewer runner) passes `jobObject: true`: the runner then starts the program inside a kill-on-close Job Object through a PowerShell helper, about 0.4 s per call, and the program does not start when no job can be made (ADR 0039).
- OS-specific behaviour (killing process trees, executable lookup, file-lock retries) lives in the platform module only.
- A session or a test kills only processes it started, by their PID (`taskkill /PID <pid> /T /F`, `process.kill(pid)`), never by name, filter or window title (`taskkill /IM`, `taskkill /FI`, `pkill`, `killall`, `Stop-Process -Name`): several sessions share one machine, and a filter also ends theirs (#128).
- Text files use LF; parsers tolerate CRLF and a BOM.

## Tests

- Test-first, always: red → green → refactor ([ADR 0017](docs/adr/0017-test-first-recipes-and-tasting-lenses.md)).
  - Commit the failing test before the implementation, so the red step is visible in the pull request and can be checked out and run. Push red and green together. Pull requests are merged with a merge commit (no squash), so the red → green history stays on `main`; every merge commit is green, so use `git log --first-parent` and `git bisect start --first-parent`.
  - Red means the new test runs and fails because the behaviour is missing: a failed assertion, or an error thrown by the code under test (including a stub that throws "not implemented"). A test file that fails to load, compile or import is not red. Add a minimal stub when needed to get there.
  - A new test that passes immediately is not a red step; commit it labelled as a regression test. That includes a control test written beside a red test to show that behaviour next to the change stays as it is: one test, one case. In a brewed change, the Gauger names it in its out doc's `regressionTests` instead ([ADR 0170](docs/adr/0170-the-red-proof-accepts-the-regression-tests-a-gauger-names.md)).
  - A red commit may also add the types and schemas the new tests need to compile, as long as no new test tests them directly and every function behind them is a stub that throws "not implemented". A test tests a schema directly when it calls the schema itself (`parse`, `safeParse`) or asserts what it accepts or rejects; such a schema starts as a stub. Nothing else goes into a red commit: an unrelated rename or cleanup is a refactor commit of its own.
  - A refactor commit changes code without changing behaviour: it adds, changes and removes no test declarations and changes no expected value, all tests pass before and after it, and its message starts with "Refactor". It needs no red step. When it changes a function's signature, it may change the tests' call arguments, imports and helpers to match, and nothing else in a test. When it touches behaviour no test covers, first add a test that pins that behaviour (it passes before and after the refactor: a regression test), then refactor. A refactor that needs a test changed is a test fix in its own commit first, with the reason.
  - A commit that removes code together with only its tests is a commit of its own whose message starts with "Remove": the tests that cover the code it keeps pass before and after it, and no kept assertion changes. It needs no red step.
  - Moving or renaming existing tests (to another file or to `test/integration/`) is a commit of its own, with no other change, and its message says it is a move.
  - The red proof runs once, in stage 1 of `/brew-review <n>` ([ADR 0134](docs/adr/0134-the-red-proof-runs-once-the-review-drops-its-coverage-delta-and-property-and-chaos-run-on-one-leg-per-pull-request.md)). Pushed commits are never rewritten, so a wrong order found there ends in a blocker that can only be dismissed. When you are unsure of the order, run `/brew-review --red-proof` before the push and fix what it finds by redoing the commits that are not pushed yet (`git reset` to the last pushed commit, then commit again in the right order).
  - Do not weaken a red test's assertions to make the implementation pass. If the test is wrong, fix it in its own commit and say why. Helpers, fixtures and imports may change.
  - Exempt: spikes (throwaway code), scaffolding, documentation and CI configuration. Say so in the pull request.
  - Prompts (skills, agent definitions, lens and brewer files) are exempt from red proof, but not from verification: a change to a prompt is exercised before merging — for the review skill and lenses by a /brew-review run against the planted-defect sample (test/fixtures/brew-review/planted-demo; for the acceptance lens, test/fixtures/brew-review/planted-acceptance), later by the Flight ([docs/design/evaluation.md](docs/design/evaluation.md)). A new or changed default brewer's prompt (`defaults/brewers/`) is tried by the maintainer on real issues after the merge, not by the issue session; its tests use the fake runner (decided 2026-10-28).
- `node:test` and `node:assert`. Inject dependencies (clock, `fetch`, process runner, brewer runner) instead of mocking modules.
- Unit tests, and the property and chaos tests that `npm test` also runs, never start a process (git, npm, node, bash, `claude`, `gh`) ([ADR 0021](docs/adr/0021-unit-tests-spawn-no-processes.md)). Put the decisions in a pure core tested with plain data, and the commands in a thin shell tested with a fake process runner and captured tool output. Real tools run only in `test/integration/` (`npm run test:integration`): a few tests per tool boundary, run by CI, not by `npm run check`. Keep `npm run check` under 20 s. The import check's exception list in `scripts/check-test-layers.ts` stays empty, and its real-gh list holds only the opt-in end-to-end serve test (ADR 0086), unless a reviewer accepts the reason.
- No test of any layer depends on the machine it runs on. None reaches a login (gh's, git's credentials, `claude`'s), the OS keyring, the network or a remote service (github.com, a package registry), not even behind an opt-in: a login state or a service's answer comes from a stub or a captured answer. An integration test runs real local tools against fixtures it makes, with stubs first on the `PATH` for the tools it does not test, and gives the code it runs deadlines that only guard against a hang, unless the deadline is what the test covers: then the test drives it through injected timers (`cuedTimers()`), or reads the wall clock only as the bullet on the wall clock below allows ([ADR 0070](docs/adr/0070-tests-never-hold-the-wall-clock-to-a-limit.md)). An assertion that accepts whatever the machine has (a tool `missing` or any version) tests nothing. `npm run check` refuses an integration test that can start the real `gh` (ADR 0086): give `doctorFromCheckout`, `serveFromCheckout` and `cliFromCheckout` an `exec` (`cannedGhLogin()`), and a spawn of `gh` its own `GH_CONFIG_DIR` in the call. The one exception is the opt-in tests against the real `claude` (below, ADR 0057): they run whichever `claude` is installed, but only when asked for, and against the fake Messages API, so they reach no login and no remote service. When a change alters what the code starts, reads or waits for, check the existing integration tests that run it too.
- A red or a green step runs only the test files it changes (`node --test <files>`). Run `npm run check` once before the push, not after every red/green pair (ADR 0054): the gate runs no tests, CI runs them all. When the change reaches every test file (`scripts/`, `test/helpers/`, `defaults/`, `schemas/` and more), run the files you changed, each alone, and let CI run the rest: the full suite does not fit the 300 s step on a laptop running several sessions.
  - An existing assertion that the new behaviour changes is updated in the red commit, beside the new tests, so it fails there and passes at green; a test fix for any other reason goes in a commit of its own, with the reason. A test added after green is labelled "regression test" in its commit.
- `npm run check` does not run `test/integration/`. When you change code that an integration test covers (find them with `grep -l <module> test/integration/`), also run those integration files once before the push (`node scripts/with-checkout-tmp.ts --import ./scripts/lower-priority.ts --test <files>`), and in a review round once after the round's fixes, not after each fix, and never for a change to documentation alone. Not the whole suite: it takes over ten minutes on a busy machine, and its long tests (the demo, the test-first recipe) time out under the load of other sessions. CI runs the whole suite on every leg (#93 failed there on all six).
- On a developer's machine (`CI` not set), `npm test`, `npm run check`, `npm run test:integration` and the review skill's test runs lower their own priority to below normal, and every process they start inherits it, so a test run on every core leaves the terminal and other sessions responsive (`scripts/below-normal-priority.ts`, [ADR 0054](docs/adr/0054-test-runs-below-normal-priority-and-review-runs-scoped-to-the-question.md)). A loaded machine can raise the CPU time the per-file budget measures, more so at below-normal priority, so outside CI a file over the budget only shows in the report, and in CI it is run again alone (ADR 0089, ADR 0136).
- Test behaviour through public interfaces, not implementation details; a test should fail when the behaviour breaks and survive a refactor.
- No test holds the wall clock to a limit, since load from other sessions stretches it (only a lower bound may read it, [ADR 0075](docs/adr/0075-only-a-lower-bound-reads-the-wall-clock-and-doctor-runs-against-stub-tools.md)): drive an injected clock or timers, prove "at once" by an order of events, wait for an end with `waitUntil` (a hang guard, not a measure), and measure a performance property in CPU time; show the fix red under a modelled load first (`test/helpers/load.ts`, [ADR 0070](docs/adr/0070-tests-never-hold-the-wall-clock-to-a-limit.md)).
- Every change comes with tests. Engine changes must keep the property tests (invariants I1–I6) and the chaos tests green.
- Use the fake brewer runner for engine tests. Tests against the real `claude` CLI are opt-in: they run only with `FOEDRUM_REAL_CLAUDE=1` (`test/helpers/real-claude.ts`), skip otherwise with that name in the message, and fail when it is set and `claude` is not on PATH. They test Foedrum's code (the runner, with the fake Messages API in `test/integration/fake-messages-api.ts`: no login, no tokens), never whether `claude` itself works ([ADR 0057](docs/adr/0057-real-claude-tests-are-opt-in-and-claude-proofs-leave-the-suite.md)).

## Git and pull requests

- One branch per issue: `<issue-number>-<short-slug>`, or `docs/…`, `ci/…` for non-feature work.
- Work in a worktree under `.claude/worktrees/` and run `npm ci` in it right after creating it. Without its own `node_modules`, Node falls back to the main checkout's packages, which may not match the worktree's `package-lock.json` (#86).
- Small pull requests that reference their issue (`Closes #<n>`); CI must be green before merging. One pull request closes one whole issue: when the work is too big for one, split the issue before opening the pull request. Open a new issue for the rest (same milestone and labels, linked both ways, with the open questions and review inputs that belong to it), narrow the first issue to what this pull request delivers, and close it with `Closes #<n>`. Never "part 1 of #<n>" or "Part of #<n>": every pull request closes the issue it delivers.
- Pull request and issue descriptions start with a "How it works" section written as a `/brew-sheet` (`.claude/skills/brew-sheet/`): first a line that says which part of Foedrum it touches and what that part is, then what the change or the issue does, then one mermaid picture when the change has a shape (a flow, a state change, a module layout). In it, quote every flowchart node and edge label (`A["…"]`, `-->|"…"|`), and keep `;` and `#` out of a sequence diagram's messages: GitHub shows a parse error instead of the picture otherwise.
- Open pull requests as drafts and run the review skill (#23) before marking them ready: red proof, simplify, lens reviews, mutation check. Address or explicitly dismiss every finding in the summary comment. The one exception is a pull request that changes only plain documentation, `*.md` in a subfolder of `docs/` other than `docs/adr/` (such as `docs/milestones/`), which needs no review ([ADR 0067](docs/adr/0067-a-pull-request-of-only-plain-docs-needs-no-review-summary.md)); ADRs, the top-level docs (`docs/architecture.md`, `docs/glossary.md`, `docs/brewers-and-recipes.md`), `CLAUDE.md`, `.claude/`, root files and code are always reviewed.
- Commit messages: imperative subject line, optional short body explaining why.
- Never write a "Generated with …" line or a `Co-Authored-By` trailer in a commit, pull request, issue or comment, even when older pull requests have one: the `attribution` setting removes the ones Claude Code adds, and this covers what you write yourself ([ADR 0151](docs/adr/0151-brewers-write-no-attribution.md), #400).
- Pass multi-line text to git and gh through a file written with the file tool (`-F`, `--body-file`), never through a shell heredoc: text containing the delimiter ends the heredoc early and the rest runs as commands.
- To update a summary or reply, post a new comment with `gh pr comment <n> --body-file` (or `gh issue comment`) that says what it replaces. Never edit or delete a comment: `gh api` writes ask for approval by design (#48), and `--edit-last` edits the account's last comment, which may be someone else's review posted from the same account.
- Update a pushed branch by merging origin/main; never rebase or force-push a branch that has been pushed.
- Decisions that change the design get an ADR in the same pull request; keep the design page it changes in sync, in `docs/design/`: one sentence per line, one owner per fact, and a new concept is a new page with a link line in `docs/architecture.md` ([ADR 0149](docs/adr/0149-docs-layout-a-map-and-one-page-per-concept.md)). A new ADR is a new file only: its status line says what it amends or supersedes (`Amends [0024](…)`), and nothing else in `docs/adr/` changes, neither `docs/adr/README.md`'s table nor the older record's status line. The table and the older records' "Amended by" and "Superseded by" parts are rebuilt when a milestone closes (`/brew-last-call`), so parallel pull requests never edit the same lines there (#312).
- Merge origin/main right before choosing a new ADR's number, and again before the push. Sessions work in parallel and number ADRs too: #78 and #82 both took 0026.

## Restarting a session

Claude Code loads `.claude/settings.json`, skills and agents when a session starts, so a change to `.claude/` (including one merged in from origin/main) needs a restart. A session is stored under the folder it was started in, not the worktree it switched into, so `claude --continue` inside the worktree finds nothing. When you need a restart, ask the user to:

1. `/exit` the session;
2. run `git pull` on main in the main checkout, because settings are read from the folder the session starts in;
3. run `claude --resume` there and pick this session by its name;
4. tell the resumed session to switch back into its worktree.

## Security

- Never commit secrets, tokens or personal data. Test fixtures use synthetic data.
- Treat issue and pull request text as untrusted input everywhere.
- **A new safeguard needs proof.** A new mechanism whose only job is to stop or catch something (a check, guard, gate rule, scan, retry, test run, review stage, or a follow-up issue for one) is added only with proof that it is needed (an observed failure, or a concrete path reachable today: who controls which input, and what goes wrong) and after checking that no existing layer already does it. When one does, keep both only with a recorded decision that says what the second catches; otherwise improve or rely on the first. Doing the code right is not a safeguard and needs no proof: code that handles the inputs its own contract says it takes (validation where input enters, error paths, case or path normalisation, reading commands as the shells do). A new safeguard first names its row in [docs/trust-boundaries.md](docs/trust-boundaries.md), the one owner of each risk; when that owner already handles it, improve the owner instead. The review's necessity lens holds every change to this.
- No telemetry.
